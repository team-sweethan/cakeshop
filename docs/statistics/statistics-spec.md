# 관리자 기간별 통계 명세

## 1. 문서 개요

### 1-1. 목적

이 문서는 `/admin/statistics`에서 제공하는 기간별 통계의 업무적 정의와
조회 기준을 정한다. 각 지표의 계산 방식과 데이터 소유권을 명확히 하여
화면, SQL, 테스트가 동일한 기준을 사용하도록 한다.

### 1-2. 대상

- 대상 화면: `/admin/statistics`
- 기능 성격: 관리자용 기간별 통계 조회
- 구현 위치: `domain/statistics`
- 조회 방식: 화면은 읽기 전용 ReadModel을 사용하고 배치는 파생 집계 데이터를 저장한다.

### 1-3. 문서 사용 원칙

- 이 문서를 관리자 기간별 통계의 구현 정본으로 사용한다.
- `확정`된 항목만 구현 계약으로 사용한다.
- `합의 필요`와 `보류` 항목은 관련 담당자 확인 전까지 구현하지 않는다.
- 별도 상태 표시가 없는 항목은 `확정`으로 본다.
- 지표의 정의를 변경할 때 문서와 테스트를 함께 갱신한다.

## 2. 구현 범위

### 2-1. 1차 구현 대상

- 조회 기간 선택
- 일별 집계
- 총 주문 건수
- 완료 주문 건수
- 취소 주문 건수
- 총매출
- 기간별 주문 건수와 매출 추이
- 조회 조건에 따른 빈 결과 표시
- 관리자 권한 검사
- 과거 날짜용 일별 통계 집계 테이블
- 통계 집계 배치와 재집계 기능
- 기존 원본 데이터의 초기 통계 적재
- 운영자 CLI를 통한 지정 기간 수동 재집계

### 2-2. 후속 구현 대상

- 상품별 주문·판매·매출 및 매출 순위
- 신규 회원 수
- 탈퇴 회원 수
- 새 게시글 수
- 환불 금액
- 쿠폰 사용 건수
- 평균 주문 금액

후속 항목은 관련 업무 정의와 집계 기준이 확정된 후 구현한다.

### 2-3. 제외 범위

- 일간 조회와 시간대별 추이 그래프
- 시간대별 픽업 건수
- 관리자 화면을 통한 통계 데이터의 수동 등록·수정·삭제
- 주문·결제·환불 등 업무 상태 변경
- 엑셀·CSV 다운로드
- 전년 또는 이전 기간 대비 증감률
- 매출 예측과 상품 추천
- 실시간 자동 갱신
- 고객용 통계 화면

### 2-4. 조회 전략

- 원본 주문·결제 데이터가 통계의 최종 정본이다.
- 통계 전용 집계 데이터는 원본으로부터 다시 생성할 수 있는 파생 데이터로 관리한다.
- 관리자 통계 화면은 집계가 완료된 어제까지의 날짜만 일별 집계 테이블에서 조회한다.
- 오늘 날짜는 통계 화면에서 조회하지 않으며 원본 테이블로 전환해 실시간 조회하지 않는다.
- 원본 테이블은 초기 적재와 일별 집계·재집계에서만 읽는다.
- 원본 조회는 읽기 전용 ReadModel Mapper에서 수행하고, 조회 결과로 파생 집계 데이터를 생성·교체한다.
- 파생 집계 데이터 쓰기는 별도의 통계 Mapper에서 수행하며 `daily_statistics`와
  `daily_product_statistics`만 변경한다.

### 2-5. 조회 유형

- 조회 유형은 `RECENT_WEEK`, `RANGE`, `WEEKLY`, `MONTHLY`로 구분한다.
- `RECENT_WEEK`는 어제를 포함한 최근 7일을 조회하고 일별 추이를 표시한다.
- `RANGE`는 별도 화면 버튼 없이 시작일·종료일 직접 선택에 사용한다.
- `WEEKLY`는 월요일부터 일요일까지의 완료된 한 주를 조회하고 일별 추이를 표시한다.
- `MONTHLY`는 완료된 한 달의 1일부터 말일까지 조회하고 주차별 추이를 표시한다.
- 화면에는 왼쪽부터 최근 일주일·주간·월간 선택 버튼을 표시한다.
- 최초 진입에서는 `RECENT_WEEK`를 선택하고 최근 일주일 버튼을 활성화한다.
- 최근 일주일은 기존 최초 조회와 동일한 기간 계산을 사용하며 별도의 집계 기준을 추가하지 않는다.
- 사용자가 시작일이나 종료일을 직접 변경하면 `RANGE`로 전환한다.
- 네 조회 유형 모두 `daily_statistics`를 사용하며 별도의 집계 테이블을 추가하지 않는다.
- 주간 조회는 월 경계와 관계없이 월요일부터 일요일까지 전체를 포함한다.
- 월간 추이의 한 주는 월요일부터 일요일까지로 구분하되 선택한 월의 날짜만 포함한다.
- 월초와 월말의 주차는 7일보다 짧을 수 있고 월에 따라 최대 6주차까지 표시한다.
- 월간 주차 라벨에는 주차 번호와 실제 집계 시작일·종료일을 함께 표시한다.

## 3. 공통 조회 및 기간 규칙

- 모든 통계 날짜는 `Asia/Seoul`을 기준으로 한다.
- 시작일과 종료일을 모두 포함하여 조회한다.
- 실제 조회 범위는 시작일 00:00 이상, 종료일 다음 날 00:00 미만으로 한다.
- 조회 유형과 조회 조건이 없으면 `RECENT_WEEK`로 어제를 포함한 최근 7일을 조회한다.
- `RECENT_WEEK`는 별도의 날짜 조건을 받지 않고 최신 조회 가능일을 종료일로 하여 7일을 계산한다.
- 주간 조회 조건이 없으면 가장 최근에 완료된 월요일부터 일요일까지 조회한다.
- 월간 조회 조건이 없으면 가장 최근에 완료된 달의 1일부터 말일까지 조회한다.
- 주간·월간 조회는 완료된 주와 완료된 달만 허용한다.
- 시작일과 종료일 중 하나만 입력한 요청은 유효하지 않은 요청으로 처리한다.
- 시작일은 종료일보다 늦을 수 없고, 종료일은 어제보다 늦을 수 없다.
- 최대 조회 기간은 시작일과 종료일을 포함하여 366일로 제한한다.
- 집계가 완료되었지만 데이터가 없는 날짜는 `0`으로 표시하고 날짜 오름차순으로 반환한다.
- 사용자가 선택한 기간에 미집계 날짜가 하나라도 포함되면 부분 결과를 반환하지 않고
  집계가 완료되지 않았다는 오류를 표시한다.

## 4. 지표 정의

### 4-1. 주문 통계

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 총 주문 건수 | 조회 기간에 생성된 주문 수 | `orders.created_at` | 모든 주문 상태 | 확정 |
| 완료 주문 건수 | 조회 기간에 생성되어 픽업까지 완료된 주문 수 | `orders.created_at` | `PICKED_UP` | 확정 |
| 취소 주문 건수 | 조회 기간에 생성되어 취소 또는 반려가 완료된 주문 수 | `orders.created_at` | `CANCELED`, `REJECTED` | 확정 |

- 주문 ID를 기준으로 중복 없이 집계한다.
- `EXPIRED` 주문은 총 주문 건수에는 포함하고 취소 주문 건수에서는 제외한다.
- `/admin`의 오늘 주문은 결제 승인 기준이고, 이 화면의 총 주문은 주문 생성 기준이므로
  서로 다른 지표다.

### 4-2. 매출 통계

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 총매출 | 조회 기간에 승인되어 현재 유효한 결제 금액의 합계 | `payments.approved_at` | `DONE` | 확정 |

- 결제 금액은 `payments.amount`를 사용한다.
- 취소·환불된 결제는 총매출에서 제외한다.
- 부분 취소는 현재 지원 범위에 포함하지 않는다.

### 4-3. 기간별 추이

- `RECENT_WEEK`, `RANGE`, `WEEKLY`의 일별 주문 건수는 총 주문 건수와 같은 기준으로 집계한다.
- `RECENT_WEEK`, `RANGE`, `WEEKLY`의 일별 매출은 총매출과 같은 기준으로 집계한다.
- `MONTHLY`의 주차별 주문·매출은 해당 주차에 포함된 일별 집계값을 합산한다.
- 주문과 매출은 기준 시각이 다르므로 같은 일자나 주차의 값이 직접 대응하지 않을 수 있다.

### 4-4. 상품별 통계와 매출 순위

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 상품별 주문 건수 | 조회 기간에 생성되어 해당 상품을 포함한 주문 수 | `orders.created_at` | 모든 주문 상태 | 확정 |
| 상품별 판매 수량 | 조회 기간에 승인되어 현재 유효한 결제에 포함된 상품 수량의 합계 | `payments.approved_at` | `DONE` | 확정 |
| 상품별 매출액 | 조회 기간에 승인되어 현재 유효한 결제 금액 중 해당 상품에 귀속되는 금액의 합계 | `payments.approved_at` | `DONE` | 확정 |

- 상품은 `order_items.product_id`로 식별하고 상품명은 주문 당시의
  `order_items.product_name` 스냅샷을 사용한다.
- 상품별 주문 건수는 주문 ID를 기준으로 중복 없이 집계한다.
- 상품별 판매 수량은 유효한 결제에 연결된 `order_items.quantity`를 합산한다.
- 상품별 매출액은 쿠폰 할인이 반영된 `payments.amount`를 사용한다.
- 한 주문에 여러 상품이 포함될 수 있으며 실제 결제액은 각 주문 항목의
  `order_items.total_amount / orders.original_amount` 비율로 배분한다.
- 배분 전에 `orders.original_amount`와 해당 주문의 `order_items.total_amount` 합계가
  일치하는지 검증하고, 일치하지 않으면 해당 날짜의 집계를 실패 처리한다.
- 원 단위 미만을 버린 뒤 남은 금액은 배분값의 소수 부분이 큰 주문 항목부터 1원씩 배분하고,
  소수 부분이 같으면 `order_items.id` 오름차순으로 배분한다.
- 한 주문의 상품별 매출액 합계는 해당 주문의 `payments.amount`와 일치해야 한다.
- 취소·환불된 결제는 상품별 판매 수량과 매출액에서 제외한다.
- 조회 기간에 주문 또는 판매 이력이 있는 전체 상품을 순위 조회 대상으로 삼는다.
- 매출 순위는 매출액 내림차순, 판매 수량 내림차순, 주문 건수 내림차순,
  상품 ID 오름차순으로 정렬하여 `1`부터 중복 없는 순번을 부여한다.
- 날짜별 상품명은 해당 행의 주문 또는 판매 집계에 포함된 주문 항목 중 `orders.created_at`이
  가장 최근인 항목의 스냅샷을 사용하고, 생성 시각이 같으면 `order_items.id`가 큰 항목을 사용한다.
- 화면에는 조회 기간 중 해당 상품의 가장 최근 집계일에 저장된 상품명 스냅샷을 표시한다.

### 4-5. 회원 활동 통계

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 신규 회원 수 | 조회 기간에 가입한 일반 회원 수 | `members.created_at` | `role = 'USER'` | 확정 |
| 탈퇴 회원 수 | 조회 기간에 탈퇴가 완료된 일반 회원 수 | `members.withdrawn_at` | `role = 'USER'`, `status = 'WITHDRAWN'` | 확정 |

- 신규 회원은 현재 상태와 관계없이 가입이 발생한 날짜에 집계한다.
- 가입 후 같은 날 탈퇴한 회원은 신규 회원과 탈퇴 회원에 각각 포함한다.
- 관리자는 신규 회원과 탈퇴 회원 집계에서 제외한다.
- `withdrawn_at`이 `NULL`인 회원은 탈퇴 회원 집계에서 제외한다.
- 탈퇴 통계는 정지·활성화 이력용인 `member_status_histories`를 사용하지 않는다.
- 일별 집계 범위는 서울 시간 기준으로 집계일 00:00 이상, 다음 날 00:00 미만으로 한다.

### 4-6. 커뮤니티 활동 통계

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 새 게시글 수 | 조회 기간에 작성된 일반 커뮤니티 게시글 수 | `posts.created_at` | 모든 게시글 상태와 카테고리 | 확정 |

- 게시글 ID를 기준으로 중복 없이 집계한다.
- 작성 후 삭제되거나 차단된 게시글과 작성자가 이후 탈퇴한 게시글도 포함한다.
- 별도 테이블에서 관리하는 공지사항은 제외한다.
- 일별 집계 범위는 서울 시간 기준으로 집계일 00:00 이상, 다음 날 00:00 미만으로 한다.

### 4-7. 쿠폰 사용 통계

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 쿠폰 사용 건수 | 조회 기간에 결제가 완료되어 현재도 유효한 쿠폰 사용 건수 | `payments.approved_at` | 회원 쿠폰 `USED`, 결제 `DONE` | 확정 |

- 회원 쿠폰 ID를 기준으로 중복 없이 집계하고 모든 쿠폰 종류를 포함한다.
- `member_coupons.applied_order_id`로 주문의 유효한 결제와 연결한다.
- `RESERVED`, `AVAILABLE`, `ENDED` 상태의 회원 쿠폰과 `DONE`이 아닌 결제는 제외한다.
- 주문 취소·환불로 쿠폰이 복구되면 기존 결제 승인일의 통계에서도 제외하고 재집계로 반영한다.
- 일별 집계 범위는 서울 시간 기준으로 집계일 00:00 이상, 다음 날 00:00 미만으로 한다.

### 4-8. 환불 통계

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 환불 금액 | 조회 기간에 결제 취소가 완료되어 반환된 금액의 합계 | `payment_cancellations.canceled_at` | `status = 'DONE'` | 확정 |

- 환불 금액은 `payment_cancellations.cancel_amount`를 합산한다.
- 고객 취소, 관리자 취소, 주문제작 반려와 시스템 보상 취소를 모두 포함한다.
- `REQUESTED`, `FAILED` 상태와 `canceled_at`이 `NULL`인 취소 요청은 제외한다.
- 현재 지원하는 전액 취소를 집계하며 부분 취소는 지원 범위가 확정될 때 별도로 정의한다.
- 취소 이력을 생성하지 않는 0원 주문 취소는 합계가 `0원`이므로 환불 금액에 영향을 주지 않는다.
- 일별 집계 범위는 서울 시간 기준으로 집계일 00:00 이상, 다음 날 00:00 미만으로 한다.

### 4-9. 평균 주문 금액

| 지표 | 정의 | 기준 시각 | 포함 조건 | 상태 |
|---|---|---|---|---|
| 평균 주문 금액 | 조회 기간의 유효 결제 금액 합계를 유효 결제 주문 수로 나눈 금액 | `payments.approved_at` | `status = 'DONE'` | 확정 |

- 분자는 총매출과 같은 `payments.amount` 합계를 사용한다.
- 분모는 `payments.order_id`를 기준으로 중복 없이 센 유효 결제 주문 수를 사용한다.
- 쿠폰 할인이 반영된 실제 결제 금액을 사용하며 0원 결제도 분모에 포함한다.
- 취소·환불된 결제는 분자와 분모에서 모두 제외한다.
- 유효 결제 주문이 없으면 `0원`으로 표시하고, 계산 결과는 원 단위로 반올림한다.
- 기간 평균은 일별 평균의 평균이 아니라 일별 총매출 합계를 일별 유효 결제 주문 수 합계로 나누어 계산한다.
- 일별 평균 자체는 집계 테이블에 저장하지 않는다.
- 일별 집계 범위는 서울 시간 기준으로 집계일 00:00 이상, 다음 날 00:00 미만으로 한다.

## 5. 데이터 소유권과 검토 책임

| 대상 | 책임 | 담당자 | 검토 상태 |
|---|---|---|---|
| `order` | 주문 상태와 주문 건수 기준 | 주환 | 확정 |
| `payment` | 결제 상태와 매출 기준 | 주환 | 확정 |
| `payment` | 결제 취소 상태·완료 시각과 환불 금액 기준 | 주환 | 확정 |
| `product` | 상품 식별자와 상품명 표시 기준 | 시은 | 확정 |
| `member` | 회원 역할·상태와 가입·탈퇴 시각 기준 | 수민 | 확정 |
| `community` | 일반 게시글의 작성 시각·상태·카테고리 기준 | 현규 | 확정 |
| `coupon` | 회원 쿠폰 상태와 사용·복구 시각 기준 | 정후 | 확정 |
| `statistics` | 통계 ReadModel과 파생 집계 데이터 | 시은 | 담당 확정 |

- 원본 테이블과 업무 상태의 정의는 해당 데이터 소유 도메인을 따른다.
- `statistics`는 원본 도메인의 상태와 업무 규칙을 별도로 정의하지 않는다.
- 원본 테이블을 처음 조회하거나 주요 조회 조건을 변경할 때 데이터 담당자의 확인을 받는다.
- 담당자 확인이 끝나면 위 표의 해당 검토 상태를 `확정`으로 변경한다.

## 6. 조회 결과, 데이터 최신성 및 화면 표시 규칙

- 요약 영역에는 총 주문, 완료 주문, 취소 주문, 총매출을 표시한다.
- `RECENT_WEEK`, `RANGE`, `WEEKLY`는 날짜별, `MONTHLY`는 주차별 주문 건수와 매출을 함께 표시한다.
- 상품별 통계는 매출 순위, 상품명, 주문 건수, 판매 수량과 매출액을 조회한다.
- 상품별 순위는 처음에 상위 5개만 표시한다.
- 조회 결과가 5개를 초과할 때만 `전체보기` 버튼을 표시한다.
- `전체보기`를 선택하면 조회된 전체 순위를 표시하고 버튼 문구를 `접기`로 변경한다.
- `접기`를 선택하면 다시 상위 5개만 표시하고 버튼 문구를 `전체보기`로 변경한다.
- 조회 결과가 5개 이하이거나 상품 통계가 비어 있거나 미집계 상태이면 전체보기 버튼을 표시하지 않는다.
- 기타 지표는 개별 카드가 아니라 `활동 지표`와 `금액 지표` 패널로 구분하여 좌우 2열로 표시한다.
- 활동 지표 패널은 신규 회원 수, 탈퇴 회원 수, 새 게시글 수, 쿠폰 사용 건수를 순서대로 표시한다.
- 금액 지표 패널은 환불 금액, 평균 주문 금액을 순서대로 표시한다.
- 각 패널 안에서는 지표명과 값을 한 행으로 나열한다.
- 모바일 화면에서는 활동 지표 다음에 금액 지표가 오도록 1열로 표시한다.
- 조회 기간에 `additional_metrics_aggregated_at`이 `NULL`인 날짜가 하나라도 있으면 활동·금액 지표를
  표시하지 않고 기타 지표가 준비되지 않았다는 안내를 표시한다.
- 기타 지표가 준비되지 않아도 기존 요약, 기간별 추이와 상품별 통계는 정상적으로 표시한다.
- 조회 기간에 `product_aggregated_at`이 `NULL`인 날짜가 하나라도 있으면 상품별 부분 결과를
  표시하지 않고 상품 통계가 준비되지 않았다는 안내를 표시한다.
- 상품별 통계가 준비되지 않아도 기존 요약과 기간별 추이는 정상적으로 표시한다.
- 건수는 천 단위 구분 기호와 `건`, 금액은 천 단위 구분 기호와 `원`을 붙인다.
- 유효하지 않은 조회 조건에는 검증 메시지를 표시하고 통계 조회를 수행하지 않는다.
- 화면에는 통계가 어제까지 제공된다는 안내를 표시한다.
- 조회 후에는 현재 조회 유형과 해당 유형의 기간 선택값을 유지한다.
- 조회 조건이 없고 전날 집계가 완료되지 않았으면 연속으로 집계가 완료된 최신 날짜를 종료일로 삼아
  최근 7일을 조회하고 집계 지연을 표시한다.
- 연속으로 집계가 완료된 날짜가 7일보다 적으면 완료된 범위만 조회하고 집계 지연을 표시한다.
- 사용자가 선택한 조회 기간은 집계 상태에 따라 자동 변경하지 않는다.
- 집계가 완료되지 않아 행이 없는 날짜를 데이터가 `0`인 날짜로 처리하지 않는다.
- 화면 조회 실패 시 원본 테이블의 실시간 집계로 전환하지 않는다.

## 7. 집계 데이터 관리

확정 통계는 어제까지 집계가 완료된 통계를 의미하며 불변 스냅샷을 의미하지 않는다.
과거 원본 데이터의 유효성에 영향을 주는 변경은 후속 배치에서 해당 날짜를 재집계하여 반영한다.

### 7-1. 일별 집계 테이블

일별 집계 테이블명은 `daily_statistics`로 하고 `statistics_date`당 한 행만 저장한다.

| 컬럼 | 역할 | 제약 |
|---|---|---|
| `statistics_date` | 통계 기준 날짜 | 기본 키 |
| `total_order_count` | 총 주문 건수 | `NOT NULL`, 기본값 `0` |
| `completed_order_count` | 완료 주문 건수 | `NOT NULL`, 기본값 `0` |
| `canceled_order_count` | 취소 주문 건수 | `NOT NULL`, 기본값 `0` |
| `total_sales_amount` | 총매출 | `NOT NULL`, 기본값 `0` |
| `new_member_count` | 신규 회원 수 | `NOT NULL`, 기본값 `0` |
| `withdrawn_member_count` | 탈퇴 회원 수 | `NOT NULL`, 기본값 `0` |
| `new_post_count` | 새 게시글 수 | `NOT NULL`, 기본값 `0` |
| `coupon_usage_count` | 쿠폰 사용 건수 | `NOT NULL`, 기본값 `0` |
| `refund_amount` | 환불 금액 | `NOT NULL`, 기본값 `0` |
| `valid_payment_order_count` | 평균 주문 금액 계산용 유효 결제 주문 수 | `NOT NULL`, 기본값 `0` |
| `aggregated_at` | 해당 날짜의 마지막 집계 완료 시각 | `NOT NULL` |
| `product_aggregated_at` | 해당 날짜의 상품별 집계 완료 시각 | `NULL` 허용 |
| `additional_metrics_aggregated_at` | 해당 날짜의 기타 지표 집계 완료 시각 | `NULL` 허용 |

- 날짜별 전체·상품별 주문·매출과 기타 지표 집계를 모두 성공한 뒤 한 트랜잭션에서
  해당 날짜의 기존 값을 교체한다.
- 업무 데이터가 없는 날짜도 모든 지표가 `0`인 행을 저장한다.
- 행이 없으면 업무 데이터가 `0`인 날짜가 아니라 집계가 완료되지 않은 날짜로 판단한다.
- 평균 주문 금액은 저장하지 않고 기간의 `total_sales_amount` 합계를
  `valid_payment_order_count` 합계로 나누어 계산한다.
- `product_aggregated_at`이 `NULL`이면 상품별 통계가 미집계된 날짜로 판단한다.
- `product_aggregated_at`이 `NULL`이 아니고 `daily_product_statistics` 행이 없으면
  상품별 집계는 완료되었지만 상품 주문·판매가 없는 날짜로 판단한다.
- `additional_metrics_aggregated_at`이 `NULL`이면 기타 지표가 미집계된 날짜로 판단한다.
- 기타 지표가 모두 `0`이어도 집계에 성공한 날짜에는 `additional_metrics_aggregated_at`을 기록한다.

### 7-2. 상품별 일별 집계 테이블

상품별 일별 집계 테이블명은 `daily_product_statistics`로 하고
`statistics_date`와 `product_id` 조합당 한 행만 저장한다.

| 컬럼 | 역할 | 제약 |
|---|---|---|
| `statistics_date` | 통계 기준 날짜 | 복합 기본 키 |
| `product_id` | 상품 식별자 | 복합 기본 키 |
| `product_name` | 주문 당시 상품명 스냅샷 | `NOT NULL` |
| `order_count` | 상품별 주문 건수 | `NOT NULL`, 기본값 `0` |
| `sales_quantity` | 상품별 판매 수량 | `NOT NULL`, 기본값 `0` |
| `sales_amount` | 상품별 매출액 | `NOT NULL`, 기본값 `0` |

- 상품별 주문 또는 판매 이력이 없는 날짜와 상품의 행은 저장하지 않는다.
- 날짜를 다시 집계할 때 해당 날짜의 기존 상품별 행을 모두 교체한다.
- `daily_statistics`와 `daily_product_statistics`의 날짜별 저장을 한 트랜잭션에서 처리한다.
- 기존 백필, 일별 배치와 수동 재집계는 두 집계 테이블을 함께 생성·교체한다.
- 백필, 일별 배치와 수동 재집계는 상품별 집계까지 모두 성공한 뒤 같은 트랜잭션에서
  `product_aggregated_at`을 DB 현재 시각으로 기록한다.
- 상품 주문·판매가 없는 날짜도 상품 행은 생성하지 않지만 `product_aggregated_at`은 기록한다.
- 관리자 화면은 선택 기간의 상품별 일별 값을 상품 ID로 합산하고 가장 최근 집계일의 상품명을 사용한다.

### 7-3. 원본 조회 인덱스

기타 지표의 일별 집계와 수동 재집계는 다음 원본 조회 인덱스를 사용한다.

| 원본 테이블 | 인덱스 | 사용 지표 |
|---|---|---|
| `members` | `idx_members_role_created_at` (`role`, `created_at`) | 신규 회원 수 |
| `members` | `idx_members_role_status_withdrawn_at` (`role`, `status`, `withdrawn_at`) | 탈퇴 회원 수 |
| `posts` | `idx_posts_created_at` (`created_at`) | 새 게시글 수 |
| `payment_cancellations` | `idx_payment_cancellations_status_canceled_at` (`status`, `canceled_at`) | 환불 금액 |
| `payment_cancellations` | `idx_payment_cancellations_updated_at_canceled_at` (`updated_at`, `canceled_at`) | 지연 완료된 환불 변경 탐색 |
| `member_coupons` | 기존 `uk_member_coupons_applied_order` (`applied_order_id`) | 쿠폰 사용 결제 연결 |
| `payments` | 기존 `idx_payments_status_approved_at` (`status`, `approved_at`) | 총매출·쿠폰 사용·평균 주문 금액 |

- 새 인덱스는 기존 컬럼의 조회 성능만 보완하며 업무 데이터와 컬럼을 변경하지 않는다.
- 새 인덱스는 기타 지표 구현 코드와 함께 새 Flyway migration으로 추가한다.
- 원본 테이블을 소유한 도메인 담당자에게 실제 집계 SQL과 인덱스를 함께 검토받는다.

### 7-4. 집계 실행 기록

집계 실행 기록 테이블명은 `statistics_batch_runs`로 하고 실행마다 한 행을 저장한다.

| 컬럼 | 역할 |
|---|---|
| `id` | 실행 기록 기본 키 |
| `batch_type` | `DAILY`, `BACKFILL` 또는 `REBUILD` |
| `status` | `RUNNING`, `SUCCEEDED`, `FAILED` |
| `source_window_started_at` | 원본 변경 탐색 시작 시각 |
| `source_window_ended_at` | 원본 변경 탐색 종료 시각 |
| `target_start_date` | 집계 대상 시작일 |
| `target_end_date` | 집계 대상 종료일 |
| `last_completed_date` | 백필 또는 수동 재집계가 마지막으로 완료한 날짜 |
| `started_at` | 실행 시작 시각 |
| `heartbeat_at` | 실행 생존 확인 시각 |
| `completed_at` | 실행 완료 시각 |
| `running_lock` | 단일 실행을 강제하는 DB 생성 컬럼 |

- `source_window_started_at`과 `source_window_ended_at`은 `DAILY` 실행에만 사용하고
  `BACKFILL`, `REBUILD` 실행에서는 `NULL`로 둔다.
- `last_completed_date`는 `BACKFILL`, `REBUILD` 실행에 사용하고 `DAILY` 실행에서는 `NULL`로 둔다.
- 성공한 `DAILY` 실행의 `source_window_ended_at`을 다음 변경 탐색의 기준으로 사용한다.
- `REBUILD` 실행 기록은 정규 일별 집계의 변경 탐색과 누락 날짜 따라잡기 기준으로 사용하지 않는다.
- 실패한 실행은 성공 기준 시각을 갱신하지 않는다.
- `running_lock`은 `RUNNING`이면 `1`, 그 외에는 `NULL`이며 UNIQUE 제약으로
  `RUNNING` 실행을 하나만 허용한다.
- 실행 중에는 날짜별 처리가 완료될 때마다 `heartbeat_at`을 DB 현재 시각으로 갱신한다.
- 새 실행 시작 시 DB 현재 시각을 기준으로 `heartbeat_at`이 1시간 이상 지난 `RUNNING`은
  비정상 종료된 것으로 판단하여 `FAILED`로 전환하고 `completed_at`을 기록한다.
- 만료되지 않은 `RUNNING`이 있으면 새 실행을 시작하지 않는다.
- 오류 상세나 SQL을 실행 기록에 저장하지 않고 별도 로그로 남긴다.
- 화면의 최신 집계일은 백필 시작일부터 `daily_statistics` 행이 끊기지 않고 연속으로 존재하는
  마지막 날짜로 판단한다.

### 7-5. 일별 집계와 재집계

- 배치는 매일 00:10 `Asia/Seoul`에 시작하고 전날을 항상 집계한다.
- `00:10`은 배치 시작 기준이며 선행 스케줄 작업에 따라 실제 시작 시각은 늦어질 수 있다.
- 일반 애플리케이션은 시작 준비가 완료된 뒤 누락된 일별 통계 따라잡기를 한 번 요청한다.
- 시작 시 DB 기준 현재 시각이 00:10 이전이면 따라잡기를 실행하지 않고 당일 00:10 정기 배치에 맡긴다.
- 시작 시 DB 기준 현재 시각이 00:10 이상이고 마지막 성공 `DAILY`·`BACKFILL`의 대상 종료일이
  어제보다 이전이면 정기 배치와 같은 일별 집계 로직으로 어제까지의 누락 날짜를 따라잡는다.
- 마지막 성공 집계의 대상 종료일이 어제 이상이면 시작 시 따라잡기를 실행하지 않는다.
- 시작 시 따라잡기는 실행 잠금을 획득한 직후 누락 여부를 다시 확인하며, 다른 인스턴스가 먼저
  어제까지 완료했다면 새 `DAILY` 실행을 남기지 않는다.
- 성공한 초기 `BACKFILL`이 없으면 시작 시 따라잡기를 실행하지 않는다.
- 시작 시 따라잡기에서 오류가 발생하면 오류 로그를 남기되 애플리케이션 시작과 요청 처리는 유지한다.
- 실행 시작 시 DB 기준 현재 시각을 변경 탐색 종료 시각으로 고정한다.
- 변경 탐색 범위는 직전 성공 실행의 종료 시각 초과부터 현재 실행의 종료 시각 이하까지로 한다.
- 첫 `DAILY` 실행은 직전 성공 실행이 없으므로 최초 `BACKFILL` 시도의 시작 시각을
  변경 탐색 시작 시각으로 사용한다.
- 재개 백필 이전에 이미 처리된 날짜에서 발생한 원본 변경도 첫 `DAILY` 실행에서 다시 탐색한다.
- 전날과 누락된 새 날짜는 주문·결제 존재 여부와 관계없이 모든 지표의 원본을 조회하여 집계한다.
- 변경 탐지는 과거 날짜의 결과에 영향을 주는 `orders.updated_at`, `payments.updated_at`과
  `payment_cancellations.updated_at`을 기준으로 한다.
- 주문 변경은 `orders.created_at`, 결제 변경은 `payments.approved_at`, 완료된 결제 취소 변경은
  `payment_cancellations.canceled_at` 날짜를 재집계한다.
- 회원 가입·탈퇴와 게시글 작성은 각 기준 시각의 새 날짜 집계에서 처리하며, 이후 상태 변경은
  해당 지표의 결과를 바꾸지 않는다.
- 결제 취소 상태 반영과 쿠폰 복구는 같은 로컬 DB 트랜잭션에서 확정하며, 어느 한쪽이 실패하면
  결제·취소·주문·쿠폰의 로컬 변경을 모두 롤백한다.
- 쿠폰 복구만 별도 트랜잭션으로 커밋하는 흐름은 허용하지 않는다.
- 위 트랜잭션에서 함께 갱신되는 `payments.updated_at`을 쿠폰 복구의 변경 탐색 기준으로 사용하여
  해당 결제의 `approved_at` 날짜를 재집계한다.
- 집계 대상은 직전 성공 실행의 `target_end_date` 다음 날부터 전날까지의 모든 날짜와
  변경 탐색 범위에서 발견한 과거 통계 기준 날짜의 합집합이다.
- 배치 작업은 DB 기반 단일 실행 잠금을 사용하여 여러 애플리케이션 인스턴스의 동시 실행을 막는다.
- 정기 배치, 초기 백필과 수동 재집계는 같은 잠금을 사용하여 동시에 실행하지 않는다.
- 같은 날짜를 반복 실행해도 결과가 중복되지 않도록 기존 값을 교체한다.
- 날짜별 재집계가 실패하면 해당 날짜의 기존 결과를 보존하고 실행 전체를 실패로 기록한다.
- 실패한 실행은 다음 실행에서 같은 변경 탐색 범위를 다시 처리한다.

### 7-6. 초기 적재

- Flyway migration은 집계 테이블과 실행 기록 테이블 구조만 관리하고 원본 데이터 집계를 수행하지 않는다.
- 초기 적재는 Flyway와 분리한 일회성 백필 작업으로 실행한다.
- 백필은 일반 애플리케이션 시작 시 자동 실행하지 않고 운영자가 CLI 명령으로 명시적으로 실행한다.
- `app.statistics.backfill.enabled=true`일 때만 백필 Runner를 활성화하며 기본값은 비활성화한다.
- 운영자는 웹 서버 없이 아래 명령으로 백필을 실행하고 종료 결과와 `statistics_batch_runs`를 확인한다.

```bash
./gradlew bootRun --args='--spring.main.web-application-type=none --spring.devtools.restart.enabled=false --app.statistics.backfill.enabled=true'
```

- 백필 성공 또는 이미 완료된 경우 종료 코드 `0`, 다른 집계 실행 중이거나 백필 실패인 경우
  `0`이 아닌 종료 코드를 반환한다.
- 성공한 백필 실행이 이미 있으면 초기 백필을 다시 시작하지 않는다.
- 백필 시작일은 집계 대상인 `orders.created_at`, `payments.approved_at`, `members.created_at`,
  `members.withdrawn_at`, `posts.created_at`,
  `payment_cancellations.canceled_at`의 가장 이른 날짜와 어제에서 6일 전 가운데 가장 이른 날짜로 한다.
- 백필 종료일은 실행 시점의 어제로 한다.
- 날짜 오름차순으로 집계하며 날짜별 집계 저장과 `last_completed_date` 갱신을 같은 트랜잭션에서 처리한다.
- 중단 후 새 백필 실행을 시작하면 가장 최근 백필 실행의 `last_completed_date`를 이어받고
  그 다음 날부터 처리한다.
- 처음부터 다시 실행해도 같은 결과가 되도록 날짜별 저장은 멱등성을 보장한다.
- 초기 백필이 완료되기 전에는 완료된 날짜만 조회할 수 있고 미집계 날짜를 `0`으로 표시하지 않는다.
- 원본 집계 대상 데이터가 모두 없어도 기본 최근 7일의 `daily_statistics` 행을 생성하고,
  `daily_product_statistics`에는 상품 행을 생성하지 않는다.
- 새 환경의 초기 백필은 날짜별 상품 집계 완료 시 `product_aggregated_at`을 함께 기록한다.
- 새 환경의 초기 백필은 날짜별 기타 지표 집계 완료 시 `additional_metrics_aggregated_at`을 함께 기록한다.

### 7-7. 운영자 수동 재집계

- 성공한 초기 `BACKFILL`이 존재할 때만 `REBUILD`를 실행할 수 있다.
- 성공한 초기 백필은 다시 실행하지 않으며, 과거 통계를 다시 계산할 때는 `REBUILD`를 사용한다.
- `REBUILD`는 일반 애플리케이션 시작 시 자동 실행하지 않고 운영자가 CLI 명령으로 명시적으로 실행한다.
- 시작일은 필수이고 종료일을 생략하면 DB 기준 현재 날짜의 어제를 사용한다.
- 시작일과 종료일은 `Asia/Seoul` 기준이며 시작일과 종료일을 모두 포함한다.
- 시작일은 종료일보다 늦을 수 없고 종료일은 어제보다 늦을 수 없다.
- 한 번에 지정할 수 있는 기간은 시작일과 종료일을 포함하여 최대 366일이다.
- 지정 기간의 모든 날짜를 오름차순으로 다시 집계하고 기존 `daily_statistics`와
  `daily_product_statistics` 행을 교체한다.
- 원본 주문과 승인 결제가 없는 날짜도 회원·게시글·쿠폰·환불 원본을 각각 조회한다.
- 개별 지표의 집계 대상 데이터가 없을 때만 해당 지표를 `0`으로 저장하고,
  상품 주문·판매가 없으면 `daily_product_statistics`에는 상품 행을 저장하지 않는다.
- 날짜별 집계 저장과 `last_completed_date` 갱신은 같은 트랜잭션에서 처리한다.
- 실행 중 오류가 발생하면 해당 실행을 `FAILED`로 기록하고 같은 명령으로 전체 지정 기간을
  다시 실행할 수 있다.
- 같은 기간을 반복 실행해도 날짜별 저장 결과가 중복되지 않도록 멱등성을 보장한다.
- 상품별 통계 도입 전 생성된 기존 `daily_statistics.product_aggregated_at`과 기타 지표 도입 전 생성된
  `daily_statistics.additional_metrics_aggregated_at`은 `NULL`로 유지한다.
- 기존 환경의 재집계 시작일은 가장 이른 `daily_statistics.statistics_date`와 집계 대상인
  `orders.created_at`, `payments.approved_at`, `members.created_at`, `members.withdrawn_at`,
  `posts.created_at`, `payment_cancellations.canceled_at`의 가장 이른 날짜 가운데 최솟값으로 한다.
- 시작일부터 어제까지 수동 재집계하여 과거 상품별 통계, 기타 지표와
  `valid_payment_order_count`를 최초 적재한다.
- 기존 `daily_statistics`의 최초일보다 앞선 원본 날짜도 재집계 대상에 포함하고, 해당 날짜의
  `daily_statistics` 행이 없으면 새로 생성한다.
- 전체 기간이 366일을 초과하면 366일 이하의 연속된 기간으로 나누어 빠짐없이 수동 재집계한다.
- 기존 환경은 전체 기간의 수동 재집계 성공을 확인한 뒤 상품별 통계와 활동·금액 지표를 사용한다.
- `app.statistics.backfill.enabled`와 `app.statistics.rebuild.enabled`는 동시에 활성화할 수 없다.
- 재집계 성공 시 종료 코드 `0`, 잘못된 날짜·다른 집계 실행 중·재집계 실패 시 `0`이 아닌 종료 코드를 반환한다.

운영자는 웹 서버 없이 다음 형식으로 수동 재집계를 실행한다.

```bash
./gradlew bootRun --args='--spring.main.web-application-type=none --spring.devtools.restart.enabled=false --app.statistics.rebuild.enabled=true --app.statistics.rebuild.start-date=2026-08-01 --app.statistics.rebuild.end-date=2026-08-10'
```

운영체제별 명령과 실행 결과 확인 방법은 [`statistics-operations.md`](statistics-operations.md)를 따른다.

## 8. 테스트 기준

- 최초 조회와 `RECENT_WEEK` 조회가 어제를 포함한 최근 7일인지 검증한다.
- 주간 기본 조회가 가장 최근에 완료된 월요일부터 일요일까지인지 검증한다.
- 월간 기본 조회가 가장 최근에 완료된 달의 1일부터 말일까지인지 검증한다.
- `RECENT_WEEK`, `RANGE`, `WEEKLY`는 일별, `MONTHLY`는 주차별 추이를 반환하는지 검증한다.
- 주간 조회는 월 경계에 걸친 주 전체를 포함하고, 월간 조회는 선택한 월 바깥 날짜를 제외하는지 검증한다.
- 월간 추이의 부분 주차, 최대 6주차와 실제 집계 날짜 범위 라벨을 검증한다.
- 시작일이나 종료일을 직접 변경하면 `RANGE`로 전환되는지 검증한다.
- 시작일·종료일 역전, 오늘·미래 날짜, 366일 초과 요청을 검증한다.
- 주문 상태별 총 주문·완료·취소 건수의 포함 및 제외 조건을 검증한다.
- `DONE` 결제만 총매출에 포함되고 취소·환불 결제가 제외되는지 검증한다.
- 신규·탈퇴 회원과 새 게시글이 각 지표의 기준 시각과 포함 조건대로 집계되는지 검증한다.
- 쿠폰 사용 건수가 결제 승인일과 회원 쿠폰 `USED`·결제 `DONE` 조건으로 집계되는지 검증한다.
- 쿠폰 복구 후 결제 변경 탐색으로 기존 승인일의 쿠폰 사용 건수가 다시 집계되는지 검증한다.
- 결제 취소 상태 반영 또는 쿠폰 복구가 실패하면 결제·취소·주문·쿠폰의 로컬 변경이 모두
  롤백되는지 통합 테스트로 검증한다.
- 완료된 결제 취소만 환불 금액에 포함되고 요청·실패 취소가 제외되는지 검증한다.
- 지연 완료된 결제 취소의 변경을 탐색하여 `canceled_at` 날짜의 환불 금액을 다시 집계하는지 검증한다.
- 평균 주문 금액이 0원 결제를 포함한 유효 결제 주문 수로 계산되고 원 단위로 반올림되는지 검증한다.
- 기간 평균이 일별 평균의 평균이 아니라 총매출 합계와 유효 결제 주문 수 합계로 계산되는지 검증한다.
- 상품별 주문 건수가 주문 생성일과 모든 주문 상태를 기준으로 중복 없이 집계되는지 검증한다.
- 상품별 판매 수량과 매출액이 승인일과 `DONE` 결제를 기준으로 집계되고
  취소·환불 결제가 제외되는지 검증한다.
- 다중 상품 주문의 실제 결제액이 주문 항목 금액 비율로 배분되고, 원 단위 나머지가
  소수 부분과 주문 항목 ID 순서에 따라 배분되는지 검증한다.
- 주문 원금과 주문 항목 금액 합계가 다르면 상품별 집계를 거부하는지 검증한다.
- 한 주문의 상품별 매출액 합계가 실제 결제액과 일치하는지 검증한다.
- 상품별 매출 순위의 정렬 기준과 중복 없는 순번을 검증한다.
- 상품별 순위가 처음에 상위 5개만 표시되고 전체보기·접기로 전체 순위를 전환하는지 검증한다.
- 상품별 순위가 5개 이하이거나 비어 있거나 미집계 상태이면 전체보기 버튼이 표시되지 않는지 검증한다.
- 조회 기간 중 가장 최근 집계일의 상품명이 표시되는지 검증한다.
- 같은 날짜에 한 상품의 이름 스냅샷이 여러 개면 가장 최근 주문 항목의 이름을 저장하는지 검증한다.
- 상품 활동이 없는 날짜에도 `product_aggregated_at`은 기록되고 상품 행은 생성되지 않는지 검증한다.
- 조회 기간에 `product_aggregated_at`이 `NULL`인 날짜가 있으면 상품별 부분 결과 없이
  미집계 안내를 표시하고 기존 기간 통계는 유지하는지 검증한다.
- 기타 지표가 모두 `0`인 날짜에도 `additional_metrics_aggregated_at`이 기록되는지 검증한다.
- 조회 기간에 `additional_metrics_aggregated_at`이 `NULL`인 날짜가 있으면 활동·금액 지표 없이
  미집계 안내를 표시하고 기존 기간·상품 통계는 유지하는지 검증한다.
- 집계가 완료된 빈 날짜는 `0`으로 반환하고 미집계 날짜는 `0`으로 위장하지 않는지 검증한다.
- 사용자가 선택한 기간에 미집계 날짜가 포함되면 부분 결과를 반환하지 않는지 검증한다.
- 관리자만 `/admin/statistics`에 접근할 수 있는지 검증한다.
- 같은 날짜를 반복 집계해도 결과가 중복되지 않는지 검증한다.
- 상품별 날짜 재집계에서 더 이상 존재하지 않는 기존 상품 행이 제거되는지 검증한다.
- 날짜별 집계 실패 시 전체·상품별 기존 결과가 함께 보존되는지 검증한다.
- 과거 주문 상태 변경과 결제 취소 후 해당 날짜를 재집계하는지 검증한다.
- 재집계 실패 시 기존 결과와 마지막 성공 기준 시각이 보존되는지 검증한다.
- 여러 애플리케이션 인스턴스에서 배치가 중복 실행되지 않는지 검증한다.
- 변경 탐색 범위의 시작·종료 경계가 누락이나 중복 없이 처리되는지 검증한다.
- 마지막 성공 집계 이후 원본 데이터가 없는 날짜도 빠짐없이 `0`행으로 따라잡는지 검증한다.
- 주문·승인 결제가 없는 날짜에도 회원·게시글·쿠폰·환불 지표를 원본 기준으로 집계하는지 검증한다.
- 애플리케이션 시작 시 DB 기준 00:10 이전에는 따라잡기를 요청하지 않고, 00:10 이상이면서 마지막
  성공 집계일이 어제보다 이전일 때만 한 번 요청하는지 검증한다.
- 마지막 성공 집계일이 어제 이상이면 애플리케이션을 다시 시작해도 새 `DAILY` 실행을 만들지 않는지
  검증한다.
- 애플리케이션 시작 시 초기 백필이 완료되지 않았으면 집계를 생성하지 않는지 검증한다.
- 시작 시 따라잡기가 실패해도 애플리케이션 시작과 요청 처리를 유지하는지 검증한다.
- 초기 백필의 반복 실행과 중단 후 재개를 검증한다.
- 재개 백필 성공 후 첫 일별 집계가 최초 백필 시작 이후의 변경을 다시 탐색하는지 검증한다.
- 성공한 초기 백필이 없으면 수동 재집계를 거부하는지 검증한다.
- 수동 재집계의 종료일 기본값, 날짜 역전, 오늘·미래 날짜와 366일 초과를 검증한다.
- 지정 기간의 기존 값 교체, 빈 날짜 `0`행 저장과 반복 실행의 멱등성을 검증한다.
- 기존 `daily_statistics`의 최초일보다 이른 회원·게시글 등 원본 날짜가 기존 환경 REBUILD 시작일에
  포함되고 앞쪽 날짜의 일별 행이 생성되는지 검증한다.
- 수동 재집계 실패 상태와 `last_completed_date`를 검증한다.
- `REBUILD` 실행 기록이 정규 일별 집계의 변경 탐색과 누락 날짜 따라잡기 기준으로 사용되지 않는지
  검증한다.
- 초기 백필과 수동 재집계 옵션을 동시에 활성화하면 실행을 거부하는지 검증한다.
- 기타 지표 원본의 날짜 범위 조회를 지원하는 확정 인덱스가 migration에 존재하는지 검증한다.
- 원본 집계와 전체·상품별 일별 집계 테이블 결과가 같은지 검증한다.
