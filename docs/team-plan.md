# cakeshop 팀 미결정 항목

이 문서는 둘 이상의 도메인 또는 운영 환경에 영향을 주며 **아직 합의되지 않은 질문만** 기록한다.
확정된 정책, 구현 진행률과 개인별 TODO는 적지 않는다. 결정이 끝나면 소유 도메인의 `DOMAIN.md`,
[`conventions.md`](conventions.md), [`README.md`](../README.md) 중 알맞은 정본으로 옮기고 여기서 지운다.

도메인 담당 배정은 [`AGENTS.md`](../AGENTS.md), 사전 협의와 리뷰어 지정 기준은
[`conventions.md`](conventions.md) 12절과 [`pull-request.md`](pull-request.md) 1절이 정본이다.

## 0. 공용 통합 환경

현재 `rds` 프로필과 접속 설정은 있지만 공용 DB를 실제 팀 통합 환경으로 운영할지는 정하지 않았다.
애플리케이션 기동 시 `rds` 프로필의 Flyway는 실행되지 않는다.

| 결정할 질문 | 관련 담당 | 결정 후 옮길 곳 |
|---|---|---|
| 공용 RDS를 도입할지, 도입한다면 언제부터 사용할지 | 전원 | `README.md` |
| migration 적용 담당자, 검토 절차와 적용 순서를 어떻게 정할지 | 전원 | `conventions.md` |
| 적용 이력, 부분 실패 복구와 롤백을 어디에 기록할지 | 전원 | `conventions.md` |
| 무중단 배포가 필요해지는 시점부터 expand-contract를 기본으로 할지 | 전원 | `conventions.md` |
| 공용 DB에 넣을 샘플 데이터의 범위와 개인정보 제거 기준을 어떻게 정할지 | 전원 | `README.md` |
| 여러 애플리케이션 인스턴스가 함께 쓸 운영 업로드 저장소를 무엇으로 할지 | 공통 협의 | `conventions.md` |

## 3. 알림 발생과 발송 범위

`NotificationRequest`, `NotificationType`과 기본 `WEB_ONLY` 동작이 구현되어 있으며, 주문 및 픽업 관련 정책은 아래와 같이 확정되어 연동되었다.

### 확정된 주문/픽업 알림 정책
* **픽업 리마인더 (D-1 / 당일)**:
  * **수신자 및 발송 범위**: 고객 및 활성 관리자 (`WEB_AND_SMS`)
  * **실행 주기**: 서울 시각(`Asia/Seoul`) 기준 오전 9시~저녁 21시 매시 정각 (`OrderPickupNotificationSync`)
  * **멱등 키**: `{NotificationType}:{receiverId}:{orderId}`
* **주문 상태 변경 (제작중/반려/취소/픽업완료)**:
  * **수신자 및 발송 범위**: 고객 및 활성 관리자 (`WEB_AND_SMS` 또는 `WEB_ONLY`)
  * **실행 주기**: 3초 간격 상태 변경 커서 동기화 (`OrderNotificationStatusSync`)
  * **실패 및 복구**: 1차 실패 시 커서 전진을 보류하여 다음 주기 재시도 보장, 탈퇴/비활성 회원은 자동 완결 처리
* **외부 SMS 재시도 정책**:
  * 단건 주문/픽업 이벤트는 최대 2회 시도 제한, 외부 발송 전 `notifications` 행 비관적 잠금(`FOR UPDATE`) 후 `PENDING` 원자적 예약으로 동시성 직렬화
  * 채팅 묶음 알림(`ROOM_`)은 30분 쿨타임 주기마다 지속 발송되도록 2회 상한 예외 적용

| 쿠폰 알림 정책 | 정후·민정 (합의 완료) | 쿠폰 발급 알림은 발급예정/시작일 혼선 방지를 위해 생략하고, 현재 사용 가능한 유효 쿠폰에 대해 만료 3일 전(D-3) 도달 시 `WEB_AND_SMS`로 실시간 웹 토스트 및 문자 알림을 발송한다. |
| 커뮤니티 댓글과 리뷰 답글은 `WEB_ONLY`로 고정할지 | 현규·민정 | 알림 도메인 정책 문서 |
| 업무 트랜잭션 rollback 시 알림도 취소할지, 알림 저장 실패가 원 업무를 실패시킬지 | 각 호출 도메인·민정 | 알림 도메인 정책 문서 |

## 4. 채팅

`chat_rooms.status = OPEN`과 기본 테이블만 존재하고 Service·Mapper의 업무 흐름은 구현되지 않았다.

| 결정할 질문 | 관련 담당 | 결정 후 옮길 곳 |
|---|---|---|
| 채팅방을 회원당 하나로 유지할지 주문별로 분리할지 | 민정·수민·주환 | 채팅 도메인 정책 문서 |
| 채팅방 생성·종료·재개 시점과 `OPEN / CLOSED` 전이를 누가 실행할지 | 민정 | 채팅 도메인 정책 문서 |
| 상담 관리자를 한 계정으로 고정할지, 방마다 배정할지 | 민정·수민 | 채팅 도메인 정책 문서 |
| 주문제작 상세의 문의 링크가 기존 방을 열지 주문 연결을 새로 만들지 | 민정·주환 | 채팅 도메인 정책 문서 |
| 미답변·읽지 않음 배지를 메시지와 읽음 이력에서 어떤 기준으로 계산할지 | 민정 | 채팅 도메인 정책 문서 |

## 5. 회원 상태와 마이페이지

회원 식별은 인증된 `MemberDetails.memberId`를 사용하고, 다른 도메인은 회원 테이블을 직접 읽지 않고
회원 소유 공개 Service 계약을 사용한다. 다음은 여러 기능에 영향을 주는 미결정 정책이다.

| 결정할 질문 | 관련 담당 | 결정 후 옮길 곳 |
|---|---|---|
| `SUSPENDED` 회원에게 허용할 조회와 금지할 쓰기 범위를 어디까지로 할지 | 수민·전원 | 회원 도메인 정책 문서 |
| 정지·탈퇴 시 이미 진행 중인 주문·결제·쿠폰·채팅을 어떻게 처리할지 | 수민·주환·정후·민정 | 각 소유 도메인 정책 문서 |
| `/mypage`의 주문 요약 외에 쿠폰·작성글·알림 요약도 집계할지 | 수민·관련 담당 | 회원 도메인 정책 문서 |
| 주문 외 마이페이지 요약을 추가한다면 각 도메인의 응답 범위와 페이징 책임을 어떻게 나눌지 | 수민·관련 담당 | 회원 도메인 정책 문서 |
