## 1. 도메인 간 연결

담당 도메인 표와 오너십 규칙은 [`AGENTS.md`](../AGENTS.md)「도메인 담당과 협업 경계」가 정본이다. 아래는 **도메인이 서로 무엇을 주고받는지** 합의할 목록이다.

### 1-1. 마이페이지 연동 (회원 ← 각 도메인)

공통 형태: 회원 담당(수민)이 로그인 사용자 식별을 제공하고, **각 도메인 담당이 "회원 ID 기준 조회"를 구현해 화면까지 연결**한다. 회원 담당이 남의 테이블을 직접 조회하지 않는다.

| 연결 | 주고받을 데이터·API | 담당 | 상태 |
|---|---|---|---|
| 회원 → 주문·결제 | 회원 ID 기준 주문·결제 내역 조회 | 수민·주환 | 🟡 형태 합의, 응답 형식 미정 |
| 회원 → 쿠폰 | 회원별 보유·사용 쿠폰 목록 조회 | 수민·정후 | 🟡 쿠폰 상태·만료 정보 형식 미정 |
| 회원 → 커뮤니티·리뷰 | 작성자 기준 게시글·댓글·리뷰 목록 조회 | 수민·현규 | 🟡 노출 항목 미정 |
| 회원 → 채팅·알림 | 회원별 알림 조회·읽음 처리, 채팅방 목록 | 수민·민정 | 🟡 알림 조회 REST API 전환 중 |

- 공통 회원 식별값(무엇을 키로 주고받을지)을 **네 연동이 같은 값으로 통일**한다. ⬜
- 로그인 사용자 식별·세션 처리 방식은 회원 담당이 정리해 공유한다. ⬜

### 1-2. 알림 연동 (각 도메인 → 알림)

인터페이스는 알림 담당(민정)이 확정해 제공한다. **각 도메인은 자기 비즈니스 로직이 끝나는 시점에 호출만 한다.**

- ✅ 제공 메서드: `notificationService.makeNotification(NotificationRequest)`
- ✅ `NotificationRequest` 필드: `receiverId`, `type`, `deliveryScope`(`WEB_ONLY` / `WEB_AND_SMS`), `args`(문구 `%s` 치환 인자 배열), 연관 PK 1개(`orderId` / `postId` / `commentId` / `reviewId` / `userCouponId` 중 해당하는 것)

| 연결 | 알림을 만들 시점 | 담당 | 상태 |
|---|---|---|---|
| 주문·결제 → 알림 | 일반 주문 완료, 주문제작 신청·승인·거절, 픽업 리마인드 | 주환·민정 | 🟡 상태별 `deliveryScope` 미정 |
| 커뮤니티·리뷰 → 알림 | 내 게시글에 댓글, 사장님 리뷰 답글 | 현규·민정 | 🟡 `WEB_ONLY` 기본값 제안 |
| 쿠폰 → 알림 | 쿠폰 발급 시 | 정후·민정 | ⬜ 소멸 알림 도입 여부 미정 |

- `NotificationType` enum 값은 **쿠폰 종류·정책이 확정된 뒤** 채운다(현재 TODO). ⬜
- 대댓글 알림은 커뮤니티 1차 범위 밖이다([`community/DOMAIN.md`](community/DOMAIN.md) 2절). 2차에 넣는다.

### 1-3. 그 밖의 연결

| 연결 | 합의할 기능과 데이터 | 담당 | 상태 |
|---|---|---|---|
| 장바구니 → 상품 | 상품·옵션·현재 가격 확인 | 수민·시은 | ⬜ |
| 주문 → 회원·장바구니·상품 | 주문자, 주문 대상, 재고 확인 | 주환·수민·시은 | ⬜ |
| 결제 → 주문 | 결제 가능 여부와 주문 상태 변경 | 주환 | ⬜ |
| 쿠폰 → 주문·결제 | 사용 가능 쿠폰 조회, 할인 계산, 사용 처리·복구 | 정후·주환 | ⬜ |
| 쿠폰 → 회원 | 발급 대상 판별용 회원 검색·조회(회원 상태, 생년월일, 가입 일시) | 정후·수민 | ⬜ |
| 리뷰 → 주문 | 구매·픽업 완료 확인 | 현규·주환 | ⬜ |
| 리뷰 → 상품 | 상품 상세 하단에 노출할지, 별도 페이지로 둘지 | 현규·시은 | ⬜ |
| 채팅 → 회원·주문 | 상담 대상과 주문 정보 조회, 주문제작 상세의 "1:1 문의하기" → `chatRoomId` 이동 | 민정·주환·수민 | ⬜ |

- `home`: 전용 Mapper 없이 각 도메인 공개 View를 단방향 조합하는 얇은 계층 — 이미 매장 조회에 연결됨. 별도 개발 대상이 아니다. 각 도메인이 완성되면 자기 공개 View를 home에 물려주기만 하면 된다.
- `statistics`: 타 도메인 데이터를 집계하는 후반 작업 도메인이며 담당자는 시은이다.
  구현 기준은 [`statistics/statistics-spec.md`](statistics/statistics-spec.md)를 따른다.
- `community`: 1차 범위에서 이미지 첨부·알림 수신·검색을 제외했다([`community/DOMAIN.md`](community/DOMAIN.md) 2절). 회원과의 연결(작성자 표시, 탈퇴 회원 처리, 관리자 차단자 기록)은 같은 문서 5·6·8절에서 이미 정했다.

> ⚠️ **결제 흐름 3인 공유**: `cart`(수민) → `order`·`payment`(주환) ← `coupon`(정후)이 `OrderStatus` 상태 전이와 checkout 흐름을 공유한다. 착수 초반에 셋이 인터페이스(장바구니→주문 생성 · 쿠폰 적용 시점 · 결제 상태 콜백)를 먼저 맞추고 각자 브랜치를 판다. 충돌·재작업이 가장 많이 나는 지점이다.

### 원칙

- FK 또는 공통 인터페이스 변경은 관련 담당자 모두가 검토한다.
- 다른 도메인은 Mapper가 아니라 합의된 Service 인터페이스를 통해 사용한다.
- 여러 도메인이 참여하는 작업은 트랜잭션을 소유할 도메인을 먼저 정한다.

## 2. 핵심 비즈니스 규칙

**이 문서에서 가장 중요한 절이다.** 여기가 비어 있으면 담당자마다 다르게 구현하고 통합 시점에 드러난다. 상태값의 *표기와 저장 방식*은 [`status-design.md`](status-design.md)가 정본이고, 아래는 *언제 누가 바꾸는가*다.

### 2-1. 상품·주문 (확정)

| 결정할 사항 | 최종 결정 | 관련 담당자 |
|---|---|---|
| 상품 유형별 준비 기간 | `GENERAL`은 미리 제작된 재고 상품으로 보고 `preparation_days`를 0일로 고정하며 당일부터 픽업할 수 있다. `CUSTOM`은 관리자가 1일 이상으로 설정하고, 가장 빠른 픽업일은 관리자 승인일에 준비 기간을 더해 계산한다. 매장 영업일·영업시간 충족 여부는 별도로 확인한다. | 시은·주환 |
| 주문 유형별 취소 가능 조건 | `GENERAL` 주문은 픽업 시각 전까지 취소할 수 있다. `CUSTOM` 주문은 관리자 승인 전까지만 취소할 수 있으며, 승인 시 취소를 차단하고 제작을 시작한다. 취소 가능 여부는 상품의 일수 설정이 아니라 주문 유형·상태·픽업 시각으로 판단한다. `order_items.cancellation_limit_days`의 유지·사용 여부는 주문 도메인에서 결정한다. | 시은·주환 |
| 당일 픽업 상품 분류 | 별도의 당일 픽업 상품군·검색 필터·메뉴·배지를 운영하지 않는다. `GENERAL` 상품은 판매 중이고 주문 수량만큼 재고가 있으면 준비 기간 0일의 결과로 당일 픽업할 수 있다. | 시은·주환 |
| 주문 시 상품 준비 기간 스냅샷 | 주문 생성 시 상품의 `preparation_days`를 `order_items.preparation_days`에 저장한다. 이후 상품의 준비 기간이 변경되어도 기존 주문의 값과 픽업 가능일은 변경하지 않는다. | 시은·주환 |
| 재고 차감 및 복구 시점 | `GENERAL` 상품은 결제 성공 시 요청 수량만큼 재고를 원자적으로 조건부 차감한다. 재고가 부족하면 주문을 결제 완료로 확정하지 않고, 이미 승인된 외부 결제는 취소·환불한다. 재고 차감 후 주문·결제가 취소되면 차감한 수량을 한 번만 복구하며, 결제 전 만료는 복구하지 않는다. `stock_quantity`가 `NULL`인 무제한 재고와 `CUSTOM` 상품은 차감·복구 대상에서 제외한다. 주문·결제 도메인이 전체 흐름과 중복 실행 방지를 소유하고, 상품 도메인은 공개 Service를 통해 원자적인 차감·복구 연산을 제공한다. | 시은·주환 |

### 2-2. 쿠폰 발급 정책

관리자 쿠폰 CRUD는 구현됐고, **발급 대상과 발급 시점**이 남았다(정후).

| 결정할 사항 | 안 | 담당 |
|---|---|---|
| 쿠폰 발급 시점 | 🟡 ①등록 시점에 전원 발급하고 사용 가능·불가 기한으로 판단 / ②등록과 별개로 스케줄러가 조건 달성 시 발급 / ③둘 다 지원 | 정후 |
| 회원별 유효기간 개별화 | ⬜ 현재 구조는 등록 시 정한 시작·종료 일시를 **모든 발급 회원에게 동일하게** 부여한다. 생일 쿠폰처럼 회원마다 기한이 달라야 하는 종류가 있으면 `member_coupons`에 기한 컬럼이 필요하다 | 정후 |
| 발급 대상 구분과 자동·수동 발급 | ⬜ (전체 / 신규 가입 / 생일 / 관리자 지정) | 정후·수민 |
| 중복 발급 방지 기준 | ⬜ | 정후 |
| 쿠폰 사용 및 복구 시점 | ⬜ 주문·결제의 취소·실패 흐름과 함께 정한다 | 정후·주환 |
