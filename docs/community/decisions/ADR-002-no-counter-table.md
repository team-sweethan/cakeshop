# ADR-002. 일일 카운터 테이블을 두지 않는다 (D2)

- 상태: **확정** (2026-08-05, 조각 7b) · **재확인** (2026-08-19, 조각 20)
- 정본 규칙: `../specs/community-popular.md` E3
- 관련 위험: `../PLAN.md` R25
- 결정 번호의 자리: `../PLAN.md` 조각 7 결정 표

원안은 `post_daily_metrics(metric_date, post_id, view_count, like_count, comment_count)`를 두고 조회·좋아요·댓글마다 실시간으로 올리는 구조였다. 두지 않기로 한 근거는 셋이다.

1. **요청 경로에 잠금이 하나 더 붙는다.** 조회수와 좋아요는 이미 `posts` 행 잠금 순서로 교착을 세 번 맞은 경로다(H13·H15·H17). 같은 트랜잭션에 `(metric_date, post_id)` 행 잠금이 추가되면 **잠금 순서가 두 벌**이 되고, 조각 6과 4에서 겪은 모양이 그대로 재현될 자리가 생긴다. 원안 12절이 이것을 Hot Row(성능)로 다루지만 실제 위험은 성능이 아니라 교착이다.
2. **좋아요 취소와 댓글 삭제가 저절로 맞는다.** `deleteLike`는 실제로 행을 지우므로(`CommunityMapper.xml`) 원본을 세면 취소가 그대로 반영된다. 증가만 하는 카운터였다면 취소–재좋아요 반복으로 점수를 무한히 올릴 수 있었다. 댓글도 `status`로 그냥 빠진다 — 원안 4.3이 "삭제된 댓글은 배치 재계산 시 제외"라고 적었지만, 증가 카운터는 재계산할 근거를 갖고 있지 않다.
3. **아끼는 값이 하룻밤에 한 번이다.** 카운터는 배치 한 번을 위해 요청 수만큼의 쓰기를 미리 하는 거래다. 배치는 인덱스로 창을 잘라 읽으면 되고, 그 인덱스는 어차피 만든다.

**학습 목표는 깎이지 않는다** — 스케줄러·크론·멱등성·스냅샷·트랜잭션 경계는 전부 그대로다. 카운터 테이블은 배치가 아니라 실시간 집계 쪽 주제다.

## 다시 제안됐고, 유지했다 (2026-08-19, 조각 20)

`post_daily_metrics(metric_date, post_id, view_count, like_count, commenter_count, updated_at)` + 활동 직후 실시간 누적 + 00:05 원본 대조·보정이 다시 제안됐다. **원안과 다른 점은 보정 단계가 붙은 것이고, 그것이 위 근거 2를 실제로 푼다** — 원본과 대조해 덮어쓰면 증가 카운터가 재계산할 근거를 갖는다. 그래도 유지한 이유는 둘이다.

1. **근거 1은 그대로다.** 보정을 붙여도 `(metric_date, post_id)` 행 잠금은 조회·좋아요 요청 경로에 그대로 들어간다. 결정적이라고 적은 것이 이것이고, 반박된 적이 없다.
2. **근거 3은 오히려 강해졌다.** 같은 조각이 집계 창을 7일에서 하루로 좁혔다. 배치가 훑는 폭이 7분의 1이 되고 `(created_at, post_id)` 커버링 인덱스는 이미 있으므로, 카운터가 아끼려던 값이 더 줄었다. **그리고 보정을 하려면 원본 집계 SQL을 그대로 들고 있어야 하므로 배치 코드는 줄지 않는다** — 실시간 코드가 순증할 뿐이다.

제안이 든 요구 다섯 중 넷은 지금 배치가 이미 하고 있었다: 00:05 전날 확정(D3), "그날 그 글에 처음 댓글을 남긴 사람만"(창이 하루가 되면 `GROUP BY post_id, member_id`가 그대로 그 뜻이다), 댓글 삭제·재작성 정합(`status = 'PUBLISHED'`), 점수의 원천 중복 없음.

**되돌아올 계기는 성능이 아니라 요구의 변화다** — 화면이 확정 스냅샷이 아니라 "지금 뜨는 글"을 요구하거나(`../PLAN.md` R24·R29와 공유), R25의 트리거가 도달해 원본을 보관 기간으로 정리하게 될 때다. 후자에서는 집계할 원본이 사라지므로 미리 접어 두는 쪽이 맞다. **성능을 이유로 다시 제안되면 이 절을 먼저 읽는다.**
