# Community 도메인 규칙 (1차 MVP)

> 이 문서는 Community 도메인의 **결정된 규칙의 정본**이다.
> 진행 상태와 조각 순서는 `docs/community/PLAN.md`를 본다.
> 프로젝트 전체 규칙은 `AGENTS.md`가 상위 정본이며, 충돌 시 `AGENTS.md`가 우선한다.

## 1. 한 문장 정의

Cakeshop 커뮤니티는 고객이 케이크 관련 질문과 후기를 공유하는 공간이다.

## 2. MVP 범위

**포함**: 게시글 목록·상세, 게시글 CRUD, 댓글(1단계) 작성·삭제, 좋아요, 신고, 관리자 차단, 페이지 번호 페이징, **조회수 정렬 옵션·인기글**

**제외**: 이미지 첨부(`post_images` 미사용), 알림, 실시간 댓글, 대댓글, 댓글 수정, 검색, 무한 스크롤, 카테고리 관리 화면

> **범위 변경 (2026-08-03).** `인기글·정렬 옵션`은 원래 제외였다. 조회수를 정렬·순위에 쓰기로 하면서 포함으로 옮겼다.
>
> 이 변경은 **6.2를 함께 뒤집어야만 성립한다.** 6.2가 조회수 중복 방지를 뺀 근거가 바로 "조회수는 정렬·순위에 쓰이지 않는다"였다. 그 전제를 없애 놓고 중복 방지를 그대로 두면 **새로고침만으로 순위가 오른다.** 순서가 있다 — 중복 방지가 먼저고 순위 화면이 나중이다(`PLAN.md` 조각 6 → 7).

## 3. 기존 자산

스키마는 `V0__initial_schema.sql`에 **이미 전부 존재**한다. 공유된 migration이므로 수정하지 않고, 필요하면 새 versioned migration을 추가한다(`gradlew newMigration -Pdesc=<snake_case>`).

- `post_categories`, `posts`, `comments`, `post_likes`, `post_images`, `post_reports`
- `post_likes(post_id, member_id)` UNIQUE 존재
- `post_reports(post_id, reporter_id)` UNIQUE 존재
- `posts`에 `status`, `blocked_at`, `blocked_reason`, `blocked_by`, `view_count`, `like_count` 존재
- `posts`에 `comment_count` 컬럼은 **없다**
- **`post_views` 테이블은 없다.** 조회수 중복 방지(6.2)에 필요하므로 새 migration으로 만든다 — V0에 기댈 수 있는 유일한 예외다

코드 뼈대: `domain/community/`에 controller 3개(뷰 이름만 반환), 빈 `CommunityService`, 빈 `CommunityMapper`, 빈 entity 3개, `CommunityErrorCode`. 테스트 0개.

템플릿: `templates/customer/community/{list,detail,form}.html`, `templates/admin/community/{list,detail}.html`

기존 공용 유틸: `global/common/paging/PageRequest`(1-based, offset, 기본 20, 최대 100), `PageResult`(totalElements, totalPages)

## 4. 상태 모델

### 4.1 노출 기준

**`posts.status`가 게시글 노출 여부의 유일한 기준이다.** `blocked_at`/`blocked_reason`/`blocked_by`는 부가 기록일 뿐 노출 판단에 쓰지 않는다.

- 이유: 조건이 두 개면 새 쿼리를 추가할 때 하나를 빠뜨려 차단된 글이 노출된다. `WHERE status = 'PUBLISHED'` 하나로 끝내면 빠뜨릴 것이 없다.
- `PostStatus { PUBLISHED, DELETED, BLOCKED }` enum으로 정의하고, `MemberStatus.canTransitionTo` 선례를 따라 전이 규칙을 enum에 둔다.
- 새 migration으로 `CHECK (status IN ('PUBLISHED','DELETED','BLOCKED'))`를 추가한다 (선례: `V20260729_123306__add_member_status_constraint.sql`).

### 4.2 게시글 전이 규칙

| 전이 | 허용 | 주체 |
|---|---|---|
| `PUBLISHED → DELETED` | 허용 | 작성자 |
| `PUBLISHED → BLOCKED` | 허용 | 관리자 |
| `BLOCKED → PUBLISHED` | 허용 | 관리자 (차단 해제) |
| `BLOCKED → DELETED` | **금지** | — |
| `DELETED → PUBLISHED` | **금지** | — |
| `DELETED → BLOCKED` | **금지** | — |

- `BLOCKED → DELETED` 금지: 차단된 글은 신고·조치의 증거다. 작성자가 지워서 없앨 수 없어야 한다. 결과적으로 **차단된 글에 대해 작성자가 할 수 있는 일은 없다**(수정·삭제 모두 불가).
- `DELETED`는 종착 상태다. 복구 기능(휴지통)은 MVP 밖이다.
- 차단 해제 시 `blocked_at`/`blocked_reason`/`blocked_by`를 **NULL로 되돌리지 않는다.** "과거에 차단된 적이 있다"는 관리자에게 유용한 이력이고, 노출은 `status`가 결정하므로 값이 남아도 영향이 없다.

### 4.3 상세 접근 규칙 (`GET /community/{id}`)

| 접근자 | `PUBLISHED` | `DELETED` | `BLOCKED` |
|---|---|---|---|
| 비로그인 / 다른 회원 | 정상 | **404** | **404** |
| 작성자 본인 | 정상 | **404** | **본문 + 차단 사유 표시** |
| 관리자 (고객 경로) | 정상 | 404 | 404 |
| 관리자 (`/admin/community/{id}`) | 정상 | 정상 | 정상 |

- 남에게 403이 아니라 404를 주는 이유: 403은 "그 자리에 글이 존재한다"는 사실을 흘린다.
- 작성자에게 `BLOCKED` 본문과 사유를 보여주는 이유: 4.2에 따라 작성자는 차단된 글에 아무 조치도 할 수 없다. 404까지 주면 글이 왜 사라졌는지 영영 알 수 없다. 차단이 처벌이 아니라 교정으로 작동하려면 사유가 전달되어야 한다.

### 4.4 댓글 상태

- 댓글 삭제도 soft delete (`comments.status = 'DELETED'`).
- **삭제된 댓글은 목록에서 지우지 않고 "삭제된 댓글입니다" 자리 표시로 남긴다.** 1차에는 자식 댓글이 없어 기능적으로 불필요하지만, 2차 대댓글 도입 시 부모 댓글이 사라지면 자식이 고아가 되므로 그때 정책을 뒤집는 비용(테스트·화면 재작업)을 피하기 위해 처음부터 이렇게 간다.
- **삭제된 댓글은 댓글 개수 집계에서 제외한다** (`WHERE status = 'PUBLISHED'`).

### 4.5 게시글 삭제와 자식 데이터

게시글을 soft delete해도 `comments`, `post_likes`, `post_reports` 행은 **그대로 둔다.**

- 게시글이 `DELETED`면 상세가 404이므로 댓글이 노출될 경로가 없다. 자식까지 일괄 `DELETED`로 바꾸는 것은 중복이고, "원래 삭제돼 있던 댓글"과 "게시글 때문에 삭제된 댓글"을 구분할 수 없게 만든다.
- **대신 댓글·좋아요·신고 Service는 대상 게시글이 `PUBLISHED`인지 반드시 검증해야 한다.** 이 검증이 없으면 삭제된 글에 API로 직접 댓글을 달 수 있다. 테스트로 고정할 항목이다.

**이 검증은 불변식이 아니라 권한 판단이다.** 확인하는 SELECT와 뒤따르는 쓰기 사이에 게시글이 차단·삭제되면 그 쓰기는 그대로 통과한다. **부모 행을 잠가서 막지 않는다** — 위 첫 항목이 말하듯 "비노출 글에는 자식 행이 없다"는 불변식 자체가 없으므로 지킬 것이 없고, 댓글 쓰기마다 게시글 행을 잠그면 6.2의 조회수 UPDATE와 같은 행을 두고 경합한다. 남는 창과 되돌아올 계기는 `PLAN.md` R14에 있다.

## 5. 권한

`SecurityConfig`에 이미 반영되어 있다.

- `GET /community`, `GET /community/{id}` → `permitAll` (비로그인 조회 허용)
- 그 외 커뮤니티 경로 → `anyRequest().authenticated()`
- `/admin/**` → `hasRole("ADMIN")`

**커뮤니티에서 회원 상태(`ACTIVE`/`SUSPENDED`/`WITHDRAWN`)를 재검증하지 않는다.**

- 근거: `MemberAuthenticationService`가 `loginAllowed = (status == ACTIVE)`로 만들고, `MemberDetailsService`가 false면 인증을 거부한다. 관리자가 정지시키면 `MemberAdminController`가 `expireSessionsByEmail`로 기존 세션도 즉시 만료시킨다. 즉 커뮤니티 코드에 도달하는 인증 사용자는 정의상 `ACTIVE`다.
- **이것은 member 도메인 구현에 대한 의존이지만, 그 전제는 테스트로 고정되어 있다** — `MemberAuthenticationServiceTests`(`SUSPENDED`/`WITHDRAWN`/status 누락 → `loginAllowed == false`), `MemberDetailsServiceTests`(`loginAllowed == false` → 인증 거부), `MemberAdminControllerTests`(정지 시 기존 세션 만료). 커뮤니티에 중복 검증을 넣지 않는다.

소유권 검증은 요청으로 전달된 회원 ID를 믿지 말고 **인증 사용자 기준으로 Service에서** 한다(`AGENTS.md`).

## 6. 기능별 규칙

### 6.1 목록 (`GET /community`)

- 오프셋 페이지 번호 페이징. `PageRequest`/`PageResult` 재사용.
- 페이지 크기 **20 고정** (사용자가 바꿀 수 없음).
- 정렬은 `?sort=` 선택. 없으면 최신순이다.

| `sort` | 정렬 | 비고 |
|---|---|---|
| (없음) / `latest` | `created_at DESC, id DESC` | 기본값 |
| `views` | `view_count DESC, id DESC` | 조회수 중복 방지(6.2) 이후에만 노출한다 |

- **`id` tiebreaker는 어느 정렬에도 붙는다.** 없으면 동일 시각 글이, 조회수 정렬에서는 **동일 조회수 글이** 두 페이지에 중복되거나 누락된다. 조회수는 0이 흔해서 최신순보다 동점이 훨씬 잦다.
- **tiebreaker가 보증하는 것은 "한 쿼리 안에서 순서가 정해진다"까지다.** 조회수순은 그 너머를 보증하지 못한다 — `view_count`는 상세를 열 때마다 바뀌므로, 1쪽을 읽고 2쪽을 누르는 사이에 아래쪽 글의 조회수가 올라 앞으로 이동하면 `OFFSET`이 밀려 **이미 본 글이 다시 나오거나 다른 글이 건너뛰어진다.** 최신순에는 없는 문제다(`created_at`은 변하지 않는다). 정렬 키가 변하는 값이면 오프셋 페이징으로는 막을 수 없고, 커서 페이징이나 순위 스냅샷이 필요하다. 1차에서는 수용하며 근거와 계기는 `PLAN.md` R28에 있다.
- **허용값은 `<choose>`로 매핑하고 `${}`로 이어 붙이지 않는다**(`AGENTS.md` SQL 안전성). 정렬은 사용자가 주소로 넣는 값이며, 그대로 SQL에 붙이면 주입 경로가 된다. 모르는 값은 오류가 아니라 **기본값으로 떨어뜨린다** — 목록은 비로그인도 여는 공개 화면이라 주소가 망가졌다고 오류 페이지를 주지 않는다(카테고리·페이지 파라미터와 같은 처리다).
- **좋아요 기준 정렬(`sort=likes`)은 넣지 않는다 (결정, 조각 7a).** 분기 하나를 더 여는 값이 크지 않다 — 분기마다 `id` tiebreaker·인덱스·형태 검사가 함께 늘어나는데, **좋아요로 줄을 세워 보고 싶은 것은 인기글이 이미 대신한다**(6.9). 인기글 점수에서 가장 큰 계수를 갖는 것이 좋아요다. 되돌아올 계기: 인기글이 7일 창이라 그 밖의 "역대 좋아요 많은 글"을 보고 싶다는 요구가 실제로 나오면 그때 분기를 연다.
- 목록에는 **"내가 좋아요 눌렀는지"를 넣지 않는다.** 상세에만 있다(6.5).
- `?categoryId=` 선택 필터. 없으면 전체.
- 총 개수 `COUNT(*)` 조회 (PageResult가 요구).
- 표시 항목: 제목, 작성자명, 카테고리명, 작성일, 조회수, 좋아요 수, 댓글 수. **작성자명은 SQL이 아니라 조립에서 채운다**(8절).
- **본문 미리보기 없음.** `content`는 TEXT이며 목록에서 SELECT하지 않는다.

**댓글 수는 반드시 스칼라 서브쿼리로 집계한다:**

```sql
SELECT p.id, p.member_id, p.title, ...,
       (SELECT COUNT(*) FROM comments c
         WHERE c.post_id = p.id AND c.status = 'PUBLISHED') AS comment_count
FROM posts p
JOIN post_categories pc ON pc.id = p.category_id
WHERE p.status = 'PUBLISHED'
ORDER BY p.created_at DESC, p.id DESC
LIMIT #{size} OFFSET #{offset}
```

**`members`를 JOIN하지 않는다.** 작성자는 `member_id`만 들고 나와 Service가 회원 계약으로 조립한다(8절, 조각 10b). **매퍼 XML에서** JOIN을 되살리면 `CommunityDomainBoundaryTests`가 문다. 다만 **이 예제 자체는 어느 검사도 읽지 않는다** — 매퍼를 그대로 둔 채 여기만 되돌려 놓으면 조용히 통과하고, 그게 이 문단이 한 번 겪은 드리프트다(`PLAN.md` R32).

**`LEFT JOIN comments ... GROUP BY p.id`로 바꾸지 말 것.** `LIMIT`은 `GROUP BY` 이후에 적용되므로 전체 게시글 × 전체 댓글을 조인하고 전부 집계한 뒤 20개를 잘라낸다. 결과는 동일하지만 전체 스캔이 된다. 스칼라 서브쿼리는 최종 결과 20행에 대해서만 평가되며 `fk_comments_post` 인덱스를 탄다.

### 6.2 상세 (`GET /community/{id}`)

> **정책 변경 (2026-08-03).** 조회수는 더 이상 참고용 표시가 아니라 **정렬·순위의 근거 데이터**다(2절, 6.1). 아래는 그에 맞춰 다시 쓴 규칙이다. 이전 규칙("무조건 +1, 중복 방지 없음")은 폐기했다 — 그 규칙의 근거 문장이 정확히 "정렬·순위에 쓰이지 않는다"였기 때문에, 용도가 바뀌면 규칙도 함께 무너진다.
>
> **구현 순서에 제약이 있다.** 중복 방지(`PLAN.md` 조각 6)가 들어가기 전에는 정렬 옵션·인기글을 화면에 내지 않는다. 먼저 내면 새로고침만으로 순위가 오르는 화면을 공개하는 것이 된다.

- 조회수는 **같은 사람이 같은 글을 10분 안에 여러 번 열어도 한 번만** 오른다. 중복 방지는 이력 테이블 `post_views`로 한다.
- 근거: 조회수가 순위를 정한다면 **F5 한 번이 순위 조작**이 된다. 새 테이블의 쓰기 부하는 그 대가로 받아들인다.

**`post_views` (새 migration으로 추가)**

| 컬럼 | 내용 |
|---|---|
| `post_id` | 대상 게시글. `posts(id)` FK |
| `viewer_key` | 회원이면 `M:{memberId}`, 비로그인이면 `S:{sessionId}` |
| `created_at` | 조회한 **시각**(DATETIME(6)). 시간 창의 기준이다 |

- `INDEX (post_id, viewer_key, created_at)`을 건다. **UNIQUE는 걸지 않는다** — 아래 "시간 창" 참조.
- 흐름은 **조건부 `UPDATE` → 갱신된 행이 1일 때만 이력 `INSERT`** 다. 0이면 창 안에서 이미 센 조회이므로 아무것도 하지 않는다.

**시간 창은 굴러가는 10분이다** (2026-08-04 변경, 원래는 날짜 칸).

- `NOT EXISTS (... AND pv.created_at > NOW(6) - INTERVAL 10 MINUTE)`로 판단한다. 기준 시각은 애플리케이션이 아니라 **DB 시계**다 — 서버가 여러 대여도 "최근 10분"의 뜻이 갈리지 않아야 한다.
- **조회 시각을 담을 컬럼을 따로 두지 않고 `created_at`을 쓴다.** `post_views`는 append-only 조회 이력이라 행이 생긴 시각이 곧 조회한 시각이다. 같은 값을 담는 컬럼이 둘이면 언젠가 어긋난다.
- **`UNIQUE`를 버렸다.** 굴러가는 창은 제약으로 표현할 수 없다. 원래 날짜 칸을 고른 이유가 바로 이것이었는데, 구현을 하고 보니 **직렬화를 실제로 하고 있던 것은 제약이 아니라 조건부 `UPDATE`가 게시글 행에 먼저 거는 배타 잠금**이었다. 창 판단이 그 잠금을 쥔 채 `UPDATE` 안에서 평가되므로 동시 요청 두 개가 함께 통과할 수 없다 — "굴러가는 창은 결국 코드가 판단하게 된다"는 우려는 여기에 해당하지 않는다.
- **대신 잃은 것이 있다.** 제약은 그 잠금 순서가 깨졌을 때 울리는 경보였고, 이제 깨져도 DB는 아무 말도 하지 않는다. 그 자리를 `CommunityViewCountConcurrencyTests`가 맡는다(`PLAN.md` H14). 순서를 되돌리면 교착이 나므로 동시성 테스트가 더 직접적으로 잡는다.
- **`UNIQUE`를 다시 걸면 기능이 죽는다.** 같은 조회자가 같은 글을 두 번째로 열어보는 순간 `recordView`가 예외를 던져 상세가 500이 된다. 시드 직후 로컬 확인에서는 나오지 않고 며칠 뒤에 나온다.
- **상한은 느슨해졌다. 이것을 알고 쓴다.** 뷰어 하나가 하루에 올릴 수 있는 조회수가 1에서 144가 된다. 그럼에도 실질 방어력 차이가 작은 것은 아래 "비로그인 중복 방지는 약하다"가 이미 말하는 대로 **작정한 조작에는 어느 창도 무력하기 때문**이다. 두 설계가 실제로 막는 것은 사람의 반복 조회이고 그건 10분으로도 막힌다. 바꾼 이유도 방어가 아니라 **표시**다 — 하루 단위로만 움직이는 숫자는 글을 다시 연 사람에게 멈춘 값으로 보인다.
- 대가는 **창이 열린 직후의 재조회가 다시 세어지는 것**이고, 이건 감수한다. 날짜 칸의 "자정 직후"가 하루 144번으로 늘어난 형태다.

**댓글 `더 보기`는 조회로 세지 않는다. 창이 아니라 경로가 가른다** (2026-08-04, PR #98 Codex 리뷰).

- `?comments=`가 붙은 상세 요청은 조회수를 올리지 않는 `getVisiblePost`로 간다. 댓글을 더 펼치는 것은 **이미 보고 있는 글 안에서의 이동**이지 새로운 조회가 아니다.
- **창에 맡기면 막히지 않는다.** 상세를 10분 넘게 읽다가 `더 보기`를 누르면 창이 이미 닫혀 그대로 +1이고, 댓글이 많은 글일수록 자기 탐색으로 순위 신호가 부푼다 — 6.4가 없애려던 자가 인플레가 형태만 바꿔 돌아온다. 날짜 칸일 때는 하루 한 번으로 눌려 있어 드러나지 않았다.
- 대가는 `?comments=`가 붙은 주소로 **처음** 들어온 조회를 세지 않는 것이다. 공유·북마크로만 생기고, **조회수가 부푸는 쪽이 아니라 덜 세는 쪽으로 틀린다.**
- 검증 실패로 상세를 다시 그릴 때 같은 메서드를 쓰는 것과 같은 자리다(조각 3). 경로가 둘로 갈려 있는 것이 그때부터 이 규칙의 재료였다.

**순서가 규칙이다. 이력을 먼저 넣지 않는다.**

자연스러워 보이는 순서는 "이력을 먼저 넣고, 새로 들어갔으면 숫자를 올린다"인데 **그렇게 하면 교착에 빠진다.** `post_views` INSERT는 FK 확인 때문에 부모인 `posts` 행에 공유 잠금(S)을 걸고, 이어지는 조회수 UPDATE는 같은 행의 배타 잠금(X)을 요구한다. 같은 글을 동시에 연 요청 둘이 서로 S를 쥔 채 상대의 X를 기다리면 그대로 멈춘다.

- 그래서 조회수 UPDATE가 **먼저** X를 잡고, 잠금을 쥔 상태에서 `NOT EXISTS`로 창 안의 조회인지까지 판단한다. 같은 글의 요청들은 이 문장에서 줄을 서므로 앞 요청이 남긴 이력을 반드시 본다. **중복을 막고 있는 것이 이 잠금이다** — 위에 적었듯 제약이 아니다.
- 이력 INSERT는 이미 X를 쥔 뒤라 잠금이 뒤집히지 않는다. **중복을 삼키지 않는다**(`INSERT IGNORE`·`ON DUPLICATE KEY`를 쓰지 않는다). 지금은 삼킬 UNIQUE 자체가 없지만, 붙여 두면 나중에 제약이 다시 생겼을 때 숫자만 오르고 이력이 없는 상태를 조용히 만든다.
- 인기 있는 글일수록 동시 조회가 많아 더 잘 터지는데, **동시 요청이 없으면 결과가 똑같아서 단일 스레드 테스트로는 드러나지 않는다.**

**갱신 행 수로 "이미 봤는지"를 판단할 때 주의할 것.** MariaDB JDBC 드라이버는 `CLIENT_FOUND_ROWS`를 켜서 갱신 행 수가 '바뀐 행'이 아니라 **'찾은 행'** 을 뜻한다. 그래서 "값이 그대로면 0"에 기대는 방식(`ON DUPLICATE KEY UPDATE` 등)은 여기서 언제나 1을 돌려주고, **제약은 멀쩡히 도는데 숫자만 부푼다.** 조건부 UPDATE는 조건이 안 맞으면 아예 행을 찾지 못하므로 0이 정확하다.
- ~~**시간 창을 굴러가는 N시간이 아니라 날짜 칸으로 잡은 이유**: `UNIQUE`로 강제할 수 있는 것은 칸뿐이다.~~ — **2026-08-04에 뒤집혔다.** 위 "시간 창" 절이 정본이다. 이 논거는 직렬화를 제약이 한다고 본 것이었는데, 실제로 하고 있던 것은 조건부 `UPDATE`의 배타 잠금이었다.

**`posts.view_count`는 `post_views`에서 파생된 캐시다.** 정본은 이력 테이블이다.

- 갱신은 **증분**이다(`view_count = view_count + 1`). 좋아요(6.5)가 매번 재계산하는 것과 다르며, 다른 이유는 **행 수의 규모**다. `post_likes`는 글당 좋아요 수만큼이지만 `post_views`는 그 수십 배로 쌓이고, 조회마다 `COUNT(*)`를 도는 것은 조회가 늘수록 비싸진다. 6.5의 "여러 경로가 건드린다" 논거도 여기엔 약하다 — `view_count`를 건드리는 경로는 상세 조회 하나뿐이다.
- 대신 **두 값의 일치를 하네스로 고정**하고, 어긋나면 `post_views`에서 재계산해 복구한다. 증분을 택하면서 "틀어져도 아무도 모른다"까지 받아들이지는 않는다.
- `INSERT`와 `view_count` 갱신은 **하나의 트랜잭션**이다.

- Service 메서드 하나 안에서 `조건부 UPDATE view_count` → (1행이면) `조회 이력 INSERT` → `SELECT 상세` 순으로 처리하고 통째로 `@Transactional`을 건다.
- **노출되지 않는 글(`DELETED`/`BLOCKED`)의 조회수는 올리지 않는다.** UPDATE에 `status = 'PUBLISHED'` 조건을 두어 처리한다. 상세가 404인 글의 조회수를 올릴 이유가 없고, 조건을 UPDATE 쪽에 두면 노출 판단 때문에 SELECT를 두 번 하지 않아도 된다. 차단된 글을 작성자가 열어보는 경우도 마찬가지로 올리지 않는다 — 조회수는 공개 지표인데 그 글은 아무에게도 노출되지 않는다.
- **조회수 UPDATE는 `updated_at`을 명시적으로 보존한다**(`SET view_count = view_count + 1, updated_at = updated_at`). `posts.updated_at`은 `ON UPDATE CURRENT_TIMESTAMP(6)`이므로 그냥 두면 조회만으로 값이 바뀌고, 6.3의 "수정됨" 표시가 켜진다. 화면에는 조용히 "(수정됨)"이 붙을 뿐이라 원인을 찾기 어렵다.

**비로그인 중복 방지는 약하다. 이것을 알고 쓴다.**

비로그인 키는 세션 id다. 쿠키를 지우거나, 애초에 쿠키를 받지 않는 클라이언트로 요청하면 **매 요청이 새 조회자**가 된다. 스크립트 한 줄로 뚫린다.

- 그래서 이 방식이 실제로 막는 것은 **사람의 반복 조회**(새로고침, 뒤로가기, 댓글 `더 보기`)이지 작정한 조작이 아니다. 이 구분을 문서에 적어 두는 이유는, 막았다고 믿는 만큼 위험해지기 때문이다(`PLAN.md` R12).
- 조작까지 막으려면 **회원 조회만 집계**하거나(계정 생성이 비용이 된다) 순위 기준을 **좋아요**로 바꾸는 것이 세트다. `post_likes`는 `UNIQUE(post_id, member_id)`라 구조적으로 중복이 없다. 지금은 둘 다 하지 않기로 했고, 되돌아올 계기를 R12에 적었다.
- `viewer_key`를 IP로 잡지 않는다. 공유 NAT에서 남의 조회가 내 조회로 합쳐지고, **개인정보를 새로 저장하게 된다**(`AGENTS.md` 보안). 세션 id는 우리가 발급한 값이라 그 문제가 없다.

### 6.3 작성·수정·삭제

- 수정 가능 항목: **제목, 본문, 카테고리** 전부.
- 수정 이력 테이블 없음. `updated_at != created_at`이면 화면에 "수정됨" 표시.
- 수정 가능 시간 제한 없음.
- 삭제는 `status = 'DELETED'` 전이 (4.2).

### 6.4 댓글

- 1단계만. **댓글 SQL에 `parent_comment_id`를 사용하지 않는다.** 컬럼은 V0에 존재하지만 2차 대댓글 전까지 값을 넣지 않는다. `CommunityCommentScopeTests`가 모든 커뮤니티 Mapper SQL을 검사하고, `CommunitySeedTests`가 시드를 검사한다.
- 작성·삭제만. **수정 없음.** 이것도 같은 테스트가 고정한다(본문을 바꾸는 UPDATE가 없는지).
- 삭제는 soft delete + 자리 표시 (4.4). 지울 수 있는 사람은 **댓글 작성자 본인뿐**이다. 게시글 작성자에게도, 관리자에게도 댓글 삭제 권한은 없다 — 관리자의 조치는 게시글 차단뿐이다(6.7).
- 댓글 작성·삭제 모두 대상 게시글이 `PUBLISHED`여야 한다 (4.5). 차단된 글을 보고 있는 작성자에게도 댓글은 열리지 않는다.

**경로**: `POST /community/{postId}/comments`(작성), `POST /community/{postId}/comments/{commentId}/delete`(삭제). 게시글 삭제와 같은 폼 POST다. GET으로 지워지면 링크 미리보기나 크롤러가 댓글을 없앨 수 있다.

**정렬과 분량 — "더 보기"**:

- 화면에는 **오래된 순**으로 나가고, 자를 때는 **최신 N건**을 남긴다. 기본 20건이고 `?comments=N`으로 20씩 늘린다.
- 쪽 번호로 나누지 않는 이유: 상세 화면에 게시글 목록과 댓글, 두 종류의 쪽 번호가 생기면 "지금 몇 쪽인가"가 두 개가 되고, 댓글을 쓰고 나서 어느 쪽으로 돌아갈지도 정해야 한다.
- 앞에서 자르지 않는 이유: 댓글이 20건을 넘는 글에서 **방금 쓴 댓글이 화면 밖에 남는다.** 사용자에게는 등록이 안 된 것과 구분되지 않는다.
- 무한 스크롤이 아니다(2절에서 범위 밖). `이전 댓글 더 보기`는 주소가 바뀌는 **링크**이며 JS 없이 동작한다. 스크롤이 아니라 사용자가 누를 때만 늘어난다.
- `N`에는 **상한 200**이 있다. 주소로 들어오는 값이라 막지 않으면 `?comments=99999999` 하나로 한 게시글의 댓글을 전부 메모리에 올릴 수 있다. 상한에 막혀 못 보여주는 댓글이 남으면 링크를 감추지 않고 **화면에 그 사실을 적는다.** 감추면 "댓글이 여기까지"로 보이는데 그것은 거짓이다.
- **"더 보기"를 눌러도 조회수는 오르지 않는다** (2026-08-04, 조각 6에서 해소). 주소가 바뀌므로 상세를 다시 여는 것은 맞지만, `?comments=`가 붙은 요청은 조회수를 올리지 않는 경로로 간다(6.2). **10분 창에 맡기지 않는 이유도 6.2에 있다** — 10분 넘게 읽다가 누르면 창이 이미 닫혀 있다. 조각 6 이전에는 클릭마다 +1이었고, 조회수가 순위를 정하게 된 이상(6.2 정책 변경) **댓글이 많은 글일수록 조회수가 저절로 부푸는 자가 인플레**였다 — 감수할 성질이 아니라 고쳐야 할 것이었다(`PLAN.md` R13). 하네스는 H12가 고정한다.

**개수는 두 가지를 따로 센다.** 화면의 `댓글 N`은 노출 중인 것만 세고(4.4), "더 펼칠 게 남았는지"는 자리 표시까지 세야 한다. 하나로 합치면 개수가 부풀거나, 삭제된 댓글만 남은 구간에서 더 보기가 사라져 그 아래 댓글에 닿을 수 없다.

**삭제된 댓글의 본문은 조회에서 `NULL`로 지운다.** 자리 표시에는 쓰지 않는 값이라 화면까지 내려보낼 이유가 없고, 내려보내지 않으면 템플릿을 잘못 고쳐도 지워진 댓글이 되살아나지 않는다. 지운 사람이 지우기를 원한 것이 바로 그 본문이다.

### 6.5 좋아요

- **`POST /community/{id}/likes`(추가) / `POST /community/{id}/likes/delete`(취소) 분리.** 토글로 만들지 않는다. 토글은 재전송·더블클릭 시 두 번 실행되어 원래 상태로 되돌아가고, 사용자는 눌렀는데 안 눌린 상태가 된다.
  - **취소가 `DELETE` 메서드가 아닌 이유** (2026-08-04 정정). 원래 `DELETE /community/{id}/likes`로 적었는데 **HTML 폼은 DELETE를 보낼 수 없다.** 보내려면 `spring.mvc.hiddenmethod.filter.enabled`를 켜야 하는데 그것은 커뮤니티 밖 전역 설정이고, 이 프로젝트에는 `@DeleteMapping`이 한 곳도 없다. 게시글·댓글 삭제도 `POST .../delete`다. **6.5가 지키려는 것은 메서드가 아니라 "토글 금지 + 양쪽 멱등"이며 그것은 그대로다.**
- 두 경로 모두 **멱등**하게 만든다. 이미 눌린 상태에서 추가를 다시 받아도 성공으로 응답하고(UNIQUE 위반을 에러로 노출하지 않는다), 누른 적 없는 상태에서 취소를 받아도 성공이다 — 사용자가 원한 상태가 이미 이뤄져 있다.
  - 추가는 `INSERT ... ON DUPLICATE KEY UPDATE`로 받는다. **`INSERT IGNORE`를 쓰지 않는다** — UNIQUE 위반만이 아니라 FK 위반과 값 잘림까지 경고로 낮춰서, 없는 게시글·없는 회원으로 들어온 요청이 조용히 성공한다.
  - **갱신 행 수로는 아무것도 판단하지 않는다.** `CLIENT_FOUND_ROWS` 때문에 새로 넣은 것과 이미 있던 것이 구분되지 않고(6.2), 구분할 이유도 없다 — 뒤따르는 재계산이 실제 행 수를 다시 센다.
- **`posts.like_count`는 매번 재계산한다**: `UPDATE posts SET like_count = (SELECT COUNT(*) FROM post_likes WHERE post_id = ?), updated_at = updated_at WHERE id = ?`
  - **`updated_at`을 자기 값으로 다시 지정하는 것이 이 문장의 일부다.** `posts.updated_at`은 `ON UPDATE CURRENT_TIMESTAMP(6)`이라 그냥 두면 좋아요를 받은 글마다 화면에 `(수정됨)`이 붙는다(6.3). 조회수 UPDATE와 같은 처리이고, 시드에 실제로 이 버그가 있었다.
- 증분(`like_count + 1`) 방식을 쓰지 않는 이유: 한 번 틀어지면 스스로 복구되지 않고 아무도 모른다. 앞으로 `like_count`를 건드릴 경로(삭제·차단·탈퇴)가 늘어날 때마다 "여기서도 조정해야 하나"를 판단해야 하는데, 재계산은 그 판단 자체가 없다. `uk_post_likes_post_member`의 선두 컬럼이 `post_id`이므로 인덱스 범위 스캔으로 끝난다.
- INSERT/DELETE와 카운트 갱신은 **하나의 Service 트랜잭션**에서 처리한다.
- **그 트랜잭션은 게시글 행을 `SELECT ... FOR UPDATE`로 먼저 잠그고 시작한다. 순서를 바꾸면 교착이다.** `post_likes` INSERT는 FK 확인 때문에 부모 `posts` 행에 공유 잠금을 걸고, 뒤따르는 재계산이 같은 행의 배타 잠금을 기다린다 — 같은 글에 동시에 좋아요를 누른 요청 둘이 서로를 기다린다. 6.2에서 맞은 것과 같은 모양이지만 **해법은 다르다.** 조회수는 순서를 뒤집어 풀었는데 여기서는 뒤집을 수 없다(재계산은 INSERT 이후여야 새 행을 센다). 그래서 배타 잠금을 앞에서 잡아 요청들이 한 줄로 서게 한다.
  - 잠금 조회는 `posts`만 읽는다. `FOR UPDATE`는 **조인한 테이블의 행까지 잠그므로**, 상세 조회처럼 카테고리를 조인해 두면 좋아요 한 번에 카테고리 행이 잠기고 같은 분류의 모든 글이 서로 줄을 선다.
  - 추가와 취소가 **같은 문장으로 시작해야 한다.** 두 경로가 다른 순서로 잠그면 둘이 섞였을 때 다시 교착이다.
  - 이 잠금 덕분에 **좋아요 경로에는 `PLAN.md` R14의 경합 창이 없다.** 상태를 잠근 채 읽으므로 확인과 쓰기 사이에 관리자가 차단할 수 없다. 댓글에서 같은 잠금을 마다한 근거가 "막는 값이 싸지 않다"였는데, 좋아요는 `like_count` 때문에 어차피 같은 행에 배타 잠금을 잡아야 해서 값이 0이다.
- **"내가 눌렀는지"는 상세에만 표시한다** (2026-08-04, 9절 보류 해소). 버튼 문구가 `좋아요`인지 `좋아요 취소`인지를 갈라야 하므로 상세에는 필요하다. 목록에는 넣지 않는다 — 20행마다 붙는 값이라 목록 SQL과 H1a를 함께 넓혀야 하는데, 목록에서 얻는 것은 표시 하나뿐이다. 비로그인에게는 아예 묻지 않는다(버튼이 없으므로 물어볼 것이 없다).

### 6.6 신고

- 중복 신고는 **에러로 응답**한다("이미 신고한 게시글입니다"). 좋아요와 달리 멱등 성공 처리를 하지 않는 이유: 재신고는 "내 신고가 처리되지 않았다"는 인식의 표현이다. 조용히 성공을 돌려주면 접수됐다고 오해하지만 실제로는 아무 일도 일어나지 않는다.
- **신고 취소 불가.** 신고는 개인 선호 표시가 아니라 관리자에게 전달된 보고다. 관리자가 이미 조치했을 수 있고, 취소를 허용하면 "신고 → 취소 → 신고"로 UNIQUE를 우회한 반복 신고가 가능해진다.
- 댓글 신고는 1차 범위 밖이다 (`post_reports`는 게시글 전용).
- 자기 글은 신고할 수 없다. 신고는 관리자에게 남을 알리는 경로이고, 자기 글이 문제라면 지우면 된다.
- 신고 대상은 노출 중인 글뿐이다(4.5). 삭제·차단된 글은 상세가 열리지 않으므로 신고할 경로도 없다.

**신고 상태 전이** (2026-08-04 결정, 9절 보류 해소).

| 전이 | 허용 | 주체 |
|---|---|---|
| `PENDING → RESOLVED` | 허용 | 관리자 (게시글 차단) |
| `PENDING → REJECTED` | 허용 | 관리자 (신고 기각) |
| `RESOLVED`/`REJECTED`에서 나가는 전이 | **금지** | — |

- `ReportStatus { PENDING, RESOLVED, REJECTED }` enum으로 정의한다. 신고 종료 SQL은 `PENDING` 행만 조건부로 변경하고, 새 migration으로 `CHECK` 제약을 건다.
- **상태를 바꾸는 것은 게시글 단위다.** 관리자가 글을 차단하면 그 글의 `PENDING` 신고가 전부 `RESOLVED`가 되고, 차단하지 않기로 하면 `기각`으로 전부 `REJECTED`가 된다. 신고 한 건씩 처리하지 않는 이유는 조치의 단위가 게시글이기 때문이다 — 같은 글에 대한 신고 다섯 건 중 셋만 처리된 상태는 관리자에게 아무 뜻도 없다.
- **작성자가 지운 글(`DELETED`)에는 기각도 할 수 없다** (2026-08-04, PR #96 Codex 리뷰). `REJECTED`는 "관리자가 보고 문제없다고 판단했다"는 기록인데, 글이 사라져 판단할 대상이 없어진 경우에 그 값을 남기면 기록이 사실과 달라진다. 남은 미처리 신고는 **자동으로 닫지 않고 그대로 둔다** — 게시글을 지워도 자식 행은 건드리지 않는다(4.5). 차단된 글은 다르다: 차단 시점에 미처리 신고가 함께 닫히므로 거기 남아 있는 것은 그 뒤에 들어온 신고이고, 이미 조치한 글이라 닫을 길이 있어야 한다.
- **차단을 해제해도 신고는 `RESOLVED` 그대로 둔다.** 4.2가 `blocked_*`를 되돌리지 않는 것과 같은 이유다. 상태는 "그때 조치했다"는 기록이지 현재 노출 여부가 아니다.
- 신고가 종착 상태로 닫힌 뒤 같은 회원이 다시 신고할 수는 없다. `UNIQUE(post_id, reporter_id)`가 회원당 한 건이며 취소도 재신고도 없다.

### 6.7 관리자 차단

- **관리자 수동 차단만.** 신고 누적 자동 차단·자동 숨김 없음.
- 근거: `blocked_by`가 `members.id` FK다. 자동 차단은 넣을 값이 없어 시스템 계정이나 암묵적 NULL 규칙이 필요하다. 스키마가 사람이 차단하는 것을 전제한다. 또한 임계값 방식은 담합 어뷰징 방어(신고자 신뢰도 등)를 불러오며 MVP를 벗어난다.
- 차단 시 `status='BLOCKED'`, `blocked_at`, `blocked_reason`, `blocked_by`를 함께 기록한다. 차단 사유는 필수다(7절) — 작성자에게 보여 주는 값이므로(4.3) 비어 있으면 차단 화면이 아무 말도 하지 않는다.
- **관리자의 조치는 차단과 해제뿐이다.** 게시글 삭제도, 댓글 삭제도 관리자 권한이 아니다. 게시글 삭제는 작성자만(4.2, `BLOCKED → DELETED`는 금지), 댓글 삭제는 그 댓글의 작성자만 할 수 있다(6.4). 관리자 화면에 그런 버튼을 두지 않는다.
- 차단·해제는 게시글 행을 잠그고 시작한다(`SELECT ... FOR UPDATE`). 6.5와 같은 자리다 — 같은 행에 쓰면서 신고 상태까지 함께 바꾸므로, 잠금 없이 하면 조회수·좋아요 경로와 잠금 순서가 엇갈린다.

**관리자 목록 화면**(`GET /admin/community`)은 상태 필터와 정렬 둘만 받는다 (2026-08-04 결정, 9절 보류 해소).

- 상태: 전체 / `PUBLISHED` / `BLOCKED`. `DELETED`도 목록에는 나온다(관리자는 모든 상태를 본다, 4.3).
- 정렬: 최신순(기본) / 미처리 신고 많은 순. `id` tiebreaker는 어느 정렬에도 붙인다(6.1과 같은 이유).
- 허용값은 `<choose>`로 매핑하고 `${}`로 잇지 않는다. 모르는 값은 기본값으로 떨어뜨린다.
- **작성자·제목 검색은 넣지 않는다.** 관리자가 하는 일은 "신고된 글을 찾아 조치하는 것"이고 그 동선은 정렬이 해결한다. 검색은 LIKE 4종과 인덱스 판단을 함께 불러오며, 필요해지면 그때 조각으로 세운다.
- 상태 어휘는 화면에서도 문서와 같은 말을 쓴다 — `노출 중`/`차단됨`/`삭제됨`. 목업의 `정상`/`제재`는 버린다.

### 6.8 카테고리

- `QNA`(질문) / `REVIEW`(후기) / `FREE`(자유) 3종을 **새 Flyway migration으로 주입**한다.
- `seed-local.sql`이 아닌 migration인 이유: `posts.category_id`가 NOT NULL FK이므로 카테고리가 없으면 운영에서 글쓰기가 아예 불가능하다. 샘플 데이터가 아니라 기능 동작에 필요한 참조 데이터다. 선례: `V20260729_003452__provision_default_store.sql`.
- 카테고리 목록(필터 드롭다운, 글쓰기 선택지)에는 `is_active = 1`만 노출한다. 비활성 카테고리에 이미 달린 글은 그대로 보인다.
- 카테고리 관리 화면은 만들지 않는다.

### 6.9 인기글

**매일 새벽 배치가 한 번 집계해 그날의 인기글을 확정하고, 화면은 확정된 결과만 읽는다.** 요청이 올 때마다 집계하지 않는다.

**점수** = 최근 7일 창의 `조회수 × 1 + 좋아요 × 25 + 댓글을 쓴 서로 다른 회원 수 × 15`

| 신호 | 계수 | 왜 이 값인가 |
|---|---|---|
| 조회수 | 1 | 비로그인 조회자의 키가 세션 id라 조작할 수 있고(R12), 10분 창에서 뷰어 하나가 하루 144까지 올린다. **가장 못 믿을 신호이므로 가장 작은 계수를 준다** |
| 좋아요 | 25 | `UNIQUE(post_id, member_id)`가 있어 회원당 최대 1이다. 구조적 상한이 있는 유일한 신호다 |
| 댓글 | 15 | **건수가 아니라 쓴 사람 수다.** `comments`에는 UNIQUE가 없어 한 사람이 몇 개든 달 수 있으므로, 건수로 세면 계정 하나가 댓글 20개로 좋아요 12명분을 만든다. `COUNT(DISTINCT member_id)`로 접어야 계수 15의 근거가 성립한다 |

- **창은 대상일을 포함해 7일이다.** 시작은 `대상일 − 6일 00:00:00` **이상**, 끝은 `대상일 + 1일 00:00:00` **미만**이다. 끝을 `23:59:59 이하`로 적지 않는다 — `DATETIME(6)`은 그 뒤로도 값이 있어 자정 직전 1초가 통째로 빠진다.
- 기간을 두는 이유는 없으면 초기에 쌓인 글이 인기글 영역을 영구 점유하기 때문이고, 하루가 아니라 7일인 이유는 활동이 적은 날에 좋아요 두 개짜리 글이 1위가 되어 순위가 잡음이 되기 때문이다.
- **노출 중이 아닌 댓글은 세지 않는다.** 자리 표시로 남은 것은 대화가 아니다(4.4).
- 점수가 0인 글은 순위에 오르지 않는다.

**확정과 스냅샷**

- 배치는 **상위 20건**을 저장하고 화면은 **10건**을 쓴다. 20−10의 여유는 비노출 글의 몫이 아니라 **선정 이후의 상태 변화**를 흡수하는 몫이다.
- **선정 단계와 노출 단계 모두 `status = 'PUBLISHED'`를 본다.** 게시글을 지워도 자식 행은 남으므로(4.5) 지워진 글도 창 안의 활동을 그대로 갖고 있고, 삭제 직전에 인기였던 글일수록 상위를 차지한다. 선정에서 안 거르면 그런 글이 20칸을 먹어 화면이 10건보다 적게 나온다.
- **선정 당시의 조회수·좋아요·댓글 수를 함께 저장한다.** 순위가 왜 그랬는지가 사후에 설명되어야 하기 때문이고, 원본이 나중에 변해도 그날의 기록은 그대로 남는다.
- **이미 확정된 날짜는 다시 집계하지 않는다.** 좋아요 취소·댓글 삭제 뒤에 재실행하면 확정된 순위가 조용히 바뀌는데, 그러면 스냅샷이 스냅샷인 이유가 사라진다. 재실행은 **실패한 날짜에만** 의미가 있다.
- **실패하면 아무것도 남기지 않는다.** 지우기·넣기·기록이 한 트랜잭션이다. 여기가 뚫리면 그날 순위가 통째로 사라지는데 화면은 전날로 폴백해 멀쩡히 보인다.
- **활동이 0인 날도 "확정했다"고 기록한다.** 기록하지 않으면 "안 돈 날"과 구분되지 않아 화면이 옛 날짜로 되돌아가고, 7일 창 밖의 오래된 글이 무기한 걸린다.

**시각의 기준**

배치가 넘기는 날짜는 서울 기준이고 `created_at`은 DB 시계로 박힌다. 둘이 같은 뜻이 되도록 **JDBC 세션 시간대를 `+09:00`으로 고정**한다(`application.yml`). 이름(`Asia/Seoul`)이 아니라 오프셋인 이유는 이름을 쓰면 MariaDB의 시간대 테이블이 채워져 있어야 하고, 기본 설치에는 비어 있어 연결 자체가 실패하기 때문이다. 한국 표준시는 서머타임이 없어 두 값이 언제나 같다.

**화면**

인기글은 **목록 화면(`GET /community`) 상단의 영역**이다. 별도 화면이 아니다 — 인기글만 보러 들어오는 사람은 없고, 목록에 가는 길에 눈에 띄어야 의미가 있다. 화면 구성은 `screens/list.md`가 받는다.

- **1쪽이고 카테고리 필터가 없을 때만 싣는다.** 필터를 건 화면에 전체 인기글이 뜨면 필터가 안 먹은 것처럼 보이고, 2쪽부터는 같은 영역이 매 쪽 반복될 이유가 없다. 이 판단은 화면이 아니라 **Service**에 있다 — 규칙이라 화면이 늘면 두 벌이 되고, 두 벌이 되는 순간 갈린다.
- **읽는 것은 최신 확정일 하나다.** 오늘 것이 있으면 오늘, 없으면 자동으로 어제 것이 나온다. 배치를 거른 날에도 화면이 비지 않는다.
- **확정 날짜를 함께 보여 준다.** 인기글은 실시간이 아니라 확정된 스냅샷이고 폴백까지 하므로, 언제 것인지 없으면 낡은 순위를 오늘 것으로 읽게 된다. 그 화면은 정상일 때와 똑같이 생겼다.
- **숫자(조회수·좋아요·댓글)를 싣지 않는다.** 같은 글이 아래 목록에도 나오고 그쪽은 **현재** 수치를 보여 준다. 한 화면에 같은 글의 숫자가 둘이면 사용자에게는 어느 쪽도 못 믿을 값이 된다. 스냅샷의 근거 수치는 사후 설명용이지 화면용이 아니다.
- **그릴 것이 없으면 영역이 통째로 사라진다.** 제목만 남기고 안을 비우지 않는다. 확정된 실행이 하나도 없을 때(첫 배포 직후)와 오른 글이 전부 지워지거나 차단됐을 때 둘 다 해당하고, **사용자가 할 수 있는 일이 같으므로 화면은 둘을 구분하지 않는다.**
- **최신 확정일이 그제 이하로 밀리면 경고 로그를 남긴다.** 폴백은 사용자에게 매끄러운 만큼 운영자에게도 아무 일 없어 보여서, 순위가 조용히 낡아 가는 것을 알릴 유일한 흔적이다. 다만 배치가 도는 새벽(01:00 전)에는 정상 상태에서도 확정일이 그제라 경고하지 않는다 — 울지 않아야 할 때 우는 경고는 곧 아무도 안 보게 된다.

## 7. 입력 검증

| 항목 | 규칙 | DB 컬럼 |
|---|---|---|
| 게시글 제목 | 필수, 1~100자 | `VARCHAR(200)` |
| 게시글 본문 | 필수, 1~5000자 | `TEXT` |
| 댓글 내용 | 필수, 1~500자 | `TEXT` |
| 신고 사유 | 필수, 1~500자 | `VARCHAR(500)` |
| 차단 사유 | 필수, 1~500자 | `VARCHAR(500)` (`posts.blocked_reason`) |

- 화면 허용 길이를 DB 컬럼 크기보다 작게 잡는다. 컬럼 크기를 그대로 쓰면 정책을 정한 게 아니라 안 정한 것이다.
- **trim 후 검증**한다. 공백만 입력은 거부. 저장 시 제목은 trim, 본문은 앞뒤만 trim(중간 줄바꿈 보존).
- **본문에 HTML을 허용하지 않는다. 순수 텍스트만.** 템플릿에서 `th:utext`를 절대 쓰지 않는다(`th:text`가 기본 이스케이프한다). 줄바꿈은 CSS `white-space: pre-wrap`으로 처리한다.

## 8. 탈퇴 회원

- `posts.member_id`는 NOT NULL FK이므로 탈퇴해도 회원 행은 남는다.
- **탈퇴 회원의 글·댓글은 유지하고, 작성자명만 "탈퇴한 회원"으로 표시**한다.
- **탈퇴 여부는 회원 도메인이 판정한다.** 커뮤니티는 `MemberCommunityQueryService`에서 `withdrawn`을 받아 표시명만 고른다. 커뮤니티 SQL이 `members`를 JOIN해 직접 판정하지 않는다(조각 10b, `conventions.md` 15.1).
- **회원 행을 찾지 못해도 글은 목록에 남고 작성자만 가려진다.** JOIN하던 때는 그런 글이 목록에서 통째로 사라졌는데, 그건 위 규칙과 어긋난다.
- 글을 함께 삭제하지 않는 이유: 질문글이 사라지면 거기 달린 답변들이 맥락을 잃는다. 커뮤니티는 개인 소유물이 아니라 공유 자산이다. 실명을 그대로 두지 않는 이유는 개인정보다. 표시명만 바꾸면 데이터를 건드리지 않으므로 되돌릴 수 있다.
