공지는 관리자가 알리는 글이고 **게시글이 아니다.** 표를 나누는 것이 이 spec의 첫 결정이며, 나머지 규칙 대부분이 거기서 따라 나온다.

## E4. 표를 나눈다 (`community_notices`)

`posts`에 `is_notice` 플래그나 공지 카테고리를 두지 않는다.

**확정된 정책 일곱 중 셋이 "없어야 한다"는 부정형이다** — 일반 글과 전환 불가, 댓글·좋아요 미제공, 조회수·인기글 집계 제외. 플래그로 두면 이 셋은 **`posts`를 읽는 모든 쿼리에 배제 조건을 빠짐없이 붙였을 때만** 지켜진다. 지금 `posts`를 읽는 자리는 목록·개수·상세·관리자 목록·관리자 상세·인기글 선정·인기글 노출이고, 인기글 배치는 `post_views`·`post_likes`·`comments` 셋을 `UNION ALL`한 뒤 `posts`와 JOIN하므로 조건이 세 군데로 번진다. **한 곳만 빠뜨리면 조용히 샌다** — 공지가 인기글 1위에 올라도 화면은 정상으로 보인다.

표를 나누면 **집계 SQL을 한 글자도 건드리지 않고** 셋이 전부 성립하고, 신고 불가도 따라온다. 조건문이 아니라 스키마가 정책을 지킨다.

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | `BIGINT` PK AUTO_INCREMENT | |
| `title` | `VARCHAR(200)` NOT NULL | 화면 허용은 100자(`../DOMAIN.md` 7절) |
| `content` | `TEXT` NOT NULL | 순수 텍스트. HTML 금지 |
| `status` | `VARCHAR(20)` NOT NULL | `PUBLISHED` / `DELETED`. 기본값 `PUBLISHED` |
| `starts_at` | `DATETIME(6)` NULL | **NULL = 즉시 노출** |
| `ends_at` | `DATETIME(6)` NULL | **NULL = 무기한** |
| `created_by` | `BIGINT` NOT NULL FK `members(id)` | 감사용. 화면에 쓰지 않는다 |
| `created_at` | `DATETIME(6)` NOT NULL | |
| `updated_at` | `DATETIME(6)` NOT NULL | `ON UPDATE CURRENT_TIMESTAMP(6)` |

표는 `V20260812_065639__add_community_notices.sql`이 만든다.

- `chk_community_notices_status`로 `CHECK (status IN ('PUBLISHED','DELETED'))`를 건다. 이름과 `DEFAULT`는 `docs/conventions.md` 11절이 정본이다(선례: `V20260802_113219__add_post_status_constraint.sql`).
- **뒤집힌 기간도 `CHECK`로 막는다** — `starts_at IS NULL OR ends_at IS NULL OR starts_at < ends_at`.
  화면 입력은 `NoticeForm`이 먼저 거르지만, 뒤집힌 기간은 **공지를 영영 안 보이게 만들면서 등록은
  성공으로 끝난다.** 조건문이 아니라 표가 정책을 지킨다는 이 spec의 방식과 같은 자리다.
- **`BLOCKED`가 없다.** 차단은 남의 글을 관리자가 막는 일이고, 공지는 관리자가 쓴다.
- **조회수 컬럼을 두지 않는다.** 두면 `post_views`의 10분 중복 방지 창과 `viewer_key` 체계를 공지용으로 한 벌 더 만들어야 하는데(`community-read.md` B3), 그 값을 쓰는 화면이 없다. 정책 7("조회수 집계 제외")을 컬럼 부재로 지킨다.
- **자식 표가 없다.** 댓글·좋아요·신고가 구조적으로 불가능하다.
- **`deleted_at`을 두지 않는다.** 노출 판단은 아래 한 조각이 전부이고, `posts`도 삭제 시각을 따로 남기지 않는다(`../DOMAIN.md` 4.1의 "조건을 늘리지 않는다"와 같은 이유).

### 노출 조건 — 조건이 셋이라는 것이 이 표의 고유 위험이다

```
status = 'PUBLISHED'
AND (starts_at IS NULL OR starts_at <= :now)
AND (ends_at   IS NULL OR :now <  ends_at)
```

**`../DOMAIN.md` 4.1은 "노출 기준은 `status` 하나"라고 못 박았고, 공지는 거기서 벗어난다.** 4.1이 조건을 하나로 묶은 이유가 "새 쿼리를 추가할 때 하나를 빠뜨린다"였는데, 노출 기간을 두기로 한 이상 셋을 피할 수 없다. 그래서 **같은 방식이 아니라 같은 목적을 지킨다**: 이 조각을 MyBatis `<sql id="visibleNotice">` 하나로 두고 **모든 고객 조회가 `<include>`로만 쓴다.** 복사해 쓰지 않는다 — 복사하는 순간 4.1이 막으려던 자리가 그대로 열린다. 지키는 것은 규율이 아니라 H42다.

정렬도 같은 이유로 `<sql id="visibleNoticeOrder">` 하나다. 아래 정렬 키는 **화면이 보여 주는 날짜와 같은 값**이어야 하는데, 조각이 갈리면 한쪽만 고쳐도 목록이 정렬 안 된 것처럼 보인다.

- **경계는 시각으로 적는다.** 시작은 `starts_at` **이상**, 끝은 `ends_at` **미만**이다. `23:59:59 이하`로 적지 않는다 — `DATETIME(6)`은 그 뒤로도 값이 있어 마지막 1초가 통째로 빠진다(`community-popular.md` E3의 창과 같은 규칙).
- **`:now`는 SQL의 `NOW()`가 아니라 Service가 `Clock`으로 만들어 넘긴 값이다.** `NOW()`를 박으면 테스트가 "시작 정각"과 "종료 정각"을 고정할 수 없어 경계 검사 자체가 불가능해진다. 인기글 배치가 날짜를 밖에서 받는 것과 같은 이유다(`../PLAN.md` D10·D3).
- **정렬 인덱스를 두지 않는다.** 공지는 수십 건 규모라 훑는 비용이 인덱스 값보다 작고, 아래 정렬 키가 함수식이라 일반 인덱스로는 어차피 못 탄다. **되돌아올 계기**: 공지가 수백 건이 되거나 목록이 느려지면 그때 `starts_at`을 NOT NULL로 좁히고(등록 시 `created_at`으로 채움) 정렬 인덱스를 세운다.

### 최신순이 무엇의 최신인가 (결정 필요했던 자리)

확정된 것은 "최신순"까지이고, **노출 기간을 함께 넣기로 하면서 기준이 갈렸다.**

- **고객 화면: `COALESCE(starts_at, created_at) DESC, id DESC`**
- **관리자 화면: `created_at DESC, id DESC`**

고객 쪽을 등록 시각으로 하면, 오늘 등록하고 다음 주로 예약한 공지가 **뜨는 날 목록 한가운데에 나타난다.** 사용자에게는 새로 생긴 글인데 위치는 과거라 눈에 띄지 않는다 — 공지를 상단에 두는 이유 자체가 무너진다. 관리자 쪽은 반대로 "내가 언제 등록했나"가 찾는 기준이라 등록 시각이 맞다.

`id` tiebreaker는 양쪽 모두에 붙인다(`community-read.md` B1과 같은 이유 — 같은 시각 공지가 두 쪽에 중복되거나 누락된다).

## B8. 상단 영역 (메인)

공지가 다른 화면 안에 실리는 자리는 **메인 하나**다. 커뮤니티 목록은 조각 18부터 공지를 조회하거나
렌더링하지 않는다. 공지와 회원 게시글을 한 목록에 섞지 않고, 공지는 B9의 독립 메뉴에서 탐색한다.

| 자리 | 건수 | 싣는 조건 | 조각 |
|---|---|---|---|
| 메인(`GET /`) 서비스 안내와 카테고리 사이 | 3 | 조건 없음 | 14c · 완료 |

- **메인에서는 `서비스 안내` 다음, `카테고리` 앞에 둔다.** 서비스의 첫인상을 먼저 보여 준 뒤 상품
  탐색 전에 공지를 읽을 수 있는 순서다. 노출 중인 공지가 없어도 영역과 전체보기 링크는 유지하고
  목록 자리에 `등록된 공지가 없습니다.`를 보여 준다.
- **건수는 커뮤니티의 메인 공개 계약이 갖는다.** 부르는 쪽이 정하면 화면이 늘 때마다 값이 흩어진다.
- **등록 개수에는 제한이 없고 메인 노출 건수에만 제한이 있다.** 4번째부터는 B9의 전체보기로 닿는다.
- **메인은 최신 3건을 한꺼번에 쌓지 않고 5초마다 한 건씩 순환한다.** 서버가 첫 공지를 보이는
  상태로 렌더링하고 나머지는 `hidden`으로 둔다. 전용 JavaScript가 실행될 때만 다음 공지를 열기
  때문에 스크립트가 오류 나거나 비활성화돼도 빈 영역이 아니라 첫 공지가 고정 노출된다.
  공지 링크에 키보드 포커스가 있거나 포인터가 영역 위에 있는 동안에는 현재 공지를 읽고 활성화할 수
  있도록 순환을 멈춘다. 운영체제·브라우저의 `prefers-reduced-motion: reduce` 설정이 켜져 있으면
  자동 순환을 시작하지 않고 현재 공지를 고정한다. 전용 홈 CSS는 링크의 flex 표시보다 `hidden`
  상태를 우선한다.
- **숫자를 싣지 않는다.** 공지에는 조회수도 반응도 없다.

## B9. 전체보기 (`GET /community/notices`)

- 고객 GNB의 `공지사항` 메뉴가 정식 진입점이다. 공지 유무와 현재 화면에 관계없이 공통 header에서
  항상 노출한다. 커뮤니티 목록 안에는 별도 공지 버튼을 두지 않는다.
- 오프셋 페이지 번호 페이징. `PageRequest`/`PageResult` 재사용, 페이지 크기 **20 고정**(B1과 같다).
- 정렬 옵션 없음. 위의 고객 정렬 하나다.
- 정렬 키가 변하지 않는 값이라 B1의 조회수순이 겪는 오프셋 문제(`../PLAN.md` R28)가 여기엔 없다.
- 표시 항목: 제목, 노출 시작일. **작성자와 본문 미리보기는 없다.**
- **화면의 날짜는 정렬 키와 같은 값이다** — `starts_at`이 없으면 `created_at`을 그 자리에 쓴다
  (`NoticeView.displayedAt`). 등록일을 보여 주면서 노출 시작일로 정렬하면 목록이 뒤죽박죽으로
  보이고, 그 화면은 정렬이 깨진 것과 구분되지 않는다.

## B10. 상세 (`GET /community/notices/{id}`)

| 접근자 | 노출 중 | 노출 기간 밖 | `DELETED` |
|---|---|---|---|
| 비로그인 / 회원 | 정상 | **404** | **404** |
| 관리자 (고객 경로) | 정상 | **404** | **404** |
| 관리자 (`/admin/community/notices`와 `/{id}/edit`) | 정상 | 정상 | 정상 |

- **관리자 공지 상세 화면은 없다.** 목록에서 바로 수정 폼(`/{id}/edit`)으로 가므로 관리자가 모든 상태의 공지를 보는 자리가 그 둘이다.
- 403이 아니라 404인 이유는 `../DOMAIN.md` 4.3과 같다 — 403은 그 자리에 글이 있다는 사실을 흘린다.
- **`customer/community/detail.html`을 재사용하지 않는다.** 공지 전용 템플릿을 판다. 재사용하면 댓글·좋아요 영역을 `th:if`로 가리게 되는데, 그러면 **표를 나눠 얻은 구조적 보증을 화면에서 도로 무른다** — 조건 하나가 뒤집히면 공지에 댓글창이 열린다.
- 본문은 순수 텍스트다. `th:utext`를 쓰지 않고 줄바꿈은 `white-space: pre-wrap`으로 처리한다(`../DOMAIN.md` 7절).

## C5. 관리자 목록 (`GET /admin/community/notices`)

- 모든 상태·모든 기간의 공지가 나온다(관리자는 전부 본다, `../DOMAIN.md` 4.3과 같은 방향).
- 오프셋 페이지 번호 페이징. `PageRequest`/`PageResult` 재사용, 페이지 크기 **20**(C1과 같다).
  상태 필터는 두지 않는다 — 배지가 네 상태를 한 화면에서 구분해 주고, 공지는 수십 건 규모다.
- **노출 상태를 배지로 보여 준다 — `예정` / `노출 중` / `종료` / `삭제됨`.** 이 배지가 없으면 **종료일을 실수로 과거에 넣은 공지가 등록 직후부터 안 보이는데, 등록 화면은 성공으로 끝난다.** 조용히 틀리는 자리를 화면에서 드러내는 것이 이 배지의 목적이고, 그래서 과거 종료일 자체는 거부하지 않는다("지금부터 감추기"는 정당한 사용이다).
- 상태 어휘는 화면에서도 문서와 같은 말을 쓴다(`community-admin.md` C1과 같은 규칙).

## C6. 작성·수정 (`GET·POST /admin/community/notices/new` · `/{id}/edit`)

- 작성과 수정은 같은 폼을 쓴다(A1·A2 선례).
- 입력 검증은 `../DOMAIN.md` 7절이 정본이다. 노출 기간은 **둘 다 선택**이고, 둘 다 있으면 `starts_at < ends_at`이어야 한다.
- 기간 순서는 **`NoticeForm`의 Bean Validation과 표의 `CHECK` 두 곳에 있다.** 폼 쪽은 관리자가 필드 오류로 고칠 수 있게 하는 자리고, 표 쪽은 그 경로를 거치지 않는 쓰기까지 막는 자리다. 길이·필수값처럼 폼만으로 끝나는 규칙과 다르게 잡은 이유는 위 E4에 있다.
- 수정은 `PUBLISHED`인 공지에만 열린다. `DELETED`는 종착 상태라 폼 자체가 닫힌다(C7과 같은 규칙).
- **일반 게시글을 공지로, 공지를 일반 게시글로 바꾸는 경로는 없다.** 표가 다르므로 만들 것이 없다 — 정책 5는 구현하지 않음으로써 지켜진다.

## C7. 삭제 (`POST /admin/community/notices/{id}/delete`)

- **soft delete** — `status = 'DELETED'`. 행을 지우지 않는다.
- `DELETED`는 종착 상태다. 복구는 범위 밖이다(`../DOMAIN.md` 4.2의 `DELETED` 취급과 같다).
- 이미 `DELETED`인 공지를 다시 지우면 0행이고, **0행을 성공으로 넘기지 않는다**(`community-admin.md` H17과 같은 자리).

## D3. 메인 공지 계약

- 메인은 `home` 도메인이라 커뮤니티의 Mapper·테이블에 직접 닿지 않고 공개 조회 계약을 거친다(`docs/conventions.md` 12절).
- 조각 13에서 만든 `CommunityHomeQueryService`에 `getNoticeSection()`을 더했다. **새 계약 클래스를 만들지 않았다** — 소비 도메인이 같으면 계약도 하나다.
- 건수 3은 그 계약이 갖는다. **목록의 "1쪽 + 필터 없음"은 가져오지 않는다** — 메인에는 쪽도 필터도 없어 조건이 성립하지 않고, `PageRequest(1, ...)`을 지어내면 목록의 페이지 크기가 바뀔 때 메인이 함께 흔들린다(인기글에서 같은 결정을 했다).
- `home`은 공통 협의 도메인이라 `HomeService`·`HomeController`·`main.html` 변경은 PR에서 확인을 받는다.

## 권한

`/admin/**`가 이미 `hasRole("ADMIN")`이므로(`../DOMAIN.md` 5절) 관리자 경로는 URL에서 강제된다. **화면 숨김에 기대지 않는다**(`AGENTS.md` 보안 규칙).

고객 경로 셋(`GET /community/notices`, `GET /community/notices/{id}`, 상단 영역)은 `permitAll`이다 — 공지는 비로그인도 읽어야 하는 안내다.

**`SecurityConfig`에 두 경로를 따로 적어야 한다.** 기존 규칙이 `/community/{id:\d+}`라 숫자만 받고, `"notices"`는 거기 걸리지 않는다. 안 적으면 `anyRequest().hasRole("USER")`로 떨어져 **비로그인이 로그인 화면으로 튕긴다** — 공지를 공개로 두려던 결정이 조용히 뒤집힌다.

## 검증

이 spec이 소유하는 하네스다. 번호만 갖는 인덱스는 `../PLAN.md`에 있다. 번호 없는 항목은 그 조각에 착수할 때 확정한다.

**H39 — 표가 미정의 상태값과 뒤집힌 기간을 거부함.** 둘 다 애플리케이션 조건문이 아니라 `CHECK`가 지키기로 한 자리라(위 E4), 제약이 실제로 걸려 있는지를 표에 직접 넣어 보고 확인한다. 뒤집힌 기간은 **등록이 성공으로 끝나면서 공지만 영영 안 보이게** 만들기 때문에 정상 경로 검사로는 절대 드러나지 않는다. 같은 시각을 시작·종료에 넣은 경우(`starts_at = ends_at`)도 함께 본다 — 노출 창이 0이라 통과시키면 안 된다.

**H40 — 노출 상태 배지 판정이 기간 경계 양쪽에서 옳음.** `starts_at` 정각은 `노출 중`이고 그 **직전**은 `예정`이다. `ends_at` 정각은 **`종료`**이고 그 직전은 `노출 중`이다. 한쪽만 보면 기간이 1일이든 30일이든 똑같이 통과한다(H23이 가르쳐 준 자리). 고정한 `Clock`으로 본다. 배지는 화면 문구가 아니라 **판정**이므로 Service 단에서 본다 — 14b의 고객 조회가 같은 경계를 SQL로 다시 쓰게 되고, 두 곳이 갈리면 목록에는 `노출 중`인데 고객 화면에는 없는 공지가 생긴다.

**H41 — 관리자 공지 쓰기가 Security 뒤에 있음.** 실제 필터 체인으로 일반 회원의 등록·삭제 요청이 거절되고 **표가 안 바뀐 것**까지 본다(`community-admin.md` H18과 같은 자리).

**H42 — 노출 조건이 한 곳에만 쓰여 있고, 모든 고객 조회가 그것을 `<include>`한다.** 이 spec의 E4 전체가 이 하나에 걸려 있다. 조건 자체를 XML에서 **딱 한 번** 세고, 고객 조회 셋이 전부 `<include refid="visibleNotice"/>`를 갖는지 본다. 조건을 복사해 넣은 네 번째 조회는 **처음에는 맞게 동작하므로 행동 검사로는 절대 안 잡힌다** — 나중에 조건이 바뀔 때 한쪽만 바뀌고, 그때도 화면은 멀쩡하다. 관리자 조회가 **그 조각을 쓰지 않는 것**도 같은 검사에서 본다(관리자는 전부 봐야 한다).

**H43 — 삭제·기간 밖 공지가 고객 경로 모두에서 빠지고, 노출 중인 공지는 남는다.** **빠뜨려도 화면은 멀쩡하다** — 종료된 공지가 하나 더 보이는 것은 고장으로 안 보인다. 정상 케이스만 보면 조건을 통째로 지운 구현이 통과하므로 **반대쪽을 반드시 함께 본다**(`community-popular.md` H25와 같은 유형). 경계 양쪽도 여기서 본다 — `starts_at` 정각은 들어가고 그 직전은 빠지며, `ends_at` 정각은 빠지고 그 직전은 들어간다. H40이 배지에서 보는 것과 **같은 규칙을 SQL에서** 다시 본다. 두 곳이 갈리면 관리자 목록에는 `노출 중`인데 고객 화면에는 없는 공지가 생긴다.

**H44 — 폐기.** 커뮤니티 목록 고정 행 자체를 조각 18에서 제거했다. 번호는 재사용하지 않는다.

**H51 — 고객 GNB에 공지 정식 진입점이 항상 그려진다.** 공지 목록의 존재만으로는 사용자가 그 화면에
닿을 수 있는지 보증하지 못한다. 대표 고객 화면을 실제 렌더링해 공통 GNB의 `/community/notices` 링크를
확인한다.

**H57 — 커뮤니티 목록이 공지를 조회하거나 렌더링하지 않는다.** 목록 Controller에서 공지 Service
의존성과 `noticeSection` Model 계약을 제거하고, 노출 중인 공지를 넣은 실제 렌더링에서도 공지 제목이
게시글 목록에 섞이지 않는지 본다. 화면에서 행만 감추고 조회를 남기면 결과는 같지만 목록 요청마다
불필요한 쿼리가 계속 실행되므로 두 경계를 함께 고정한다.

**H45 — 메인이 자기 건수(3)로 읽고, 공지가 없으면 빈 상태 안내를 보이며, 서비스 안내와 카테고리 사이에 있다.** 건수는 인기글 H38과 같은 방식으로 그 값으로 물은 스텁만 응답하게 두어 다른 값을 물으면 결과가 비게 만든다 — 건수를 잘못 늘려도 **화면은 멀쩡해 보인다**(공지가 많은 날과 구분되지 않는다). 빈 결과를 실제 렌더링해 영역과 `등록된 공지가 없습니다.`가 함께 남는지 본다. 자리는 낱말이 아니라 `id`로 보고, `서비스 안내 < 공지 < 카테고리` 순서인지 본다.

**H58 — 메인 공지 롤링의 서버 폴백이 첫 공지를 고정 노출한다.** 여러 공지를 실제 렌더링해 첫 링크에는
`hidden`이 없고 나머지 링크에는 있는지, 전용 롤링 스크립트가 연결됐는지 함께 본다. 처음부터 모든
공지를 감춘 뒤 JavaScript가 첫 공지를 여는 구현은 정상 브라우저에서는 같아 보여도 스크립트 오류·비활성화
시 공지 영역이 비므로 허용하지 않는다.

## 2차로 미룬 것

- **상단 고정 순서 수동 조정.** 지금은 최신순 하나다. 순서를 손으로 바꾸려면 정렬 컬럼과 그 재배치 UI가 함께 필요하다.
- **공지 카테고리·중요도.** 배지를 나누려면 분류 체계를 먼저 정해야 한다.
- **예약 공지 알림.** 노출 시작 시점에 알리는 것은 `notification` 도메인과의 계약이 선행이다.
- **첨부 이미지.** 게시글 이미지 첨부(A4)와 같은 결정에 묶인다.
