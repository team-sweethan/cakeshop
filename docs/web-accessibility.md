# cakeshop 웹 접근성 가이드라인

이 문서는 고객·관리자 웹 화면을 설계, 구현, 검토할 때 적용하는 접근성 기준의 정본이다. 목표는
[WCAG 2.2](https://www.w3.org/TR/WCAG22/) Level AA의 성공 기준을 개발 기준으로 사용하는 것이다.
이 목표는 현재 서비스 전체가 WCAG 2.2 AA를 충족한다는 적합성 선언이 아니다. 적합성은 완성된 페이지와
사용자 과정을 대상으로 자동 검사와 수동 검증을 마친 뒤에만 주장한다.

이 문서는 프로젝트에서 반복해서 적용할 구현·검증 규칙을 정리한 것이며 WCAG 성공 기준 전체를 옮긴
체크리스트가 아니다. 이 문서에 따로 적지 않은 Level A·AA 성공 기준도 WCAG 2.2 원문을 기준으로 적용한다.

공통 레이아웃과 프래그먼트 배치는 [`frontend-template-format.md`](frontend-template-format.md), 테스트의
계층과 중복 기준은 [`testing.md`](testing.md)를 함께 따른다. 아직 합의되지 않은 공통 UI 정책은
[`team-plan.md`](team-plan.md)에 기록하고, 합의가 끝나면 이 문서나 프런트엔드 정본으로 옮긴다.

## 1. 적용 범위와 원칙

- `templates`에서 렌더링하는 고객·관리자·인증·홈·오류 화면과 공통 프래그먼트에 적용한다.
- 화면 동작을 만드는 CSS와 JavaScript, 사용자가 업로드하거나 운영자가 등록하는 화면 콘텐츠에도 적용한다.
- 네이티브 HTML 요소로 표현할 수 있으면 ARIA 역할을 새로 만들지 않는다. ARIA는 의미를 보완하며 네이티브
  요소가 제공하는 키보드 동작을 대신하지 않는다.
- 사용자 기능을 특정 입력 방식으로만 실행할 수 있게 만들지 않는다. 경로 자체가 입력에 필수인 자유 곡선
  그리기 같은 기능은 키보드 조작의 예외로 둘 수 있지만, 단순한 이동·선택·크기 조절에는 동등한 조작을
  제공한다.
- 색, 위치, 모양, 아이콘과 소리만으로 상태나 지시사항을 전달하지 않는다.
- 접근성 속성의 존재만으로 완료로 판단하지 않고 실제 렌더링 결과와 전체 사용자 과정을 확인한다.

## 2. 문서 구조와 콘텐츠

- 전체 HTML 문서는 `<!doctype html>`, 문서 주 언어인 `lang="ko"`, 화면 목적을 구분할 수 있는 `title`을
  제공한다.
- 문서 주 언어와 다른 문구나 구절은 고유명사처럼 언어를 판별할 수 없는 경우를 제외하고 해당 `lang`을
  지정한다.
- 화면마다 주 콘텐츠를 `main` 하나로 구분하고, 제목은 내용을 건너뛰지 않는 논리적인 순서로 구성한다.
- 여러 화면에서 반복되는 탐색 영역보다 주 콘텐츠에 먼저 접근할 수 있도록 건너뛰기 링크나 동등한 방법을
  제공한다.
- 반복되는 주요 탐색 영역은 `nav`와 식별 가능한 이름을 사용한다. 같은 종류의 탐색 영역이 여러 개라면
  `aria-label` 또는 `aria-labelledby`로 구분한다.
- 링크는 이동에, 버튼은 현재 화면의 동작에 사용한다. 클릭 동작을 `div`나 `span`에만 연결하지 않는다.
- 링크 목적은 링크 텍스트만으로 또는 프로그램으로 확인 가능한 주변 문맥과 함께 구분할 수 있어야 한다.
  버튼의 접근 가능한 이름은 동작을 구분할 수 있게 작성한다.
- 표 형식의 관계가 있는 데이터는 `table`과 적절한 머리글을 사용하고, 단순 배치에는 표를 사용하지 않는다.

## 3. 키보드와 포커스

- 경로 기반 입력이 본질적으로 필요한 예외를 제외한 모든 사용자 기능은 특정한 키 입력 시간 제한 없이
  키보드 인터페이스로 실행할 수 있어야 한다. 각 컨트롤은 `Tab`, `Shift+Tab`, `Enter`, `Space` 등
  네이티브 요소나 채택한 위젯 패턴의 키보드 관례를 따른다.
- 드래그로 실행하는 기능은 클릭·탭처럼 드래그하지 않는 단일 포인터로 완료할 수 있는 동등한 방법도
  제공한다. 드래그가 기능에 본질적이거나 사용자 에이전트가 제공하고 작성자가 수정하지 않은 동작은 예외로
  둘 수 있다.
- 포커스 순서는 화면의 읽기 순서와 일치해야 한다. 양수 `tabindex`로 순서를 강제하지 않는다.
- 포커스 표시를 제거하지 않는다. 커스텀 표시를 사용할 때는 배경과 구분되고 가려지지 않아야 한다.
- 일반적인 성공 알림 때문에 사용자의 포커스를 강제로 이동하지 않는다. 입력 오류, 대화상자와 화면 전환처럼
  이동이 필요한 경우에는 이동 위치와 복귀 위치를 함께 설계한다.
- modal dialog는 열릴 때 내부의 적절한 요소로 포커스를 이동하고, 열린 동안 포커스가 배경으로 빠지지 않게
  하며, `Escape` 또는 명시적인 닫기 동작을 제공하고, 닫힌 뒤 실행 요소로 포커스를 돌려보낸다.
- 복합 위젯을 직접 만들 때는 [WAI-ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/)의
  해당 패턴과 키보드 관례를 따른다.

## 4. 폼과 오류

- `input type="hidden"`을 제외하고 사용자가 입력하거나 선택하는 폼 컨트롤에는 화면에 보이는 `label`을
  연결한다. 보이는 이름을 제공할 수 없는 경우에만 접근 가능한 이름을 별도로 제공한다.
- 필수 여부, 형식과 제한은 placeholder만으로 설명하지 않는다.
- 이름, 전화번호, 생년월일처럼 사용자 본인에 관한 정보를 받으며 WCAG의 입력 목적 목록에 해당하는 필드는
  의미에 맞는 `autocomplete` 토큰 등으로 입력 목적을 프로그램이 식별할 수 있게 한다.
- 오류는 문제가 발생한 입력 근처에 텍스트로 표시하고, 해당 입력과 `aria-describedby` 등으로 연결한다.
- 제출 실패 시 첫 오류나 오류 요약으로 포커스를 이동할 수 있어야 하며, 사용자가 입력한 정상 값은 가능한 한
  유지한다.
- 오류 원인뿐 아니라 가능한 수정 방법을 함께 제공한다. 색상이나 테두리만으로 오류를 표시하지 않는다.
- 인증 과정은 붙여넣기와 비밀번호 관리자를 방해하지 않고, 불필요한 기억·계산 과제를 요구하지 않는다.

## 5. 이미지와 비텍스트 콘텐츠

- 정보를 전달하는 `img`에는 목적을 설명하는 `alt`를 제공한다.
- 인접한 텍스트와 완전히 중복되는 장식 이미지는 `alt=""`로 보조기기에서 제외한다.
- 아이콘만 있는 버튼에는 동작을 설명하는 접근 가능한 이름을 제공한다. 아이콘 모양 자체를 이름으로 쓰지 않는다.
- 차트와 시각화는 같은 핵심 정보를 확인할 수 있는 텍스트 요약이나 데이터 표를 제공한다.
- 자동 재생되는 소리와 사용자가 멈출 수 없는 반복 애니메이션을 사용하지 않는다. 동작 효과는 운영체제의
  `prefers-reduced-motion` 설정을 존중한다.

## 6. 시각적 표시와 반응형 화면

- 일반 텍스트는 배경과 최소 `4.5:1`의 명암비를 확보한다. 최소 `24 CSS px`이거나 굵은 글씨이면서 최소
  `18.66 CSS px`인 큰 텍스트는 최소 `3:1`을 확보한다.
- 입력 테두리, 포커스 표시와 의미 있는 아이콘 같은 UI 표시는 인접 색상과 최소 `3:1`의 명암비를 확보한다.
- 브라우저 확대 `200%`에서 콘텐츠와 기능이 손실되지 않아야 한다.
- 너비 `320 CSS px` 수준의 화면에서도 콘텐츠와 기능의 손실 없이 한 방향으로 스크롤하며 읽고 조작할 수
  있어야 한다. 데이터 표처럼 의미상 2차원 배치가 필요한 콘텐츠는 예외로 둘 수 있다.
- 텍스트 크기를 고정 높이 컨테이너에 가두어 확대 시 잘리지 않게 한다.
- 포인터 입력 대상은 최소 `24 × 24 CSS px`이어야 한다. 이보다 작은 대상은 각 대상의 경계 상자 중앙에
  지름 `24 CSS px`인 원을 놓았을 때 그 원이 다른 대상이나 다른 작은 대상의 원과 겹치지 않는 간격을
  확보한다. 같은 페이지에 기준을 충족하는 동등한 대상이 있거나, 문장 안의 링크처럼 줄 높이가 크기를
  제한하거나, 작성자가 수정하지 않은 브라우저 기본 컨트롤이거나, 해당 표현이 본질적·법적으로 필요한
  경우에는 예외로 둘 수 있다.

## 7. 상태 메시지와 화면 알림

이 절의 화면 알림은 저장·수정·로그아웃 결과처럼 현재 사용자 동작에 대한 UI 피드백을 뜻한다. 알림 저장,
읽음 상태와 외부 발송을 소유하는 `notification` 도메인과는 별개다.

- 포커스를 받지 않는 상태 변화는 보조기기가 인식할 수 있는 역할이나 속성을 제공한다.
- 성공과 일반 진행 상태는 `role="status"` 또는 `aria-live="polite"`를 기본으로 한다.
- 즉시 알려야 하는 오류와 경고만 `role="alert"` 또는 `aria-live="assertive"`를 사용한다. 같은 메시지를
  중복으로 읽게 하는 역할과 live 속성의 중첩을 피한다.
- 알림은 색상만으로 성공과 실패를 구분하지 않고 의미가 드러나는 텍스트를 포함한다.
- 자동으로 사라지는 알림이 정보를 확인할 유일한 방법이면 표시 시간을 조절·연장하거나 다시 확인할 경로를
  제공한다. 중요한 오류와 후속 조치가 필요한 내용은 사용자가 확인하기 전에 제거하지 않는다.
- 닫기나 후속 동작이 있는 알림은 키보드로 조작할 수 있고 각 동작에 접근 가능한 이름이 있어야 한다.
- toast, 페이지 내 message area, dialog와 `window.alert()`의 사용 구분은 공통 UI 정책으로 합의한다.
  표현 방식을 확정하기 전에도 위 접근성 요구사항은 동일하게 적용한다.

## 8. 검증과 완료 조건

화면 변경은 위험과 범위에 맞춰 다음 검증을 선택한다. 자동 도구 결과만으로 WCAG 적합성을 선언하지 않는다.

1. 렌더링 테스트에서 제목, `label` 연결, 개인정보 필드의 입력 목적, 상태 역할과 필요한 ARIA 관계 등 변경한
   접근성 계약을 확인한다.
2. 브라우저에서 키보드만 사용해 모든 기능의 진입과 실행, 오류 수정, dialog 닫기와 포커스 복귀를 확인한다.
3. `200%` 확대와 좁은 화면에서 콘텐츠 잘림, 가림과 불필요한 양방향 스크롤을 확인한다.
4. 변경한 색 조합의 텍스트·UI·포커스 명암비와 포인터 대상의 크기·간격을 검사한다.
5. 동적 메시지와 커스텀 위젯은 대표 브라우저와 스크린 리더 조합으로 이름, 역할, 상태와 읽기 순서를
   확인한다.
6. axe, Lighthouse 같은 자동 검사 도구를 사용할 수 있지만 결과를 수동 검증의 대체로 보지 않는다.
7. 실제 렌더링 HTML은 필요할 때 [W3C Markup Validation Service](https://validator.w3.org/) 등으로
   검사한다. Thymeleaf 원본이 아니라 서버가 생성한 HTML을 대상으로 한다.

PR에는 변경한 화면, 수행한 자동·수동 검증, 확인하지 못한 항목과 남은 위험을 기록한다. 전체 WCAG 적합성을
검증하지 않았다면 `WCAG 준수 완료`라고 표현하지 않는다.
