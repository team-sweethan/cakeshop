# Flyway로 데이터베이스 변경을 관리하는 이유

- 상태: 채택
- 기록일: 2026-08-10
- 대상: MariaDB 스키마, 제약조건, 인덱스와 필수 기준 데이터

## 해결하려던 문제

cakeshop의 업무 규칙은 Java 코드뿐 아니라 MariaDB의 테이블, 외래 키, UNIQUE·CHECK 제약조건과
인덱스에도 존재한다. 팀원이 각자 SQL을 수동으로 실행하면 실행 순서와 누락 여부를 알기 어렵고, 로컬·CI·
공용 DB가 서로 다른 구조가 될 수 있다.

MyBatis는 애플리케이션 시작 시 Entity를 기준으로 스키마를 자동 생성하지 않는다. 따라서 어떤 스키마에서
코드가 동작하는지 저장소 안에서 재현하고, 코드 변경과 DB 변경을 같은 리뷰 단위로 확인할 수단이 필요했다.

## 결정

공통 스키마와 모든 환경에 필요한 기준 데이터의 변경을 Flyway versioned migration으로 관리한다.

- migration은 `src/main/resources/db/migration`에 순서가 있는 SQL 파일로 저장한다.
- 새 파일은 Gradle `newMigration` 태스크로 생성한다.
- 이미 공유되거나 적용된 migration은 수정하지 않고 후속 migration을 추가한다.
- 로컬 화면 확인용 샘플 데이터는 `db/seed`로 분리한다.
- 개인 local DB와 테스트에서는 자동 적용하고, 공용 RDS는 검토된 별도 절차로 반영한다.

## 선택 이유

### 스키마를 코드와 함께 재현할 수 있다

빈 데이터베이스에 migration을 순서대로 적용하면 애플리케이션이 기대하는 테이블과 제약조건을 만들 수
있다. 새 팀원과 CI가 별도의 수동 SQL 전달 없이 같은 출발점에서 실행된다.

### 변경 이력과 적용 여부가 남는다

각 변경은 버전과 설명을 가진 파일로 Git에 남고, Flyway의 이력 테이블에는 실제 DB에 적용된 버전과
checksum이 기록된다. “현재 스키마가 무엇인가”뿐 아니라 “어떤 순서로 여기까지 왔는가”를 추적할 수 있다.

### 코드와 DB 변경을 한 PR에서 검토할 수 있다

새 상태값, 필수 컬럼과 인덱스처럼 코드가 전제하는 스키마를 구현과 함께 검토한다. Java 코드만 먼저
배포되거나 SQL 전달이 누락되는 위험을 줄이고, 기존 데이터에 미치는 영향과 복구 방법을 PR에서 확인할 수
있다.

### DB 제약을 모든 환경에서 동일하게 검증한다

소유권과 상태 전이는 Service가 검증하지만 UNIQUE, FK와 CHECK 같은 마지막 방어선은 DB가 담당한다.
테스트도 MariaDB Testcontainers에 동일한 migration을 적용하므로 운영과 다른 간이 스키마에서 초록 테스트가
나오는 일을 줄인다.

### 필수 기준 데이터와 샘플 데이터를 구분한다

기능이 성립하려면 반드시 필요한 분류·대표 행은 migration으로 모든 환경에 제공한다. 개발 화면을 채우기
위한 회원·상품·게시글은 seed로 분리해 운영 데이터와 Flyway 이력을 오염시키지 않는다.

## 검토한 대안

### 팀원이 SQL을 수동 실행

도구가 단순하지만 누가 어느 SQL을 실행했는지, 순서가 맞는지, 누락된 환경이 어디인지 저장소만으로 확인할
수 없다. 재현 가능한 개발·테스트 환경을 만들기 어려워 선택하지 않았다.

### 애플리케이션 시작 시 자체 초기화 SQL 실행

최초 생성에는 사용할 수 있지만 변경 이력, checksum과 이미 적용된 버전 판단을 별도로 구현해야 한다.
부분 실패와 재실행 정책까지 애플리케이션 코드가 떠안게 되어 선택하지 않았다.

### ORM 스키마 자동 생성

현재 데이터 계층은 MyBatis이며 JPA Entity를 사용하지 않는다. 자동 생성은 운영 스키마 전환의 순서,
기존 데이터 backfill과 인덱스·제약조건의 세밀한 변경을 명시적으로 리뷰하기에도 적합하지 않다.

## 감수한 비용과 한계

- 공유된 migration은 불변이므로 작은 수정도 더 높은 버전의 새 파일로 추가해야 한다.
- 여러 브랜치가 동시에 migration을 만들면 버전과 적용 순서를 병합 시 다시 확인해야 한다.
- MariaDB DDL은 여러 문장이 모두 트랜잭션으로 되돌아간다고 보장할 수 없어 부분 적용과 복구 절차를
  설계해야 한다.
- Flyway가 변경 SQL의 업무적 안전성까지 보장하지 않는다. 기존 데이터 검증과 backfill 순서는 작성자가
  별도로 판단해야 한다.
- 공용 RDS는 자동 적용을 꺼 두었으므로 승인된 반영 절차가 없으면 코드와 DB가 달라질 수 있다.

## 다시 검토할 조건

다음 변화가 생겨도 스키마 이력 도구 자체는 필요하지만 적용 전략은 다시 검토한다.

- 구버전과 신버전 애플리케이션이 동시에 실행되는 무중단 배포가 필요하다.
- 대용량 테이블의 DDL과 backfill을 한 배포에서 처리할 수 없다.
- 여러 서비스가 같은 데이터베이스 스키마를 독립적으로 변경한다.
- 공용 RDS 배포를 자동화해 승인·검증·복구 단계를 파이프라인으로 옮긴다.

이 경우 Flyway를 제거하기보다 expand·backfill·contract 분리, 서비스별 스키마 소유권과 배포 파이프라인을
먼저 검토한다.
