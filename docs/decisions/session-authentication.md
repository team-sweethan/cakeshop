# 세션 기반 인증을 선택한 이유

- 상태: 채택
- 기록일: 2026-08-10
- 대상: 고객·관리자 웹 인증

## 해결하려던 문제

cakeshop은 브라우저에서 상품을 탐색하고 주문·결제·회원·관리자 기능을 사용하는 웹 애플리케이션이다.
로그인 이후 요청마다 인증 사용자를 식별하고, 역할에 따라 고객과 관리자 경로를 보호하며, 로그아웃이나
회원 정지 시 기존 인증을 종료할 방법이 필요했다.

현재 클라이언트는 Spring MVC와 Thymeleaf로 렌더링되는 웹 화면이며, 별도의 모바일 앱이나 제3자 API
클라이언트는 없다. 인증 결과를 여러 종류의 클라이언트가 독립적으로 소비해야 하는 요구도 없다.

## 결정

Spring Security의 폼 로그인과 `HttpSession`을 사용하는 세션 기반 인증을 채택한다. 브라우저는
`JSESSIONID` 쿠키를 보내고, 서버는 세션에 연결된 인증 상태를 기준으로 요청을 인가한다.

서버 사이드 렌더링(SSR)은 이 결정을 뒷받침하는 조건이지, 세션을 반드시 사용해야 하는 이유는 아니다.
SSR 애플리케이션도 토큰 인증을 사용할 수 있고, 반대로 클라이언트 렌더링 애플리케이션도 서버 세션을
사용할 수 있다. 이 프로젝트에서는 **브라우저 중심의 동일 출처 웹 화면, Spring Security 폼 로그인,
서버가 인증을 즉시 종료해야 하는 업무 요구**가 함께 있어 세션 방식이 가장 단순했다.

## 선택 이유

### Spring MVC 화면 흐름과 직접 결합된다

로그인이 필요한 화면으로 접근하면 요청을 저장했다가 로그인 후 원래 경로로 돌려보내고, 역할에 따라
고객과 관리자 기본 진입점을 나눈다. 인증 성공 후 서버가 다음 View 또는 redirect를 결정하는 현재 흐름은
Spring Security의 폼 로그인과 세션 기능으로 별도 토큰 저장·재발급 코드를 만들지 않고 구현할 수 있다.

### 인증 종료를 서버에서 통제할 수 있다

로그아웃할 때 세션과 인증 정보를 제거하고 `JSESSIONID` 쿠키를 삭제한다. 관리자가 회원을 정지하면
`SessionRegistry`에서 해당 회원의 세션을 찾아 즉시 만료시킨다. 이미 발급한 인증을 만료 시각까지
허용하는 단순한 자체 포함 토큰보다 현재 회원 관리 정책을 직접 표현한다.

### 브라우저 보안 기능을 기존 프레임워크 흐름으로 유지한다

상태를 변경하는 폼과 요청은 Spring Security의 CSRF 보호를 사용한다. 외부 시스템이 호출하는 결제 웹훅만
명시적으로 제외하며, 전체 CSRF 보호를 끄지 않는다. 인증 쿠키와 CSRF 토큰의 생성·검증을 프레임워크가
함께 관리하므로 애플리케이션이 별도의 토큰 전달 규약을 만들 필요가 없다.

### 현재 요구에 토큰 인프라의 비용이 필요하지 않다

액세스 토큰·리프레시 토큰의 발급, 저장, 회전, 폐기 목록과 탈취 대응은 모두 별도 정책과 코드가 필요하다.
현재는 동일한 서버가 화면과 인증을 함께 제공하고 외부 API 소비자가 없으므로 그 비용을 지불할 근거가
없다.

## 검토한 대안

### JWT 기반 무상태 인증

여러 독립 클라이언트가 API를 사용하거나 인증 서버와 리소스 서버를 분리할 때 유리하다. 그러나 현재
프로젝트에서는 브라우저 저장 위치, 토큰 갱신, 강제 로그아웃과 회원 정지 직후 폐기 정책을 새로 설계해야
하는 반면 얻는 이점이 작아 선택하지 않았다.

### 세션과 JWT의 동시 지원

현재 존재하지 않는 클라이언트를 예상해 인증 경로를 두 벌로 만들면 인가 규칙과 테스트도 두 벌이 된다.
실제 API 소비자가 생기기 전에는 도입하지 않는다.

## 감수한 비용과 한계

- 서버가 인증 상태를 보유하므로 완전한 무상태 확장은 할 수 없다.
- 애플리케이션 인스턴스가 여러 대가 되면 세션 고정 또는 Redis 같은 공유 세션 저장소가 필요하다.
- 쿠키 기반 인증이므로 CSRF 보호를 계속 유지해야 한다.
- 웹 API를 외부에 공개하면 브라우저 화면에 맞춘 로그인·redirect 계약을 그대로 재사용하기 어렵다.

## 다시 검토할 조건

다음 중 하나가 실제 요구가 되면 토큰 인증 또는 세션 저장소 확장을 다시 검토한다.

- 모바일 앱이나 외부 파트너가 독립적으로 API를 사용한다.
- 인증 서버와 화면/API 서버를 서로 다른 서비스로 분리한다.
- 여러 애플리케이션 인스턴스 사이에서 로컬 세션을 공유해야 한다.
- 다른 서비스가 cakeshop의 사용자 인증 결과를 전달받아야 한다.

## 현재 구현에서 확인할 위치

- [`SecurityConfig`](../../src/main/java/com/cakeshop/global/security/SecurityConfig.java): 폼 로그인, 경로별 인가,
  세션 등록, 로그아웃과 CSRF 설정
- [`MemberSessionService`](../../src/main/java/com/cakeshop/domain/member/service/MemberSessionService.java): 회원별
  기존 세션 만료
- [`MemberAdminController`](../../src/main/java/com/cakeshop/domain/member/controller/MemberAdminController.java):
  회원 정지 후 세션 만료 호출
- [`인증과 인가 규칙`](../conventions.md#10-인증과-인가): 요청값을 신뢰하지 않는 권한·소유권 검증 기준
