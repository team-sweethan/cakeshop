# 도메인 중심 수직 슬라이스 구조를 선택한 이유

- 상태: 채택
- 기록일: 2026-08-10
- 대상: 패키지 구조, 계층 의존 방향, 도메인 간 연동

## 해결하려던 문제

cakeshop은 상품·주문·결제·회원·쿠폰·커뮤니티·후기처럼 업무 규칙과 담당자가 다른 기능을 한 저장소에서
함께 개발한다. 기능 경계가 없으면 한 도메인의 변경이 다른 도메인의 Mapper와 테이블까지 직접 건드리고,
누가 규칙을 결정하고 검토해야 하는지 불분명해진다.

레이어별 최상위 패키지만 사용하는 구조에서는 하나의 기능을 이해하기 위해 Controller, Service, Mapper,
DTO 디렉터리를 계속 오가야 한다. 또한 같은 레이어에 있다는 이유로 다른 업무의 내부 타입을 참조하기
쉬워져 팀 작업의 충돌 범위가 넓어진다.

## 결정

업무 기능을 `domain/<domain>` 아래에 모으는 도메인 중심 수직 슬라이스를 채택한다. 각 도메인 내부에서는
다음 의존 방향을 유지한다.

```text
Controller -> Service -> Mapper -> DB
```

데이터와 업무 규칙은 해당 도메인이 소유한다. 다른 도메인은 그 도메인의 Entity, Mapper와 테이블을 직접
사용하지 않고, 소유 도메인이 제공하는 공개 `QueryService`·`CommandService`와 필요한 최소 DTO를 통해
연동한다.

이 구조는 DDD(Domain-Driven Design)의 **도메인 경계, 업무 언어, 명시적인 연동 계약**에서 영향을 받았다.
하지만 전술적 DDD 전체를 적용했다고 표현하지 않는다. 현재 Entity는 MyBatis가 DB 한 행을 매핑하는
객체이고, 모든 기능을 Aggregate·Value Object·Repository로 모델링하지 않는다. 따라서 cakeshop의 현재
구조를 가장 정확하게 설명하는 이름은 **DDD에서 영향을 받은 도메인 중심 수직 슬라이스**다.

## 선택 이유

### 기능 변경의 응집도를 높인다

한 기능의 Controller, Service, Mapper, Entity와 DTO가 같은 도메인 아래에 있어 변경 범위와 영향을 찾기
쉽다. 파일 종류보다 업무 기능을 기준으로 탐색할 수 있다.

### 데이터와 규칙의 소유권을 분명히 한다

회원 상태는 member, 결제 상태는 payment처럼 규칙을 결정할 위치가 명확하다. 다른 도메인이 내부 테이블을
직접 읽어 같은 판단을 다시 구현하지 않으므로 도메인별 정책이 서로 다르게 변하는 것을 막는다.

### 팀 담당과 리뷰 경계를 코드 구조에 반영한다

도메인 담당자가 자신의 변경을 주도하고, 도메인 간 계약이나 여러 테이블을 읽는 ReadModel은 관련
담당자가 함께 검토한다. Git의 디렉터리 경계만으로 충돌을 없앨 수는 없지만, 협의가 필요한 변경을 코드
구조에서 드러낼 수 있다.

### 기술 계층이 업무 규칙을 침범하지 않게 한다

Controller는 HTTP 입력과 View·redirect를, Service는 권한·상태·트랜잭션을, Mapper는 SQL을 담당한다.
의존 방향을 고정하면 화면이나 SQL에 업무 판단이 흩어지는 것을 줄일 수 있다.

### 필요한 만큼만 DDD 개념을 사용한다

MyBatis와 Spring MVC로 구성된 현재 규모에서 전술 패턴 전체를 강제하면 클래스와 변환 계층이 크게
늘어난다. 도메인 경계와 계약처럼 협업에 직접 도움이 되는 개념은 채택하고, Aggregate나 Value Object는
실제 불변식과 복잡성이 요구할 때만 도입한다.

## 검토한 대안

### 레이어별 최상위 패키지

모든 Controller, Service와 Mapper를 각각 한 디렉터리에 모으면 작은 애플리케이션에서는 단순하다. 하지만
기능과 담당자가 늘어날수록 한 업무의 파일이 흩어지고 다른 도메인의 내부 타입을 참조하기 쉬워져 선택하지
않았다.

### 전술적 DDD의 전면 적용

모든 도메인에 Aggregate Root, Repository, Value Object와 별도 영속성 모델을 의무화하면 복잡한 불변식을
표현하는 데 도움이 될 수 있다. 현재 기능 전체가 그 비용을 요구하지 않고 MyBatis 매핑 모델과 별도의
도메인 모델을 항상 유지할 실익도 확인되지 않아 전역 규칙으로 채택하지 않았다.

### 도메인 간 직접 JOIN과 Mapper 공유

초기 구현은 빠를 수 있지만 데이터 소유 도메인의 상태·제외 조건을 우회하고 스키마 변경의 영향이 호출부에
전파된다. 통계처럼 여러 도메인의 집계가 본질인 읽기 기능만 검토와 테스트를 전제로 ReadModel 예외를
사용한다.

## 감수한 비용과 한계

- 간단한 조회에도 공개 Service와 계약 DTO가 추가될 수 있다.
- 경계를 잘못 나누면 비슷한 조립 코드가 여러 도메인에 생길 수 있다.
- 홈·통계·대시보드처럼 여러 도메인의 데이터를 보여 주는 화면은 연동 계약 또는 ReadModel을 별도로
  설계해야 한다.
- 패키지를 도메인별로 나눴다는 사실만으로 DDD가 완성되지는 않는다. 업무 용어와 불변식이 코드에 제대로
  반영됐는지는 각 기능에서 계속 검토해야 한다.

## 다시 검토할 조건

- 하나의 도메인 안에서 여러 Entity의 불변식을 일관되게 지키기 어려워진다.
- 영속성 모델과 업무 모델의 변경 주기가 달라 서로 독립시킬 필요가 생긴다.
- 도메인을 별도 서비스로 분리해 네트워크 계약과 데이터 독립성이 필요해진다.
- 공개 Service 계약이 지나치게 많아지고 동일한 조립이 반복되어 현재 경계가 잘못됐다는 증거가 생긴다.

이 경우 필요한 도메인에 한해 Aggregate, Value Object, 별도 도메인 모델 또는 서비스 분리를 검토한다.
