# cakeshop PR 작성 규칙

- **범위**: GitHub Pull Request 작성, 리뷰 요청, 병합 기준
- **PR 본문 양식**: [GitHub PR 템플릿](../.github/pull_request_template.md)
- **관련 문서**: [코드 컨벤션](conventions.md), [테스트 작성 규칙](testing.md)

이 문서는 PR 정책과 병합 기준을 정한다. PR에서 작성할 항목은 GitHub PR 템플릿을 정본으로 사용한다.

## 1. 기본 원칙

- 하나의 PR은 하나의 목적만 다룬다. 기능 변경과 관련 없는 패키지 이동, 이름 변경, 포맷 정리는 분리한다.
- 리뷰 가능한 상태가 아니거나 설계 논의가 필요하면 Draft PR로 생성한다.
- PR 작성자는 리뷰 요청 전에 변경 파일을 직접 확인하고 불필요한 파일, 비밀 정보, 디버그 코드를 제거한다.
- Codex 리뷰는 보조 수단이며 CI와 `main` 병합에 필요한 사람의 승인을 대신하지 않는다.

### 담당 외 도메인의 연동 계약

담당 외 도메인에 연동 계약을 새 파일로 추가할 때는 그 담당자가 작성한 기존 파일을 수정하지 않는다면
사전 합의 없이 작성할 수 있다. 연동 계약은 `<소유 도메인><사용 도메인><역할>` 네이밍 규칙을 따른다.

`review`가 `member` 데이터를 사용하는 계약은 다음과 같이 작성한다.

- `MemberReviewQueryService`
- `MemberReviewCommandService`
- `MemberReviewMapper`
- `MemberReviewMapper.xml`

새로 만드는 Service 메서드에는 다음 주석을 작성한다.

```java
/**
 * ******************************
 * 작성자 :
 * 담당자 :
 * 작성일 :
 * 기능 :
 * 설명 :
 * ******************************
 */
```

기존 공개 Service 계약, 상태 전이 또는 담당자가 작성한 기존 파일을 변경할 때는 먼저 협의하고 PR 본문에
합의 내용을 기록한다. 여러 도메인을 JOIN하는 ReadModel은 조회 대상 테이블 담당자의 확인을 받는다.

## 2. PR 제목

제목은 `<type>: 변경 요약` 형식으로 작성한다. 제목만 읽어도 변경 결과를 알 수 있게 작성하고 마침표는 붙이지 않는다.

| type | 사용 기준 |
|---|---|
| `feat` | 사용자에게 제공되는 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서만 변경 |
| `ci` | CI workflow 변경 |
| `chore` | 빌드, 설정, 개발 환경 정비 |

```text
feat: 관리자 상품 재고 수정 기능 추가
fix: 결제 취소 시 상품 재고 복구 누락 수정
ci: PR Gradle 테스트 workflow 추가
```

## 3. PR 본문 작성

- [PR 템플릿](../.github/pull_request_template.md)의 필수 항목을 작성한다.
- 실행한 테스트 명령과 결과를 기록한다. 실행하지 못한 테스트는 사유를 남긴다.
- DB/Flyway/seed 변경이 있으면 변경 파일, 기존 데이터와 운영 환경 영향, 적용·복구 방법을 기록한다.
- 공유된 versioned migration은 수정하지 않고 새 파일을 만든다. 생성 명령과 규칙은
  [코드 컨벤션의 Flyway와 seed 절](conventions.md#8-flyway와-seed)을 따른다.
- 기존 공개 계약이나 담당자의 기존 파일을 변경했다면 사전 합의 내용을 기록한다.
- 화면을 변경했다면 스크린샷을 첨부한다.
- 조건부 항목에 해당하지 않으면 `없음`으로 작성한다.

## 4. 리뷰 요청과 병합 기준

### 리뷰 요청 전

1. PR 템플릿의 필수 항목을 작성한다.
2. 변경 사항을 self-review한다.
3. 변경한 동작을 검증하는 테스트를 추가하거나 미추가 사유를 기록한다.
4. 기존 공개 계약, 상태 전이 또는 담당자의 기존 파일을 변경했다면 필요한 사전 협의를 완료한다.
5. CI 통과를 확인한다.
6. Draft 상태를 해제해 리뷰 가능한 상태로 전환한다.

`dev` PR의 리뷰어 지정은 선택 사항이다. `main` PR은 리뷰어를 지정하고 2명의 승인을 받아야 한다.

### 병합 전

1. 전체 CI가 성공해야 한다. `main`은 required check가 설정되어 있지 않으므로 병합 전에 사람이 직접 확인한다.
2. 미해결 review conversation을 정리한다.
3. Codex 리뷰의 P0/P1 항목을 해결하거나 처리 근거를 남긴다.
4. `main` PR은 2명의 승인을 확인한다.

긴급하게 예외 병합이 필요하면 사유와 후속 조치 이슈를 남기고 팀의 승인을 받는다.

### 브랜치별 기준

| 기준 | `dev` | `main` |
|---|---|---|
| required check | `Test`, `Migration immutability` | 없음, 병합 전 CI 수동 확인 |
| 리뷰어 지정 | 선택 | 필수 |
| 승인 | 필수 아님 | 2명 필수 |
| review conversation 정리 | 원칙 | 필수 |

`main`은 평소 잠금 상태로 유지하며 릴리스 시점에 관리자가 잠금을 해제하고 병합한다.

### Codex 자동 리뷰

- Draft를 Ready for review 상태로 전환한 뒤 자동 리뷰가 시작되는지 확인한다.
- 자동 리뷰가 시작되지 않으면 PR 댓글에 `@codex review`를 남긴다.
- Codex 리뷰의 P0/P1 항목은 병합 전에 해결하거나 처리 근거를 남긴다.
- Codex 리뷰는 CI와 `main` 병합에 필요한 사람의 승인을 대신하지 않는다.
