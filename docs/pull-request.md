# cakeshop PR 작성 규칙

- **범위**: GitHub Pull Request 작성, 리뷰 요청, 병합 기준
- **관련 문서**: [코드 컨벤션](conventions.md), [테스트 작성 규칙](testing.md)

## 1. 기본 원칙

- 하나의 PR은 하나의 목적만 다룬다. 기능 변경과 관련 없는 패키지 이동, 이름 변경, 포맷 정리는 분리한다.
- 다른 담당자의 코드나 테스트를 수정해야 한다면 먼저 담당자와 수정 범위를 합의하고 PR 본문에 기록한다.
- 리뷰 가능한 상태가 아니거나 설계 논의가 필요하면 Draft PR로 생성한다.
- PR 작성자는 리뷰 요청 전에 변경 파일을 직접 확인하고 불필요한 파일, 비밀 정보, 디버그 코드를 제거한다.
- AI 코드 리뷰는 보조 수단이며 CI 통과와 사람의 승인을 대신하지 않는다.

## 2. PR 제목

제목은 `<type>: 변경 요약` 형식으로 작성한다.

| type | 사용 기준 |
|---|---|
| `feat` | 사용자에게 제공되는 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서만 변경 |
| `ci` | CI workflow 변경 |
| `chore` | 빌드, 설정, 개발 환경 정비 |

제목만 읽어도 변경 결과를 알 수 있게 작성하고 마침표는 붙이지 않는다.

```text
feat: 관리자 상품 재고 수정 기능 추가
fix: 결제 취소 시 상품 재고 복구 누락 수정
ci: PR Gradle 테스트 workflow 추가
```

## 3. PR 본문 필수 항목

### 변경 목적

어떤 문제를 해결하는지와 이 변경이 필요한 이유를 작성한다. 구현 방법만 나열하지 않는다.

### 주요 변경 사항

리뷰어가 변경 범위를 파악할 수 있도록 핵심 동작과 구조 변경을 작성한다. 관련 없는 세부 구현은 생략한다.

### 테스트 결과

- 실행한 명령과 결과를 작성한다.
- 추가한 정상·실패·권한·경곗값 시나리오를 필요한 범위에서 작성한다.
- 실행하지 못한 테스트가 있다면 사유와 후속 계획을 기록한다.
- 테스트 실패를 숨기거나 `-x test`로 우회하지 않는다.
- 최종 병합 전에는 전체 CI가 통과해야 한다.

### DB / Flyway 변경 여부

- DB 변경이 없으면 `없음`으로 명시한다.
- DB 변경이 있으면 새 migration 파일명, 변경 내용, 기존 데이터에 미치는 영향을 작성한다.
- 이미 공유되거나 적용된 versioned migration은 수정하지 않고 새로운 버전으로 추가한다.
- migration 파일명은 직접 짓지 않고 `gradlew newMigration -Pdesc=<snake_case>`로 만든다.
- 공통 schema migration은 `db/migration`, 로컬 seed는 `db/seed`에 둔다. seed는 Flyway 관리 대상이 아니라 RDS에서 실행될 일이 없다.
- seed를 고쳤다면 팀원이 다시 실행해야 한다는 점을 본문에 적는다(DB 재생성은 필요 없다).
- 데이터 삭제나 호환성 문제가 생길 수 있는 변경은 적용 순서와 복구 방법을 함께 작성한다.

### 리뷰어가 집중해서 볼 부분

작성자가 불확실하게 판단한 부분, 위험한 업무 규칙, 트랜잭션·권한·동시성 등 집중 리뷰가 필요한 지점을 작성한다. 특별한 요청이 없으면 `없음`으로 명시한다.

### 관련 이슈

GitHub 키워드와 이슈 번호를 사용한다.

```text
Closes #123
Related to #456
```

### 체크리스트

PR 템플릿의 체크리스트를 확인한다. 해당하지 않는 항목은 체크한 뒤 본문에 `해당 없음`인 이유를 적거나, 항목을 체크하지 않고 사유를 남긴다.

## 4. 리뷰 요청과 병합 기준

리뷰 요청 전 다음 조건을 만족해야 한다.

1. PR 본문의 필수 항목을 모두 작성한다.
2. 자신의 변경 사항을 self-review한다.
3. 변경한 동작을 검증하는 테스트를 추가하거나 미추가 사유를 기록한다.
4. 담당자가 다른 코드의 수정 범위를 합의한다.
5. CI 통과 후 Codex 자동 리뷰의 P0/P1 항목을 해결하거나 처리 근거를 남긴다.
6. Draft 상태를 해제한다.

병합 전에는 전체 CI 성공, 최소 1명의 승인, 미해결 review conversation 정리를 원칙으로 한다. 긴급하게 예외 병합이 필요하면 사유와 후속 조치 이슈를 남기고 팀의 승인을 받는다.

### Codex 자동 리뷰 설정과 운영

- 저장소 관리자는 [Codex Code Review 설정](https://chatgpt.com/codex/settings/code-review)에서 `team-sweethan/cakeshop`의 **Code review**와 **Automatic reviews**를 활성화한다.
- 리뷰는 연결된 ChatGPT/Codex 요금제 사용량으로 실행한다. 별도의 OpenAI API 키, GitHub Secret, 코드 리뷰용 GitHub Actions workflow를 추가하지 않는다.
- Codex는 루트 `AGENTS.md`의 `## Code Review Rules`를 저장소 전역 리뷰 기준으로 사용한다.
- 자동 리뷰가 시작되지 않으면 PR 댓글에 정확히 `@codex review`를 남기고 저장소 연결 및 Automatic reviews 설정을 확인한다.
- Codex 리뷰는 추가 검토이며 CI, branch protection, 사람의 필수 승인을 대체하지 않는다.

## 5. PR 작성 예시

> 아래 이슈 번호와 테스트 이름은 형식을 설명하기 위한 예시다.

### 제목

```text
fix: 결제 취소 시 상품 재고 복구 누락 수정
```

### 본문

```markdown
## 변경 목적

결제 완료 후 주문을 취소하면 결제 상태만 변경되고 차감된 상품 재고가
복구되지 않는 문제를 수정합니다.

## 주요 변경 사항

- 결제 취소 트랜잭션에서 주문 상품 수량만큼 재고를 복구합니다.
- 동일한 취소 요청이 반복돼도 재고가 중복 복구되지 않도록 취소 상태를 확인합니다.
- 정상 취소와 중복 취소 시나리오 테스트를 추가합니다.

## 테스트 결과

- `.\gradlew.bat test`: 통과
- 결제 완료 주문 취소 시 재고 복구: 통과
- 이미 취소된 주문 재요청 시 재고 중복 복구 방지: 통과
- 다른 회원의 주문 취소 요청 거부: 통과

## DB / Flyway 변경

- 없음

## 리뷰어가 집중해서 볼 부분

- 결제 취소와 재고 복구가 하나의 트랜잭션으로 처리되는지
- 중복 요청 방지 조건이 결제 취소 정책과 일치하는지

## 관련 이슈

Closes #123

## 체크리스트

- [x] 하나의 목적만 포함한 PR입니다.
- [x] 변경 사항을 self-review했습니다.
- [x] 전체 로컬 테스트를 실행하고 결과를 작성했습니다.
- [x] 테스트 코드를 추가했거나 미추가 사유를 작성했습니다.
- [x] DB/Flyway 변경 여부와 영향을 작성했습니다.
- [x] 기존 Flyway migration을 수정하지 않았습니다.
- [x] 로컬 seed가 운영 환경에서 실행되지 않는지 확인했습니다.
- [x] 민감 정보, `.env`, 디버그 코드를 포함하지 않았습니다.
- [x] 코드 컨벤션과 테스트 작성 규칙을 확인했습니다.
- [x] 관련 문서 변경 필요 여부를 확인했습니다.
- [x] 다른 담당자의 코드 수정 여부와 합의 내용을 확인했습니다.
```
