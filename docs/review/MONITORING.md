# 후기 모니터링 계획

- 상태: **초안** (2026-08-20). 아직 계측이 붙어 있지 않다.
- 범위: `src/main/java/com/cakeshop/domain/review/**`, `src/main/resources/mapper/review/**`
- 짝 문서: `docs/community/MONITORING.md` (같은 형식, 커뮤니티 도메인)

## 0. 이 문서를 왜 만드나

후기 도메인에는 **"나중에 재 보고 다시 판단한다"고 이미 적어 둔 위험이 둘** 있다.

- `reviews/risks.md` **R8** — 상품별 후기 조회를 받쳐 줄 인덱스가 없다.
  되돌아올 계기: *"한 상품의 후기가 수백 건을 넘거나 상품 상세가 눈에 띄게 느려지면"*
- `reviews/risks.md` **R12** — 관리자 검색이 받는 ID 목록에 상한이 없다.
  되돌아올 계기: *"회원이나 주문 상품이 수천 건을 넘고 관리자 검색이 눈에 띄게 느려지면"*

둘 다 **"눈에 띄게 느려지면"**이 조건인데, 지금은 그걸 알아챌 방법이 없다.
누가 우연히 화면을 열어 보고 느리다고 느끼기 전까지는 아무도 모른다.

이 문서는 **그 계기가 도달했는지를 알아채는 방법**을 정한다.
감시 대상 여섯 개를 고르고, 각각에 대해 무슨 일이 일어나는지·왜 그런지·어느 선을 넘으면
손을 대는지를 적었다.

**여기는 규칙의 정본이 아니다.** 기능 규칙은 `specs/`와 `DOMAIN.md`, 위험은 `reviews/risks.md`,
결정은 `decisions/`에 있다. 이 문서는 그 문장들이 여전히 맞는지 **재는 방법**만 갖는다.

### 알아 둘 전제

`risks.md` **R11**이 적어 둔 대로, **운영(rds)에는 이 도메인의 테이블이 아직 없다.**
Flyway가 꺼져 있어 스키마가 반영된 적이 없다. 그래서 이 계획은 전부 **로컬과 테스트 환경**을 대상으로 한다.
운영 모니터링은 배포 절차가 생긴 다음의 일이다.

## 1. 먼저 준비해야 하는 것

계측 도구를 붙이는 준비 작업은 커뮤니티와 완전히 같다.
**같은 내용을 두 번 적지 않는다** — `docs/community/MONITORING.md` 1절을 본다.

요지만 옮기면 이렇다.

- 지표를 만드는 라이브러리(`micrometer-registry-prometheus`)가 아직 없다
- 지표를 꺼내가는 통로(`/actuator/prometheus`)가 로그인에 막혀 있다
- 느린 쿼리 기록이 꺼져 있다

이 셋은 도메인과 무관한 공통 작업이라 `global` 쪽 변경이고, 후기 코드는 한 줄도 건드리지 않는다.

### 후기 도메인에 필요한 추가 준비

**데이터를 심어야 한다.** 지금 로컬 후기는 **2건**이다.
`seed-review.sql`이 일반 주문 1건·주문제작 1건에만 후기를 붙이고, 파일 끝의 주석도
*"유형별 작성 완료 1건·작성 가능 1건"*이라고 스스로 적고 있다.
**이 규모에서는 무엇을 재도 전부 빠르다.** 커뮤니티가 게시글 30건인 것과 같은 상황이다.

R8의 계기가 "**한 상품의 후기가 수백 건**"이므로, 그 근처와 그 위를 확인하려면 다음처럼 심는다.

| 상품 | 후기 수 | 무엇을 보려고 |
|---|---|---|
| A | 10건 | 지금 상태의 기준선 |
| B | 500건 | R8이 말한 계기 근처 |
| C | 5,000건 | 계기를 넘겼을 때 어떻게 되는가 |

**한 상품에 몰아서 심는 것이 핵심이다.** 후기 총량이 아니라 **한 상품이 가진 후기 수**가
이 도메인의 비용을 정한다. 아래 M1·M2·M3이 전부 같은 이유로 그렇다.

`uk_reviews_order_item` 때문에 후기 하나에 주문 상품 하나가 필요하다.
`order_items`도 함께 만들어야 하고, 이건 다른 도메인 테이블이라 **읽기만 하는 준비용 스크립트**로 둔다.

## 2. 무엇을 지켜보나

후기 도메인은 커뮤니티와 성격이 다르다.
커뮤니티는 **읽기가 많고** 쓰기는 가볍지만, 후기는 **쓰기 한 번이 무겁다.**
후기를 하나 쓸 때마다 그 상품의 평균 평점을 다시 계산해야 하기 때문이다.

그래서 감시 대상도 쓰기 쪽에 쏠려 있다.

| 사용자가 하는 일 | 감시 대상 |
|---|---|
| 후기를 쓴다 / 고친다 / 지운다 | **M1** 평점 재계산 비용, **M2** 같은 상품 동시 쓰기, **M4** 알림 |
| 상품 상세에서 후기를 본다 | **M3** 목록과 건수 |
| (배경) 상품 목록이 평점순으로 정렬된다 | **M5** 평점 값의 정확성 |
| 관리자가 후기를 관리한다 | **M6** 관리자 검색 |

### M1. 후기 하나를 쓰면 그 상품의 후기를 **전부** 다시 센다

**무슨 일이 일어나나**
후기가 많은 인기 상품일수록 **후기 쓰기가 느려진다.**
후기가 10개인 상품에는 금방 써지는데, 5,000개인 상품에는 눈에 띄게 오래 걸린다.
사용자 입장에서는 "인기 상품일수록 후기 쓰기 버튼이 굼뜨다"로 보인다.

**왜 그런가**
평균 평점을 저장해 두는 방식이라, 후기가 하나 늘거나 줄 때마다 **처음부터 다시 계산한다.**

```sql
SELECT COALESCE(AVG(overall_rating), 0), COUNT(*)
  FROM reviews
 WHERE product_id = #{productId} AND status = 'PUBLISHED'
   FOR UPDATE
```

이 쿼리가 하는 일은 **그 상품의 공개 후기를 전부 읽는 것**이다. 후기가 5,000개면 5,000줄을 읽는다.
후기 하나를 쓰는 값이 그 상품이 이미 가진 후기 수에 비례해서 커진다.

게다가 `reviews` 테이블에 이 조건에 맞는 **찾아보기(인덱스)가 없다.**
외래키가 만든 `product_id` 하나가 전부라서, **상품은 빨리 찾지만 그 후기들이 공개 상태인지는
줄을 하나씩 열어 봐야 안다.** `risks.md` R8이 적어 둔 것이 바로 이 자리다.

**무엇을 보나**

- 후기 쓰기 화면의 응답 시간 — `http_server_requests_seconds`의 p95
  (p95는 "가장 느린 5%를 뺀 나머지 중에서 가장 느린 값"이다. 평균보다 체감에 가깝다)
- **후기가 10개인 상품과 5,000개인 상품의 응답 시간 차이.** 이게 이 항목의 핵심 지표다
- slow query log에 `aggregateForUpdate`가 올라오는지

**어느 선을 넘으면 손을 대나**
R8이 정한 계기 그대로 — **한 상품의 후기가 수백 건을 넘고, 응답 시간이 후기 수에 비례해 늘 때.**
처방도 R8이 이미 적어 뒀다: `(product_id, status, created_at, id)` 복합 인덱스를 새 migration으로 더한다.
온라인으로 붙일 수 있어서 서비스를 멈추지 않아도 된다.

**인덱스로도 안 풀리는 부분이 남는다.** 인덱스는 "줄을 하나씩 열어 보는" 비용을 없애 주지만
**5,000줄을 읽는 것 자체는 그대로다.** 거기까지 가면 평균 평점을 매번 다시 계산하지 말고
누적해 두는 방식을 봐야 하는데, 그건 `ADR-001`이 정한 집계 소유권을 다시 여는 일이므로
**측정값 없이 꺼내지 않는다.**

### M2. 같은 상품에 여러 명이 동시에 후기를 쓰면 줄을 선다

**무슨 일이 일어나나**
같은 상품에 여러 사람이 동시에 후기를 쓰면, **한 번에 한 명씩만 처리된다.**
사람이 늘어도 처리되는 양은 그대로이고 기다리는 시간만 길어진다.

**왜 그런가**
평균 평점이 어긋나지 않게 하려고, 후기를 쓰기 전에 **상품 한 줄을 먼저 잠근다**
(`ProductReviewCommandService.lockForRating`). 잠긴 동안에는 같은 상품을 건드리는 다른 요청이 기다린다.

**이건 실수가 아니라 의도한 설계다.** 잠그지 않으면 두 사람이 동시에 후기를 쓸 때
둘 다 "내가 쓰기 전의 후기 수"를 기준으로 평균을 계산해서 값이 틀어진다.
잠그는 순서도 **상품 → 후기**로 항상 같아서, 서로가 서로를 기다리는 교착이 생기지 않는다.
(커뮤니티가 잠금 순서를 잘못 잡아 교착을 세 번 겪은 것과 대비되는 자리다.)

그러니 이 항목은 **"고장났는지"가 아니라 "얼마를 치르고 있는지"를 보는 것이다.**

**무엇을 보나**

| 볼 것 | 뜻 |
|---|---|
| `Innodb_row_lock_waits` | 줄을 기다린 횟수. 0에서 떠오르면 경합이 시작된 것 |
| `Innodb_row_lock_time_avg` | 한 번 기다릴 때 평균 얼마나 기다렸나 |
| `Innodb_deadlocks` | 교착. **여기는 0이어야 한다.** 0이 아니면 잠금 순서 규율이 깨진 것이다 |
| 같은 상품 동시 쓰기의 처리량 | 사람을 늘려도 늘지 않는 지점이 어디인가 |

**어느 선을 넘으면 손을 대나**

- **교착이 한 번이라도 나면 즉시.** 이건 성능 문제가 아니라 사용자에게 오류가 보이는 문제이고,
  잠금 순서 규율이 깨졌다는 뜻이다
- 기다리는 시간이 길어지는 것 자체는 **당장 손대지 않는다.** 실제로 한 상품에 여러 명이
  동시에 후기를 쓰는 일은 드물다. 다만 M1과 겹치면 나빠진다 —
  후기가 많은 상품일수록 잠금을 쥐고 있는 시간이 길어지기 때문이다.
  **두 지표를 같이 봐야 하는 이유가 이것이다**

**이미 있는 방어선과의 관계**
`ReviewReplyConcurrencyTests`가 비슷한 것을 이미 검사하고 있다.
모니터링은 그 검사를 대체하지 않는다 — 테스트는 "코드가 규칙을 지키는가"를 보고,
모니터링은 "실제로 얼마나 기다리는가"를 본다. **둘 다 필요하다.**

### M3. 상품 상세의 후기 목록

**무슨 일이 일어나나**
후기가 많이 달린 상품일수록 **상품 상세 페이지가 느려진다.**
후기를 20개만 보여 주는데도 그렇다.

**왜 그런가**
목록 쿼리가 이렇게 생겼다.

```sql
SELECT ... FROM reviews
 WHERE product_id = #{productId} AND status = 'PUBLISHED'
 ORDER BY created_at DESC, id DESC
 LIMIT #{size} OFFSET #{offset}
```

`product_id`로 후보를 찾는 것까지는 찾아보기가 있어서 빠르다.
문제는 그다음이다 — **찾아낸 후기들을 최신순으로 줄 세우는 일**을 찾아보기가 도와주지 못한다.
그래서 조건에 맞는 걸 전부 모아 놓고 따로 정렬한다. 후기가 많을수록 이 정렬이 커진다
(`EXPLAIN`에 `Using filesort`로 나타난다).

**총 몇 건인지 세는 쿼리도 같은 문제**를 갖는다. 20건만 보여 줘도 쪽 수를 내려면 전부 세야 한다.

**무엇을 보나**

- 상품 상세의 응답 시간을 **후기 10개 / 500개 / 5,000개 상품별로** 비교
- `EXPLAIN`에 `Using filesort`가 나오는지
- 깊은 쪽(마지막 페이지 근처)이 첫 쪽보다 얼마나 느린지

**어느 선을 넘으면 손을 대나**
M1과 **같은 인덱스 하나로 같이 풀린다.** `(product_id, status, created_at, id)`를 더하면
후보 찾기·상태 거르기·정렬이 한 번에 해결된다.
그래서 M1과 M3은 따로 판단하지 않고 **둘 중 하나라도 계기에 닿으면 함께 처리한다.**

### M4. 알림은 후기가 저장된 다음에 나간다

**무슨 일이 일어나나**
후기는 잘 저장됐는데 **알림만 안 간다.** 화면에는 아무 문제도 안 보인다.

**왜 그런가**
알림을 보내는 시점이 **후기 저장이 확정된 뒤**로 잡혀 있다
(`ReviewNotificationService`의 `afterCommit`, `ReviewNotificationSender`의 `REQUIRES_NEW`).

**이건 올바른 설계다.** 알림을 후기 저장과 같은 묶음에 넣으면
알림이 실패했다는 이유로 **후기까지 취소된다.** 그건 사용자가 원하는 동작이 아니다.

대신 대가가 하나 생긴다 — **알림이 실패해도 후기는 이미 저장되어 있고, 아무도 모른다.**
화면에는 후기가 정상으로 보이고, 오류도 안 뜬다.
"관리자에게 새 후기 알림이 안 갔다"는 사실은 **한참 뒤에 사람이 알아채기 전까지 드러나지 않는다.**

**무엇을 보나**

- 알림 발송에서 발생한 예외 건수 (로그)
- **후기 수와 알림 수의 차이.** 새 후기 100건에 `NEW_REVIEW` 알림이 100건 만들어졌는가
- 알림 발송에 걸린 시간이 후기 쓰기 응답 시간에 얼마나 얹히는가
  (커밋 뒤라도 사용자 요청은 아직 안 끝났다)

**어느 선을 넘으면 손을 대나**
후기 수와 알림 수가 **하나라도 어긋나면** 원인을 본다.
이건 느려지는 문제가 아니라 **조용히 어긋나는 문제**라, 기준선을 느슨하게 두면 의미가 없다.

발송이 응답 시간을 눈에 띄게 늘리면 그건 알림 도메인과 함께 볼 일이다 —
후기 도메인이 혼자 정할 수 있는 범위가 아니다.

### M5. 상품에 저장된 평점이 실제 후기와 같은가

**무슨 일이 일어나나**
상품 목록의 별점이 실제 후기와 다르다. 상품을 평점순으로 정렬하면 **엉뚱한 순서**가 나온다.

**왜 그런가**
평균 평점을 매번 계산하지 않고 `products.average_rating`과 `products.review_count`에 **저장해 둔다.**
빠르지만, 저장해 둔 값과 원본이 어긋날 수 있다는 위험이 따라온다.

누가 이 값을 관리하는지는 `ADR-001`이 정했다 — **후기 도메인이 계산하고, 상품 도메인이 쓴다.**
그래서 어긋나면 **후기 쪽 책임**이다.

`risks.md` R2가 "갱신되지 않는다"는 문제로 한 번 올라왔다가 조각 1·2를 한 배포로 묶어 해소됐다.
**해소됐다는 것은 코드가 맞다는 뜻이지, 앞으로도 계속 맞는다는 보장은 아니다.**

**출발점은 깨끗하다.** `seed-review.sql`이 마지막에 두 값을 실제 후기 기준으로 맞춰 놓고 끝난다.
그러니 시드 직후에 어긋나 있다면 시드의 문제이고, **한동안 앱을 쓴 뒤에 어긋났다면
어딘가에서 재계산이 빠진 것이다.** 둘을 구분할 수 있다는 게 이 지표의 값이다.

**무엇을 보나**
주기적으로 저장된 값과 실제를 대조한다.

```sql
SELECT p.id, p.average_rating, p.review_count,
       COALESCE(AVG(r.overall_rating), 0) AS 실제평점,
       COUNT(r.id)                        AS 실제건수
  FROM products p
  LEFT JOIN reviews r ON r.product_id = p.id AND r.status = 'PUBLISHED'
 GROUP BY p.id
HAVING p.review_count <> COUNT(r.id)
```

**어느 선을 넘으면 손을 대나**
**한 건이라도 어긋나면 즉시.** 어긋난 것 자체가 어딘가에서 재계산이 빠졌다는 뜻이다.

특히 확인할 자리는 **관리자가 후기를 숨겼을 때**다.
후기가 `BLOCKED`로 바뀌면 공개 후기 수가 줄어드는데, 그때도 평점이 다시 계산되는지 본다.
(`specs/review-admin.md`의 규칙과 대조한다.)

### M6. 관리자 검색이 회원 목록을 통째로 받아 온다

**무슨 일이 일어나나**
관리자가 닉네임으로 후기를 검색할 때, 검색어가 짧으면 **크게 느려진다.**
`김` 한 글자를 치면 수천 명이 걸리는 식이다.

**왜 그런가**
후기 SQL은 회원 테이블을 직접 볼 수 없다(도메인 경계). 그래서 닉네임으로 **회원 ID 목록을 먼저 받아
그걸 `IN` 절에 넣는다.** 그런데 그 목록에 **상한이 없다.**
`risks.md` R12가 적어 둔 자리이고, 상한을 두지 않은 이유까지 함께 적혀 있다 —
상한을 두면 목록과 전체 건수가 갈리기 때문이다.

**무엇을 보나**

- 관리자 후기 검색의 응답 시간을 검색어 길이별로 (한 글자 / 두 글자 / 전체 닉네임)
- 계약이 실제로 돌려주는 ID 개수
- slow query log에 이 쿼리가 올라오는지

**어느 선을 넘으면 손을 대나**
R12가 정한 계기 그대로 — **회원이나 주문 상품이 수천 건을 넘고 검색이 눈에 띄게 느려질 때.**
처방도 R12가 적어 뒀다: 계약을 ID 목록이 아니라 **페이지 결과**를 돌려주는 모양으로 바꾼다.

**이건 다른 도메인과 함께 정할 일이다.** 계약을 바꾸는 것이므로 회원 도메인 담당자와의 합의가 먼저다.
관리자 화면은 사용자가 적어 우선순위가 낮다.

## 3. 요약 — 한 장으로

| | 무엇을 본다 | 왜 중요한가 | 손대는 기준 |
|---|---|---|---|
| **M1** | 후기 수가 다른 상품별 쓰기 응답 시간 | 후기가 많을수록 쓰기가 느려진다 | `risks.md` R8의 계기 |
| **M2** | 잠금 대기와 교착 | 같은 상품 쓰기가 줄을 선다 | 교착 1회 |
| **M3** | 후기 수가 다른 상품별 상세 응답 시간 | 정렬을 인덱스가 못 돕는다 | M1과 함께 |
| **M4** | 후기 수 대비 알림 수 | 실패해도 화면에 안 보인다 | 1건이라도 어긋나면 |
| **M5** | 저장된 평점 대 실제 후기 | 상품 정렬이 틀어진다 | 1건이라도 어긋나면 |
| **M6** | 검색어 길이별 관리자 응답 시간 | `IN` 절에 상한이 없다 | `risks.md` R12의 계기 |

**우선순위**: M5 → M4 → M1·M3 → M2 → M6.

앞의 둘이 먼저인 이유는 **조용히 어긋나는 항목**이라서다.
M1·M3은 느려지면 누구든 알아채지만, M4·M5는 **아무도 모르는 채로 계속 틀린다.**
느린 것은 불편이지만 틀린 것은 신뢰의 문제다.

## 4. 순서

1. **계측을 붙인다** — `docs/community/MONITORING.md` 1절. 후기 코드는 안 건드린다
2. **M5·M4의 대조 쿼리를 먼저 만든다** — 데이터를 많이 심지 않아도 지금 바로 돌릴 수 있다.
   **이미 어긋나 있는지부터 확인한다**
3. **데이터를 심는다** — 한 상품에 500건·5,000건 (1절)
4. **M1·M3을 잰다** — R8의 계기에 닿았는지 판정한다. 둘은 같은 인덱스로 같이 풀린다
5. **M2를 잰다** — 교착이 0인지만 확인하면 당장은 충분하다
6. **M6은 관측만** — 관리자 화면이라 우선순위가 낮다

## 5. 결과를 어디에 적나

**측정값과 해석을 갈라 적는다.** 측정값은 잰 조건(상품별 후기 수, 어떤 PC, 힙 크기)과 함께 적어야
나중에 다시 잴 수 있고, 해석은 그 조건에서만 유효하다는 단서와 함께 적는다.
조건 없이 적으면 다음 사람이 그 숫자를 절대값으로 믿는다.

파이프라인 자리는 평소와 같다.

- **R8·R12에 실측값이 붙으면 그 행을 갱신한다.** 새 행을 만들지 않는다 — 같은 위험이다
- 새 문제가 나왔다 → `reviews/risks.md`에 새 `R#`
- 그래서 이렇게 하기로 했다 → `decisions/decision-log.md`에 날짜 한 줄
- 규칙이 바뀌었다 → `DOMAIN.md` 또는 해당 `specs/*.md`
- **재 봤더니 괜찮더라도 적는다** — 그게 다음 사람이 같은 걱정을 반복하지 않게 하는 값이다
