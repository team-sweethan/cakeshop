# 후기 조회 — B1·B2·B3

> 공통 규칙(상태·평점·권한·검증·오류 코드·표시·도메인 경계)은 `../DOMAIN.md` 2절이 정본이다.
> 조각 순서와 진행 상태는 `../PLAN.md`. 결정의 배경은 `../decisions/`.
> 조각: 3 — **구현 완료**. B2는 조각 2에 딸려 완료됐다.

### B1. 상품 후기 목록

| | |
|---|---|
| 액터 | **누구나** (비로그인 포함) |
| 경로 | 미리보기 `GET /products/{id:\d+}` 안 · 전체 목록 `GET /products/{id:\d+}/reviews` |
| 화면 | `customer/product/detail.html` 후기 영역(미리보기) · `customer/review/product.html`(전체) |

**후기는 두 자리에 나뉘어 붙는다.**

| 자리 | 개수 | 페이징 |
|---|---|---|
| 상품 상세 후기 영역 | 최신순 **3개** | 없음. 아래에 `전체 리뷰 확인` 버튼 → `/products/{id}/reviews` |
| 전체 목록 페이지 | 전부 | 여기에만 둔다 |

미리보기를 3개로 고정한 덕에 **상세 렌더링에 모델로 주입해도 된다.** 원래 걸림돌은 "페이징 있는 목록을 상세에 통째로 실으면 2페이지부터 갈 곳이 없다"는 것이었는데, 개수를 묶어 그 문제가 사라졌다.

**처리**

- **먼저 그 상품이 고객에게 공개되는 상품인지 확인한다.** 아니면 `404`다.
  - `ProductQueryService.getSalesInfo(productId)`가 이미 있다(`docs/conventions.md` 12절의 최소 공개 계약). 리뷰가 `products`를 직접 조회하지 않는다.
  - **`NOT_ON_SALE`을 그대로 흘리지 않고 404로 바꾼다.** 그 계약은 없는 상품에는 `NOT_FOUND` 404를, `INACTIVE` 상품에는 `NOT_ON_SALE` 400을 던진다. 두 응답이 갈리면 주소를 훑어 **"있지만 판매 중지된 상품"을 골라낼 수 있어** 가리려던 것이 그대로 드러난다. 리뷰 쪽에서 두 경우 모두 `REVIEW_NOT_FOUND` 404로 잡는다. `DOMAIN 2.5`의 소유권 판정과 같은 이유다.
  - **없으면 판매 중지 상품의 후기가 계속 공개된다.** `ProductMapper.xml`은 상품 상세를 `p.status = 'ACTIVE'`로 거르는데 후기 목록은 후기의 `status`만 본다. 상품 화면에서는 사라진 상품인데 `/products/{id}/reviews`를 직접 부르면 후기 본문과 작성자 닉네임이 그대로 나온다.
  - 화면 안에서는 드러나지 않는다. 상세가 이미 404라 후기 영역까지 갈 일이 없고, **주소를 직접 넣는 경로에서만 보인다.**
- `WHERE r.product_id = ? AND r.status = 'PUBLISHED'`. 후기의 노출 판단은 `status` 하나다(`DOMAIN 2.1`). 위 상품 확인은 후기 조건이 아니라 **선행 관문**이라 이 원칙과 어긋나지 않는다.
- 정렬은 `created_at DESC, id DESC`. **`id` tiebreaker는 반드시 붙인다** — 없으면 동일 시각 후기가 두 페이지에 중복되거나 누락된다.
- **페이징은 전체 목록 페이지에만 둔다.** `PageRequest`/`PageResult` 재사용. 미리보기 3개는 페이징하지 않는다.

**출력**: 작성자명(`DOMAIN 2.6`), 평점 4종, 본문, 작성일, 답글(B4 `review-reply.md` — 조각 6에서 붙었다)

**빈 목록**: `아직 등록된 후기가 없습니다.` 목업의 `준비 중` 문구를 이것으로 대체했다. 미리보기가 비면 `전체 리뷰 확인` 버튼도 띄우지 않는다 — 눌러 봐야 빈 화면이기 때문이다.

한 건의 표시는 미리보기와 전체 목록이 `fragments/customer/product-review.html`을 함께 쓴다(`../DOMAIN.md` 3절).

> **붙이는 방식은 2026-08-06 시은님과 합의해 정해졌다.** 상세 안 미리보기 3개는 `ProductController.detail`이 리뷰 계약을 불러 **모델에 담고**, 전체 목록은 리뷰가 소유한 별도 화면이 맡는다. fragment/API 방식은 택하지 않았다 — 개수가 3개로 고정되어 모델 주입으로 충분하다.
>
> - **`detail.html`과 `ProductController`는 시은님 담당이다.** 후기 영역 교체와 모델 주입이 그쪽 파일에 들어갔고, 주입 필드에 작성자·담당자 주석을 남겼다(`domain/review/CLAUDE.md`). **조각 3에서 담당자 파일을 고친 자리는 여기뿐이다.**
> - **검증에 "상품 상세 화면 자체가 후기 3개를 렌더링하는지"를 넣었다.** 전체 목록 경로 응답만 확인하면 이 구멍이 그대로 통과한다.
> - 계약은 리뷰가 소유하는 `ReviewProductQueryService.getPreview`다. 상품이 `reviews`를 읽지 않게 방향만 반대로 둔 것이고, 이름과 위치는 `../DOMAIN.md` 2.7이 정본이다.

> 상품별 후기 조회를 받쳐 줄 인덱스가 `fk_reviews_product`뿐이라 정렬에 filesort가 붙는다. 1차 데이터로는 문제가 없다. 되돌아올 계기는 `PLAN.md` R8에 있다.

### B2. 상품 평균 평점·후기 수

**화면은 처음부터 완성되어 있었다.** `product.averageRating`·`product.reviewCount`가 상품 상세에 바인딩되어 있고 `ProductMapper.xml`이 조회한다.

**막혀 있던 것은 값이었다** — 갱신하는 코드가 없어 영원히 0이었다. 조각 2의 D1(`product-rating.md`) 집계 갱신이 들어오면서 이 항목은 화면을 건드리지 않고 완료됐다.

### B3. 내가 쓴 후기 목록

| | |
|---|---|
| 액터 | 로그인 고객 |
| 경로 | `GET /mypage/reviews` · 알림 진입 `GET /mypage/reviews/{reviewId:\d+}` |
| 화면 | `customer/review/my.html` |

**처리**

- `WHERE r.member_id = 인증회원 AND r.status <> 'DELETED'`.
- **`BLOCKED` 후기도 본인에게는 보인다.** 숨겨진 사실을 본인이 알아야 한다. 화면에는 `숨김` 표시가 붙는다. 조각 4에서 생긴 수정·삭제 버튼은 **`BLOCKED`에는 뜨지 않는다** — 숨겨진 후기에 작성자가 할 수 있는 일은 없다(`DOMAIN 2.1`).
- 정렬 `created_at DESC, id DESC`.

- 상품명·주문번호는 `OrderReviewQueryService.findOrderItemSnapshots` 묶음 조회로 받는다(`../DOMAIN.md` 2.7). **작성자 표시명 계약은 부르지 않는다** — 보는 사람이 곧 작성자다.
- **각 항목의 상품명이 그 상품의 후기 목록(B1)으로 가는 링크다.** `/products/{id}/reviews`로 간다.
  - 조각 3에서는 카드 전체가 앵커였다. **조각 4에서 수정·삭제가 카드 안으로 들어오면서 상품명으로 좁혔다** — 앵커 안의 버튼과 폼은 유효하지 않은 마크업이고, 삭제 확인창이 앵커의 이동과 겹친다.
  - 링크의 상품 식별자는 **주문 스냅샷이 아니라 `reviews.product_id`**를 쓴다. 가는 곳이 "그때 산 상품"이 아니라 "지금 이 후기가 붙어 있는 상품"이라서다.
  - **상품이 내려가면 이 링크는 404다.** B1이 판매 중지 상품을 가리는 것과 같은 판정이라 예외를 두지 않았다. 되돌아올 계기: 내 후기에서 404를 만나는 것이 실제로 걸리면, 상품 공개 여부를 묶음으로 받는 계약을 시은님과 새로 만들어 링크를 접는다. 건별 `getSalesInfo` 호출은 N+1이라 답이 아니다.

**출력**: 상품명(`order_items.product_name`), 주문번호, 평점, 본문, 작성일, 상태 표시, 답글(B4 — 조각 6에서 붙었다. **`BLOCKED`면 후기는 보여도 답글은 가린다**), 수정·삭제 버튼(`PUBLISHED`일 때만 — A4·A5(`review-edit-delete.md`), 조각 4에서 붙었다)

버튼을 조각 3에 미리 띄우지 않은 이유는 경로가 아직 없었기 때문이다. 눌러서 404를 만나는 버튼은 없느니만 못하다.

**A1(`review-write.md`)과 다른 목록이다.** A1은 *아직 안 쓴* 것, B3는 *이미 쓴* 것이다. 마이페이지에 링크 두 개가 나란히 있어야 한다.

**알림 진입 경로는 같은 화면을 다른 창으로 그린다.** 대상 후기가 첫 쪽 밖이면 창에 끌어오고, 쪽 번호는 그대로 1이다. 규칙의 정본은 `review-notification.md` D3다.
