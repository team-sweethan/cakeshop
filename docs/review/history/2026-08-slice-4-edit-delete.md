# 조각 4 — 수정·삭제 (#111, PR #184 머지 완료)

> **끝난 조각의 기록이다. 지금 구속하지 않는다.**
> 이 조각이 만든 규칙의 정본은 `../specs/review-edit-delete.md`.
> 조각 순서와 진행 상태는 `../PLAN.md`, 발견된 문제는 `../reviews/`,
> 방향을 고른 판단은 `../decisions/`에 있다.

**다른 도메인에 새로 만든 계약이 없다.** 후기 한 건을 고치고 지우는 일이라 필요한 값이 전부 `reviews` 안에 있고, 상품 쪽은 조각 2의 `ProductReviewCommandService`를 그대로 부른다. 이 조각에서 남의 파일은 한 줄도 건드리지 않았다.

- 소유권 검증은 인증 사용자 기준으로 Service에서. **소유권과 기대 상태를 UPDATE 조건에 함께 넣는다**(`../specs/review-edit-delete.md` A4, `../DOMAIN.md` 2.1)
- 삭제 = `PUBLISHED → DELETED` 전이, 집계 재호출
- `ReviewErrorCode`에 `BLOCKED_REVIEW`(403)·`INVALID_REVIEW_TRANSITION`(400)이 들어왔다(`../DOMAIN.md` 2.5)
- **B3의 각 항목이 카드 전체 앵커에서 상품명 앵커로 바뀌었다** — 수정·삭제가 카드 안으로 들어왔기 때문이다(`../specs/review-read.md` B3)

**검증**: 남의 후기 수정·삭제 거부, `BLOCKED` 후기 수정·삭제 거부, 삭제 후 집계 반영, **평점이 그대로인 수정도 재집계가 도는지**, 삭제 후에도 재작성이 막히는지(`uk_reviews_order_item`), 수정·삭제 동시 실행 뒤 집계가 실제 행과 맞는지, **상품 잠금을 기다리는 동안 커밋된 삭제를 원인 재판정이 보는지**.

**동시 실행 검증에 빠졌던 자리는 조각 5에서 메웠다.** `../DOMAIN.md` 2.1이 든 예는 **작성자 삭제(A5)와 관리자 숨김(C4)**이 겹치는 경우인데 당시 C4가 없어 재현할 수 없었다. 조각 5에서 동시 요청 테스트 두 건으로 고정했다(아래).
