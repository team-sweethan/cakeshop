# cakeshop 테스트 규칙

이 문서는 cakeshop에서 테스트의 범위, 중복과 유지 비용을 판단하는 정본이다.

테스트의 목표는 개수나 coverage 수치를 늘리는 것이 아니라 **변경으로 생긴 위험을 가장 작은 범위에서
재현 가능하게 검증하는 것**이다. 같은 결함을 잡는 테스트를 여러 계층에 반복하지 않는다.

- 코드와 계층 책임: [conventions.md](conventions.md)

## 1. 작성 원칙과 종료 조건

### 필수 원칙

- 새 업무 동작과 버그 수정에는 그 변경을 검증하는 테스트가 있어야 한다. 기존 테스트가 같은 위험을
  이미 검증한다면 새 테스트를 추가하지 않아도 된다.
- 테스트는 독립 실행할 수 있어야 하며 실행 순서, 실제 시각, 로컬 경로와 개인 환경에 의존하지 않는다.
- 운영·공용 DB와 실제 외부 API를 호출하지 않는다.
- 실패를 통과시키기 위해 테스트를 삭제하거나 `@Disabled`를 붙이거나 assertion을 약화하지 않는다.
- 공유 브랜치에 push하거나 PR을 올리기 전에 전체 테스트를 통과시킨다.

### 테스트를 추가하지 않아도 되는 경우

- 문구·주석·문서만 바뀌고 실행 동작이 변하지 않는다.
- 외부 동작이 같은 내부 리팩터링이며 기존 테스트가 그 동작을 충분히 보호한다.
- 이미 더 작은 계층의 테스트가 동일한 조건·행위·결과를 검증하고 새 결함 가능성이 추가되지 않았다.
- 프레임워크나 Lombok 자체의 동작을 다시 검증하는 테스트밖에 만들 수 없다.

테스트가 없는 이유를 감추기 위해 형식적인 정상 경로 하나를 추가하지 않는다. 변경 위험이 없다면
추가하지 않고, 위험이 있다면 그 위험을 직접 검증한다.

### 종료 조건

다음을 모두 만족하면 테스트 작성은 충분하다.

1. 변경으로 생긴 업무·보안·데이터 위험을 목록으로 설명할 수 있다.
2. 각 위험을 담당하는 테스트가 하나 이상 있다.
3. 각 테스트는 그 위험을 검증할 수 있는 가장 작은 계층에 있다.
4. 같은 결함을 잡는 더 느리거나 넓은 테스트가 불필요하게 반복되지 않는다.
5. 전체 테스트가 독립적으로 통과한다.

정상·실패·경곗값을 기계적으로 모두 채우는 것은 종료 조건이 아니다. 요구사항상 결과가 달라지는
대표값과 실제 장애로 이어질 경계만 선택한다.

## 2. 변경 위험에 따른 테스트 선택

가장 작은 테스트로 시작하고, 그 테스트가 잡지 못하는 결함이 있을 때만 범위를 넓힌다.

| 변경 | 기본 선택 | 더 넓은 테스트가 필요한 경우 |
|---|---|---|
| 순수 계산·enum 전이·값 객체 | JUnit 단위 테스트 | 없음 |
| Service 업무 규칙 | 실제 Service + mock 협력 객체 | 트랜잭션·잠금·실제 Bean 연결이 위험일 때 |
| Controller 바인딩·검증·응답 | standalone MockMvc | 실제 Security filter가 검증 대상일 때 |
| Mapper XML·SQL·DB 제약 | `@MybatisTest` + MariaDB | 여러 Service·Mapper의 원자성이 검증 대상일 때 |
| Security URL·CSRF·역할 정책 | `@WebMvcTest` + 실제 Security 설정 | 전체 로그인 흐름이 검증 대상일 때 |
| 트랜잭션·잠금·동시성 | 필요한 Bean만 포함한 Spring 통합 테스트 | 전체 애플리케이션 wiring 자체가 위험일 때 |
| Thymeleaf 템플릿 연결 | 대표 렌더링 smoke test | 중요한 조건부 노출이 서버 모델과 함께 깨질 수 있을 때 |
| 파일·외부 client | 임시 자원과 fake·stub | 실제 프로토콜 호환을 검증할 별도 테스트 환경이 있을 때 |

변경 종류별 기본 판단은 다음과 같다.

- **버그 수정**: 수정 전 실패하고 수정 후 통과하는 회귀 테스트를 가장 낮은 유효 계층에 추가한다.
- **업무 규칙 추가**: 대표 정상 경로와 결과가 달라지는 주요 거부·경계만 규칙 소유 계층에 추가한다.
- **SQL 변경**: 변경된 필터·정렬·갱신 행 수·매핑을 Mapper 통합 테스트로 검증한다.
- **권한 변경**: URL 역할 정책은 Security 테스트, 자원 소유권은 Service 테스트로 검증한다.
- **트랜잭션 변경**: 중간 실패 시 전체 rollback을 실제 DB 통합 테스트로 검증한다.
- **단순 리팩터링**: 기존 테스트가 외부 동작을 보호하면 새 테스트를 추가하지 않는다.

가능한 입력의 모든 조합을 만들지 않는다. 조합에 따라 결과가 달라지는 조건만 고르고, 같은 규칙의
입력 표라면 `@ParameterizedTest`로 묶는다.

## 3. 계층별 검증 책임

하나의 업무 규칙에는 **주된 테스트 소유 계층**이 있어야 한다. 상위 계층은 연결 계약만 확인하고
하위 계층의 모든 사례를 반복하지 않는다.

### 순수 객체

- 계산, 정규화와 상태 전이 결과를 검증한다.
- getter·setter, record accessor, 단순 생성자와 Lombok 생성 결과는 검증하지 않는다.
- 같은 전이표나 경곗값 집합은 parameterized test 하나로 표현한다.

### Controller

- URL·HTTP method, Form 바인딩과 Bean Validation을 검증한다.
- 성공 시 View 또는 redirect, 실패 시 필드 오류와 재렌더링을 검증한다.
- Controller가 Service에 전달하는 공개 입력과 응답 Model의 필수 계약만 검증한다.
- Service의 상태 전이, 소유권 판단과 계산 결과를 다시 검증하지 않는다.
- 검증 실패 시 Service를 호출하지 않아야 하는 등 웹 흐름상 의미 있는 호출만 `verify`한다.

기본은 `MockMvcBuilders.standaloneSetup`이다. 실제 인증 principal, 역할, CSRF와 Security filter가
검증 대상이면 [8절](#8-security화면외부-시스템)의 Security 테스트를 사용한다.

### Service

- 업무 규칙, 상태 전이, 소유권, ErrorCode와 협력 객체에 전달하는 업무 명령을 검증한다.
- 실제 Service를 사용하고 외부 협력 객체만 mock으로 둔다.
- Mapper SQL 결과, Spring transaction rollback과 Security filter 동작을 단위 테스트로 증명하려 하지 않는다.
- 협력 객체 호출 순서는 잠금 순서나 외부 부작용 순서처럼 업무 계약일 때만 검증한다.

### Mapper

- 실제 XML을 MariaDB에서 실행해 SQL, 타입 매핑, 필터·정렬, 제약과 갱신 행 수를 검증한다.
- Service가 처리할 업무 분기와 Controller 응답을 검증하지 않는다.
- SQL 구현 형태가 아니라 결과를 검증한다. 특정 잠금문이나 실행 계획이 요구사항일 때만 형태를 고정한다.

### 통합 테스트

- 단위 테스트가 증명할 수 없는 transaction rollback, 실제 Bean wiring, 잠금과 동시성만 검증한다.
- 넓은 테스트 하나로 이미 빠른 단위 테스트가 검증하는 모든 실패 사례를 반복하지 않는다.
- 핵심 정상 흐름은 smoke test로 남길 수 있지만 세부 업무 분기는 소유 계층 테스트에 맡긴다.
- `@SpringBootTest`는 전체 Context가 필요한 이유를 설명할 수 있을 때만 사용한다.

## 4. 중복·통합·삭제 기준

### 중복 판정

두 테스트가 다음 세 가지를 모두 공유하면 계층이나 클래스가 달라도 중복으로 본다.

1. 같은 사전 조건
2. 같은 행위
3. 같은 관찰 결과로 같은 종류의 결함을 검출

다음처럼 검출하는 결함이 다르면 같은 업무 문장이 등장해도 중복이 아니다.

- Service 테스트의 금지 상태 전이와 DB 테스트의 허용 값 `CHECK` 제약
- Controller 테스트의 빈 Form 거부와 Service 테스트의 자원 소유권 거부
- Mapper 테스트의 조건부 UPDATE 0행과 통합 테스트의 여러 쓰기 rollback

넓은 통합 테스트와 작은 단위 테스트가 같은 결함을 잡는다면 작은 테스트를 주된 소유자로 남긴다.
통합 테스트는 wiring이나 대표 흐름처럼 그 범위에서만 검증할 수 있는 assertion만 유지한다.

### 통합하거나 줄일 대상

- 동일한 규칙에 입력값만 달라지는 테스트는 parameterized test로 합친다.
- 정렬·필터 조합은 결과가 달라지는 대표 조합만 남긴다. 모든 조합의 곱집합을 만들지 않는다.
- 같은 템플릿의 빈 목록·한 건·여러 건은 UI 결과가 실질적으로 다를 때만 각각 둔다.
- 한 테스트에서 이미 원소와 순서를 검증한다면 별도의 크기 검증 테스트를 추가하지 않는다.
- 동일한 예외를 만드는 여러 내부 경로가 같은 공개 계약이면 대표 경로만 남길 수 있다.

### 삭제 대상

다음 테스트는 고유한 위험을 보호하지 않는 한 삭제한다.

- getter·setter, record accessor, Lombok과 프레임워크 기본 동작 검증
- 현재 private 메서드, 지역 변수, mock 호출 횟수와 내부 구현 순서 고정
- 실제 동작 테스트가 있는데 SQL 문자열·Java 메서드 본문을 다시 파싱하는 테스트
- Markdown에 테스트 클래스·메서드 목록을 적고 그 목록과 소스를 맞추는 테스트
- 화면의 모든 문구나 전체 HTML을 고정하는 snapshot 성격의 테스트
- 이미 작은 테스트가 검증하는 정상 경로를 더 넓은 Context에서 그대로 반복하는 테스트
- coverage 수치만 올리며 실패해도 제품 위험을 설명할 수 없는 테스트

기계적으로 검사할 수 있는 파일 형식, 링크, import와 의존 방향은 formatter·정적 분석·Hook을 우선한다.
JUnit으로 소스와 문서를 파싱하는 검사는 빌드 자체를 깨뜨리는 저장소 불변식이고 전용 도구가 없을
때만 둔다. 테스트 메서드 본문이나 이름 같은 구현 세부는 파싱하지 않는다.

테스트를 삭제하거나 합칠 때는 그 테스트가 보호하던 위험과 남은 소유 테스트를 확인한다. 단순히
현재 통과한다는 이유나 실행 시간을 줄이기 위해 보호 범위를 없애지 않는다.

## 5. 테스트 클래스 구조와 이름

### 위치와 이름

- 운영 코드의 패키지 구조를 `src/test/java` 아래에서 따른다.
- 기본 클래스명은 `<대상클래스명>Tests`다.
- 특정 관심사나 실행 환경을 분리하면 `<대상><관심사>Tests`로 이름 짓는다.
- 설정·스키마·아키텍처처럼 특정 클래스가 대상이 아니면 검증 대상을 클래스명에 사용한다.
- 모든 테스트 클래스는 `Tests`로 끝낸다.
- 메서드명은 `method_condition_expectedResult` 구조로 작성한다.

### 한 클래스에 둘 기준

다음이 같으면 한 테스트 클래스에 둔다.

- 테스트 대상
- Context와 주요 fixture
- 검증하는 업무 책임

같은 대상 안에서 목록·작성·삭제처럼 관심사만 구분하면 `@Nested`를 사용할 수 있다. fixture와 실행
환경이 같다면 파일 수를 늘리기 위해 별도 클래스를 만들지 않는다.

다음 중 하나에 해당하면 별도 클래스로 분리한다.

- 필요한 Spring Context나 테스트 종류가 다르다.
- 공통 fixture보다 관심사별 준비 코드가 더 많다.
- 서로 독립적으로 변경되는 업무 책임을 다룬다.
- 한 클래스에서 원하는 테스트를 찾고 실패 원인을 파악하기 어렵다.

테스트 메서드 30개 또는 600줄을 넘으면 **분리 강제가 아니라 책임 재검토 신호**로 본다. 테스트만
나누기 전에 운영 클래스가 너무 많은 책임을 가진 것은 아닌지 먼저 확인한다. 반대로 한두 테스트만
있는 파일은 독립된 실행 환경이나 저장소 불변식을 검증하는 경우가 아니라면 기존 클래스와 합친다.

### 본문과 fixture

- 한 테스트는 하나의 시나리오와 하나의 실패 원인을 다룬다. assertion 개수는 하나로 제한하지 않는다.
- Given-When-Then 흐름이 읽히게 작성하되 기계적인 주석을 반드시 붙이지 않는다.
- `@BeforeEach`에는 모든 테스트가 공통으로 사용하는 최소 설정만 둔다.
- fixture helper는 기본값을 예측할 수 있게 만들고, 결과에 영향을 주는 값은 호출부에 드러낸다.
- 공통화 때문에 행위와 기대 결과가 숨겨지면 중복 몇 줄을 허용한다.

## 6. Mock·fixture·assertion

### Mock

- 테스트 대상의 외부 협력 객체만 mock으로 둔다. 테스트 대상과 private 메서드를 mock하지 않는다.
- DTO, enum과 값 객체는 실제 객체를 사용한다.
- 반환값·상태만으로 충분하면 `verify`를 추가하지 않는다.
- `InOrder`는 호출 순서가 업무 안전성이나 외부 부작용에 영향을 줄 때만 사용한다.
- 광범위한 `any()`와 `lenient()`로 잘못된 입력이나 불필요한 stubbing을 숨기지 않는다.

### Fixture와 데이터

- 각 테스트는 필요한 데이터를 직접 준비하고 다른 테스트나 로컬 seed에 의존하지 않는다.
- 자동 생성 PK를 예상하지 않고 실제 생성 결과를 사용한다.
- 핵심 조건이 아닌 값은 fixture 기본값으로 둘 수 있다. 테스트 결과를 가르는 값은 명시한다.
- 운영 개인정보를 복사하지 않는다.
- 시각은 `Clock` 같은 주입 가능한 경계로 고정한다. 무작위 값은 seed를 고정해 재현 가능하게 한다.

### Assertion

- AssertJ `assertThat`을 기본으로 사용한다.
- 업무 예외는 타입과 `ErrorCode`를 함께 검증한다.
- 컬렉션은 크기만 확인하지 말고 필요한 원소와 의미 있는 순서를 검증한다.
- `isNotNull()`이나 HTTP 상태 하나만으로 업무 결과 검증을 끝내지 않는다.
- 구현 세부 대신 반환값, 상태 변화, 저장 결과와 공개된 부작용을 검증한다.
- 전체 HTML·SQL 문자열보다 필요한 공개 계약만 검증한다.

## 7. DB·트랜잭션·동시성

### MariaDB 통합 환경

DB 동작은 H2나 개인 DB가 아니라 MariaDB Testcontainers로 검증한다.

```java
@MybatisTest
@MariaDbIntegrationTest
@AutoConfigureTestDatabase(replace = Replace.NONE)
class ProductMapperTests {
}
```

- 공통 `@MariaDbIntegrationTest`와 `MariaDbTestContainerConfig`를 사용한다.
- datasource 주소와 MariaDB image 버전은 공통 설정 한 곳에서 관리한다.
- schema는 실제 Flyway migration으로 만들고 로컬 seed에 의존하지 않는다.
- 테스트마다 필요한 행을 직접 만들고 transaction rollback 또는 명시적 정리로 격리한다.
- 컨테이너를 테스트 메서드마다 새로 만들지 않는다.
- DB 통합 테스트는 병렬 실행하지 않는다.
- MariaDB Testcontainers를 사용하는 테스트는 공통 `@MariaDbIntegrationTest`를 붙인다. 공통 Spring
  설정을 쓸 수 없어 컨테이너를 직접 띄우는 테스트는 클래스에 `@Tag("mariadb")`를 붙인다. 이 태그가
  CI의 `unitTest`와 `mariaDbTest` 분리 경계다.

Spring 기동 실패 자체를 검증하는 등 공통 Context로 만들 수 없는 상태만 테스트가 컨테이너를 직접
관리할 수 있다. 이 경우 일반 설정을 사용할 수 없는 이유를 클래스에 남긴다.

### Mapper와 스키마

- 변경한 SQL의 대표 정상 결과와 중요한 제외 조건을 검증한다.
- insert 생성 키, 조건부 update·delete의 영향 행 수와 필요한 DB 제약을 검증한다.
- enum·날짜·금액처럼 MariaDB 매핑이 중요한 타입을 검증한다.
- 모든 status 값을 각 Mapper 테스트에서 반복하지 않는다. 스키마 제약 테스트가 값 집합을 소유한다.
- Flyway 파일명·전체 적용·실패 안내 같은 저장소 공통 규칙은 global 테스트 한 곳에서 검증한다.

정확한 SQL 문장, scalar subquery 사용 여부와 내부 JOIN 순서는 성능·잠금 요구가 아닌 한 고정하지 않는다.
쿼리 수 테스트는 실제 N+1 회귀가 있었거나 명시적인 성능 요구가 있는 조회에만 두고 대표 데이터 규모
하나로 검증한다.

### 트랜잭션과 동시성

- 여러 쓰기 중 하나를 의도적으로 실패시켜 전체 rollback을 검증한다.
- mock 단위 테스트로 rollback이나 DB 잠금을 증명하지 않는다.
- 동시성 테스트는 실제로 경쟁 상태가 가능한 쓰기에만 작성한다.
- `Thread.sleep()`으로 실행 순서를 맞추지 않고 latch·barrier 등 결정적인 동기화 수단을 사용한다.
- 처리 순서보다 최종 데이터 불변식, 중복 반영 여부와 교착 상태 발생 여부를 검증한다.
- 같은 경쟁 조건을 단위·Mapper·Spring 통합 테스트에 반복하지 않는다.

## 8. Security·화면·외부 시스템

### Security

- 공통 URL 패턴, 로그인·로그아웃, 역할 접근과 CSRF 정책은 실제 Security 설정을 사용하는 테스트가
  소유한다.
- 같은 `/admin/**` 정책을 모든 Controller에서 반복하지 않는다. 공통 정책의 대표 경로와 예외적으로
  다른 경로만 추가한다.
- 같은 URL 안의 회원 소유권과 상태별 업무 거부는 Service 테스트가 소유한다.
- 화면에서 버튼을 숨기는 테스트는 서버 인가 테스트를 대신하지 않는다.
- standalone MockMvc로 Security filter 동작을 검증했다고 주장하지 않는다.

### Thymeleaf 화면

- 템플릿명과 Model 연결은 템플릿별 대표 렌더링 smoke test로 검증한다.
- 비어 있음, 한 건, 여러 건을 모두 렌더링하지 않고 결과가 실질적으로 달라지는 상태만 선택한다.
- 권한별 버튼, 모든 안내 문구와 모든 HTML 조각을 테스트로 고정하지 않는다.
- 사용자 입력 escaping처럼 보안상 중요한 출력은 대표 입력으로 검증할 수 있다.
- 화면 명세 Markdown이 테스트 메서드명이나 assertion 본문을 참조하도록 만들지 않는다.

### 파일과 외부 시스템

- 파일 테스트는 JUnit `@TempDir` 아래에서 실행한다.
- 실제 이메일, 결제, 알림과 클라우드 저장소를 호출하지 않는다.
- 외부 client 경계에서 fake·stub 또는 대역 서버를 사용한다.
- timeout, 오류와 중복 응답이 업무 결과를 바꾸는 경우에만 해당 실패 경로를 검증한다.
- 테스트가 만든 파일 핸들, 서버와 자원을 종료 후 정리한다.

## 9. 실행과 유지보수

개발 중에는 변경 대상 테스트를 먼저 실행하고, 공유 브랜치에 push하거나 PR을 올리기 전에는
README의 명령으로 전체 테스트를 실행한다. CI 설정과 required check는 workflow와
[pull-request.md](pull-request.md)를 정본으로 한다.

CI는 DB 없는 `unitTest`와 `mariaDbTest`를 별도 러너에서 병렬 실행한다. `unitTest`만 두 JVM으로
나누고 `mariaDbTest`는 위의 동시성 규칙대로 한 JVM에서 순차 실행한다. 두 결과는 branch protection의
기존 필수 체크 이름인 `Test` 잡이 합친다.

문서와 마크다운만 바뀐 변경에서는 두 잡이 테스트 실행을 건너뛴다. 생략해도 되는 경로의 목록과
판정 방식은 workflow가 정본이다.

- 테스트 실패는 제품 코드 결함, 테스트 결함, 환경 결함 중 무엇인지 먼저 구분한다.
- 같은 원인의 flaky test를 재실행 횟수로 숨기지 않는다.
- flaky test는 데이터 격리, 비동기 동기화와 시각 의존성을 먼저 확인한다.
- 테스트 이름 변경·분리·삭제만을 위한 대규모 정리는 기능 변경과 분리한다.
- 관련 기능을 수정할 때 발견한 작은 중복은 같은 변경에서 정리할 수 있다.
- coverage 백분율을 목표로 테스트를 추가하지 않는다. 업무·보안·데이터 위험의 누락을 검토한다.

리뷰에서는 다음 질문만 확인한다.

1. 변경으로 새로 생긴 위험은 무엇인가?
2. 각 위험의 소유 테스트는 어디에 있는가?
3. 더 작은 계층에서 같은 결함을 잡을 수 있는가?
4. 이미 같은 조건·행위·결과를 검증하는 테스트가 있는가?
5. 이 테스트를 삭제하면 사라지는 보호 범위를 설명할 수 있는가?
6. 테스트 비용이 보호하는 위험보다 커지지 않았는가?
