# 측정 전용 데이터

성능을 재려면 데이터가 있어야 한다. 개발용 DB에는 게시글 30건·후기 5건뿐이라
**무엇을 재도 전부 빠르다** — 인덱스가 있고 없고의 차이가 나타나지 않는 규모다.

이 폴더는 측정용 DB(`cakeshop_perf`)를 만들고 채우는 스크립트를 담는다.
**무엇을 볼지**는 `docs/community/MONITORING.md`와 `docs/review/MONITORING.md`가 정한다.

> **개발용 DB(`cakeshop`)는 건드리지 않는다.** 이름이 다른 별도 DB라
> 이 스크립트가 개발 데이터에 닿을 방법이 없다. 끝나면 통째로 버린다.

## 왜 별도 DB인가

개발용 DB에 그냥 부으면 셋이 문제가 된다.

1. **화면 확인이 망가진다.** 게시글 목록에 측정용 글 10만 건이 섞인다.
2. **되돌리기가 위험하다.** 측정 데이터만 골라 지워야 하는데 조건 하나 틀리면 개발 데이터가 날아간다.
3. **지워도 디스크가 안 준다.** 행을 지워도 `.ibd` 파일은 그대로라 `OPTIMIZE TABLE`을 따로 돌려야 한다.

별도 DB면 정리가 `DROP DATABASE` 한 줄이고, `innodb_file_per_table`이 켜져 있어
**디스크가 실제로 반환된다.**

## 만드는 순서

**1. 빈 DB를 만든다.**

```bash
mariadb -P 3307 -u root -p -e "CREATE DATABASE cakeshop_perf CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci"
```

**2. 앱을 그 DB로 한 번 띄운다.** Flyway가 스키마를 만든다.

```bash
java -jar build/libs/cakeshop-0.0.1-SNAPSHOT.jar --spring.profiles.active=local,s3,oauth --server.port=8081 "--spring.datasource.url=jdbc:mariadb://localhost:3307/cakeshop_perf?connectionTimeZone=+09:00&forceConnectionTimeZoneToSession=true"
```

테이블 50개가 생기고 기준 데이터(매장 1건, 게시글 카테고리 3종)도 함께 들어온다.
로그에 `Migrating schema`가 쭉 지나가고 기동이 끝나면 **앱을 내린다.**

따옴표가 필요한 것은 URL 안의 `&` 때문이고, 포트를 8081로 옮긴 것은
개발용 앱이 8080에 떠 있어도 부딪히지 않게 하려는 것이다.

**3. 데이터를 붓는다.** 순서를 지킨다 — 뒤의 둘은 `01`이 만든 부모에 붙는다.

```bash
for f in 01-parents 02-community 03-review; do mariadb -P 3307 -u root -p --default-character-set=utf8mb4 cakeshop_perf < monitoring/perf-data/$f.sql; done
```

각 스크립트 끝에 확인 조회가 붙어 있다. 아래 값이 나와야 한다.

| 스크립트 | 확인할 것 |
|---|---|
| `01-parents` | 회원 1,001 · 상품 50 · 주문 6,000 · 주문상품 6,000 |
| `02-community` | 게시글 100,000 · 댓글 1,000,000, 그리고 카테고리별 1쪽 댓글 수가 **500 / 100 / 0** |
| `03-review` | 상품 1·2·3의 후기가 **10 / 500 / 5,000**, 마지막 대조 조회가 **0행** |

## 무엇이 들어 있나

**커뮤니티 — 댓글 밀도를 카테고리로 갈랐다.**

| 카테고리 | 게시글 | 댓글 | 쓰임 |
|---|---|---|---|
| 질문(1) | 20,000 | 최신 1,000개에 글당 **500** | 최악 |
| 후기(2) | 30,000 | 최신 5,000개에 글당 **100** | 중간 |
| 자유(3) | 50,000 | **없음** | 대조군 |

**이렇게 가른 것이 이 데이터의 핵심이다.** M1이 재려는 것은 "목록 한 쪽을 그릴 때
댓글 수가 비용을 정하는가"인데, 보통은 댓글 많은 글과 적은 글을 비교하려면 쪽 번호를
바꿔야 하고 그러면 `OFFSET` 비용이 함께 변해 원인이 갈리지 않는다.

카테고리로 가르면 두 조회가 **같은 정렬·같은 1쪽·같은 `OFFSET`**이고 다른 것은 댓글 수뿐이다.

```
GET /community?categoryId=1&page=1    ← 1쪽에 댓글 500짜리 글 20개
GET /community?categoryId=3&page=1    ← 1쪽에 댓글 0짜리 글 20개
```

`created_at`을 id 순으로 늘려 심었기 때문에 **카테고리별 1쪽 = 그 카테고리의 가장 큰 id 20개**로
예측 가능하다.

**후기 — 한 상품이 가진 수를 갈랐다.**

| 상품 | 후기 |
|---|---|
| 1 `측정상품A-후기10` | 10 |
| 2 `측정상품B-후기500` | 500 |
| 3 `측정상품C-후기5000` | 5,000 |

이 도메인의 비용은 후기 총량이 아니라 **한 상품이 가진 후기 수**가 정한다.
후기를 하나 쓸 때마다 `aggregateForUpdate`가 그 상품의 공개 후기를 전부 읽고,
상품 상세의 목록·건수도 같은 조건으로 훑는다(M1·M3). 500건은 `risks.md` R8이
되돌아올 계기로 적은 "한 상품의 후기가 수백 건" 근처다.

## 크기와 시간

| | |
|---|---|
| 생성 시간 | **9초** 남짓 (부모 0.3초 + 커뮤니티 8.6초 + 후기 0.2초) |
| DB 크기 | **약 394 MB** (데이터 242 + 인덱스 152) |

**버퍼 풀(약 4 GB)에 다 들어간다.** 그래서 워밍업 뒤에는 전부 메모리에서 읽힌다.

- **좋은 점**: 디스크 I/O가 변수에서 빠져 **인덱스 유무의 순수한 차이**가 깨끗하게 보인다.
  M1·M2처럼 "몇 줄을 훑느냐"가 쟁점인 항목에는 오히려 이상적이다.
- **한계**: "데이터가 메모리보다 커지면 어떻게 되나"는 못 본다. 이번 범위 밖이다.

버퍼 풀은 **서버 전체 공유**라 DB를 나눠도 메모리는 안 나뉜다. 측정 중에는 개발용 DB를
쓰지 않는 편이 낫다.

## 지울 때

```bash
mariadb -P 3307 -u root -p < monitoring/perf-data/teardown.sql
```

## 알아 둘 것

- **이 데이터는 앱을 거치지 않고 들어간다.** 그래서 후기에는 `NEW_REVIEW` 알림이 없다.
  M4 대조의 측정 창(최근 7일) 밖이라 안 걸리지만, 창을 늘려 보면 통째로 뜬다 — 정상이다.
- **`post_likes`·`post_views`는 채우지 않았다.** 정렬에 쓰이는 `posts.like_count`·`view_count`
  열은 값이 들어 있지만 원본 행은 없다. 그 둘은 **쓰기 실험(M4·M5)에서 k6가 직접 만든다.**
  대신 지금 상태에서 "저장된 좋아요 수와 실제 행 수 대조"를 하면 어긋난 것처럼 보인다.
- **`db/seed/`와 섞지 않는다.** 거기는 개발용 시드 자리다. 이 스크립트가 그쪽에 있으면
  팀원이 실수로 10만 건을 받게 된다.
